AI Velocity Weekly 04

AI Velocity Weekly

The reviewer approved two writes and one of them ran zero times: this week the count of executions stopped matching the count of approvals

Issue 04 · week ending 25 September 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Kumar

Your agent proposes two changes to a care plan. A pharmacist is shown both, reads both, approves both. Your audit table now holds two approvals with a name and a timestamp on each. Here is the question nobody asks at review: how many writes happened? The frameworks answered it three different ways this week, and none of the answers was two.

In deepagents 0.7.16 the answer is one. A new check runs after the approval middleware and refuses the second mutation of a file in the same model response, so the second approved write is answered with an error and never runs. In llama-index-core below 0.14.25 the answer to a different question, how many times a failing write ran, was two: a tool that committed and then raised was called again with keyword arguments, and the caller saw one call and one error. And Microsoft's Agent Framework team wrote, in a blog post about checkpoint-and-recover hosting, the sentence every architect should pin above the desk: "Recovery does not imply exactly-once execution of external effects."

Issue 03 asked what a yes is bound to: the arguments the model wrote or the ones the tool ran. This week the question moves one step later, to the distance between the approval and the record. A yes is a promise that something will happen once. Zero times and twice are both audit gaps, and both were reachable from a clean install this week with no model key.

Three checks against your own system. For every approval you record, find the tool result with the same call id and assert it succeeded; if you cannot, your approvals table is a wish list. For every write tool, work out what happens when it commits and then raises, because a gateway timeout after commit is the ordinary failure, and count the rows. And if you run anything that recovers from a checkpoint, make every external write idempotent, because the vendor has now told you in writing that it will not do that for you.

If this is your first issue, read the Start here page first; it sets out the obligations and the vocabulary used below.

1.1 deepagents 0.7.16: the second approved write executes zero times executed

The problem: a reviewer approves two changes to the same record in one model turn, and you assume both happened.

Commit 2e2ee91 (20 Sept, #6446, "fix(sdk): reject parallel same-file edits"), released in 0.7.16 on 21 Sept. In libs/deepagents/deepagents/middleware/filesystem.py a new _parallel_file_mutation_error(), docstring "Reject later same-path file mutations in one model response.", is called first thing in FilesystemMiddleware.wrap_tool_call and its async twin. It looks at the most recent AIMessage, walks its tool_calls in order until it reaches the current call, and if any earlier call in {"write_file", "edit_file", "delete"} targets the same validated path, returns ToolMessage(status="error") with "Error: parallel file mutations to the same path are not allowed." The handler is never invoked. The check matches on the argument key file_path only, and only inside deepagents' own file tools.

agent = create_deep_agent(model=scripted, tools=[], interrupt_on={"write_file": True}, checkpointer=InMemorySaver())
out = agent.invoke({"messages": [("user", "Write the plan for pt-123.")]}, cfg)     # model emits two write_file calls
reqs = out["__interrupt__"][0].value["action_requests"]                            # reviewer is shown both
out = agent.invoke(Command(resume={"decisions": [{"type": "approve"}, {"type": "approve"}]}), cfg)
executed = sum(1 for m in out["messages"] if isinstance(m, ToolMessage) and m.status != "error")
print("approved: 2 | executed:", executed, "| record:", out["files"][PLAN]["content"])

Observed, scripted model, no model key. 0.7.15: without a gate, an edit_file (10 to 20 mg) and a write_file (hold the drug, K+ 6.1) in one response both returned status=success and the file ended "Plan: HOLD lisinopril, K+ 6.1 mmol/L, repeat BMP"; with human-in-the-loop, "approved writes: 2 | executed writes: 2 | final file: 'Plan B: HOLD lisinopril, K+ 6.1'". 0.7.16: without a gate, c3 returned status=error 'Error: parallel file mutations to the same path are not allowed.' and the file ended "Plan: start lisinopril 20 mg daily"; with the gate, the reviewer was shown two action requests, approved both, and "approved writes: 2 | executed writes: 1 | final file: 'Plan A: continue lisinopril 20 mg'". The scripted model said "Both plans written." on both versions. Script test_da_parallel_writes.py; full output in section 5.

What it changes. The fix is reasonable: two mutations of one path in one response are a race, and refusing the later one is safer than letting it win. But it runs after HumanInTheLoopMiddleware, so a reviewer can sign a call that the framework has already decided not to execute, and nothing tells them. Your approvals table has two rows, your ToolMessages have one success and one error, and your record has Plan A. Which plan wins also flipped: on 0.7.15 the last call in the model's list wrote the file; on 0.7.16 the first does. An evaluation that scored the agent's final plan on 0.7.15 is measuring a different system on 0.7.16 with no code change on your side. Reconcile approvals against tool results by call id before you report anything as done, and treat an error ToolMessage for an approved call as an incident, not a retry.

  • 0.7.18 (00fef9c, #6299): unknown keys in the task subagent tool are now rejected. Docstring: "Models sometimes put the real instructions under an invented key (e.g. prompt) and leave a short label in description. Ignoring the extra key dispatched the subagent with the label alone and reported success". Before this, a subagent could run on a one-line label while the transcript held the full instruction.
  • 0.7.19 (ca5f0e5, #6519): tool offload paths are bounded and long IDs abbreviated. If you key an audit row on an offloaded result path, read the new bound before you trust old joins.
  • The check inspects only the latest AIMessage. A mutation approved in a previous turn and one in this turn are not compared; the same path can still be written twice across turns.

1.2 llama-index-core 0.14.25: a failing write no longer runs twice executed

The problem: your tool commits to the record and then raises, and the framework, trying to be helpful, calls it again.

Commit e07b962 (#22841, "fix(core): avoid retrying failed function tools"), merged 27 August and first released in 0.14.25 on 21 September. In llama_index/core/tools/calling.py the old call_tool() handled a one-parameter tool as try: tool(single_arg) except Exception: return tool(**arguments), with the comment "some tools will REQUIRE kwargs, so try it". Any exception from the first call, including one raised after a side effect, triggered a second call. The fix adds _function_tool_accepts_kwargs(), which binds the generated arguments to the function's signature before calling, so a FunctionTool is called once. The try-then-kwargs fallback is still there for other BaseTool subclasses.

RECORD = []
def append_note(note: str) -> str:
    RECORD.append(note)                                       # the write commits ...
    raise RuntimeError("EHR gateway: timeout after commit")   # ... then the call fails
out = call_tool(FunctionTool.from_defaults(fn=append_note), {"note": "BP 120/80, K+ 6.1 mmol/L"})
print(out.is_error, len(RECORD))

Observed. 0.14.24: "one call_tool() | is_error=True | tool output: 'Encountered error: EHR gateway: timeout after commit'", "writes in the record: 2". 0.14.25: the same error, "writes in the record: 1". Script test_li_failed_tool_twice.py.

What it changes. This is the twice case. One call in the transcript, one error in the trace, two rows in the record, and no log line anywhere saying a retry happened. A gateway that commits and then times out on the acknowledgement is the ordinary failure mode of an EHR integration, not an edge case. If you have run llama-index agents against a write endpoint on 0.14.24 or earlier, count duplicate rows created within seconds of a tool error. Going forward, give every write an idempotency key the tool checks before it commits, so a second call of any origin is a no-op; the framework's retry policy is not something you control from outside.

  • llama-index-workflows 2.24.1 (ff4fc6b, #762): "Fix serializer selection failing for unhashable workflows.", a regression from the 2.24.0 serializer registry. If you moved to the registry last week and workflows failed to restore, this is why.
  • Custom BaseTool subclasses with one parameter keep the old behaviour. Search your tool package for classes that are not FunctionTool.

1.3 LangGraph 1.2.12: a typed approval, validated for the node and stored raw executed

The problem: an approval arrives as a free-form dict, and a typo becomes a decision.

Commit 448a763 (#8886) shipped in langgraph 1.2.12 on 21 September via 19273fa (#8987). interrupt(value, response_schema=...) in libs/langgraph/langgraph/types.py "Accepts a JSON Schema dict (used as-is, resume values are not validated), or a Pydantic model class, TypedDict, or dataclass, which are converted to JSON Schema for clients and used to validate the resume value; the validated object is what interrupt returns." The code builds a TypeAdapter only for the non-dict case, validates the resume value, and then appends the raw value to scratchpad.resume and sends that list as the persisted RESUME write. langgraph-sdk 0.4.5 mirrors Interrupt.response_schema.

Observed. 1.2.11: TypeError: interrupt() got an unexpected keyword argument 'response_schema'; with no schema, resume {"action": "aprove"} was committed and the node read it as a rejection (written=''). 1.2.12: the surfaced schema had properties ['action', 'reviewer_id']; the same typo raised ValidationError: 2 validation errors for Decision out of invoke() and the graph stayed paused at state.next=('gate',); a valid resume delivered Decision(action='approve', reviewer_id='rn-42') to the node; the same typo against a JSON Schema dict was committed as a rejection, exactly as 1.2.11. Script test_lg_typed_resume.py.

What it changes. This is the first place in the LangChain stack where an approval can be a typed object with an approver id rather than a string, and a bad one is refused before the checkpoint moves. Use a Pydantic model, never a dict; the dict form is a rendering hint that validates nothing. Two things to know before you build the audit row on it. The invalid resume surfaces as an exception from invoke(), not as a fresh interrupt, so your approval service must catch it and re-prompt. And the checkpoint keeps the raw value the client sent, not the validated object, so a reviewer id that Pydantic normalised is stored unnormalised. Store the validated decision yourself, from inside the node, in the state.

  • langchain-core 1.6.5 (19cadaa, #40792): in XML buffer strings "tool-call IDs longer than 64 characters are displayed as the first 64 characters followed by ...; the original messages are not changed." SummarizationMiddleware builds its summary input with get_buffer_string(..., format="xml"), so two call ids sharing a 64-character prefix are indistinguishable in a summary. Never reconcile writes from summary text.
  • langchain-core 1.6.4 (3290757, #40711): BaseChatMessageHistory and InMemoryChatMessageHistory are deprecated, removal 2.0.0. A conversation store built on RunnableWithMessageHistory now has an end date; the replacement is checkpointer state.
  • Unreleased on langchain main (bfa03c8, #40530, 22 Sept): create_agent repairs invalid tool calls by inserting a synthetic error ToolMessage, "could not be executed - arguments were malformed or truncated.", and commits the repaired history as [RemoveMessage(id=REMOVE_ALL_MESSAGES), *repaired, *response]. When it ships, a checkpoint diff will show every message removed and re-added; calls with id is None are skipped and never answered.
  • langsmith 0.14.0 (096ea51, #3520): runs can be addressed by LANGSMITH_AGENT_ID and LANGSMITH_AGENT_ENVIRONMENT; "Both are required and neither is defaulted". A workspace without the feature "rejects these runs with a 403" and warns via warnings.warn, which PYTHONWARNINGS=ignore silences. That is silent trace loss on an audit path; alert on the 403.

1.4 Agent Framework main: an unresolved child approval fails the parent, and a matched result is terminal docs, source read, not executed

The problem: an agent used as a tool by another agent asks for approval, and the parent has nowhere to put it.

No Python or .NET release in window; about 85 commits on main since 1.19.0. 04efdbf (#8527, 21 Sept, "Python: Fail closed on unresolved agent-tool approvals") amends docs/specs/004-python-function-calling-loop.md: "any unresolved child function approval does not enter the caller's approval state or model transcript. An approval-only response fails the agent-tool invocation ... Interactive, delayed, or durable approval belongs in a workflow." Parent and child ToolApprovalMiddleware instances "must use distinct source_id values; an overlap fails before the child runs." c9d63b5 (#8579, breaking): "A matched function_result is terminal regardless of its text, including an exact or embedded [APPROVAL_PENDING]. Legacy textual placeholder results are no longer supported." 898f6bf (#8595): sequential orchestration output now comes only from the request-info executor, with the comment "Only the request info executor surfaces approved responses. The agent's unapproved response remains available through the request_info event." 4f0cc5b (#8589, breaking, ADR 0043 proposed): declarative MCP approvals "contain header names and an HMAC over the request ID and canonical evaluated headers ... A changed or unverifiable header set produces a fresh approval for the pinned operation before dispatch."

What it changes. Three of this week's changes are about the count. A child agent's approval cannot be forwarded to the human by the parent any more; it fails, and you must model delayed approval as a workflow. A session store that persisted [APPROVAL_PENDING] placeholders will, after upgrade, treat those approvals as completed, so migrate the store before you upgrade. And an unapproved draft note no longer leaves a sequential workflow as output, which is right, and which will break any consumer that read drafts from outputs. Read the 24 Sept blog line again, "Recovery does not imply exactly-once execution of external effects.", and make every write idempotent before you turn on checkpoint-and-recover hosting.

  • .NET bf93c53 (#8641, breaking): "A response takes effect only when its matching request was recorded in the current AgentSession by the framework. Request content supplied or replayed by the caller does not establish that binding." ec7114f (#8403): "fix: a bug where invoke function tool could bypass approval" in InvokeFunctionToolExecutor.cs. If you run .NET workflows with function-invocation executors, an approval bypass existed before this commit.
  • .NET 30b9b8e (#8692): stored approval state is consumed only when the run succeeds; "a failed run leaves them intact and the caller can supply the same approval response again." Good for retries; it also means one approval can authorise two attempts, so your idempotency key must cover the second.
  • 2055e66 (#8640): unknown function calls can be made fatal, "configured true raises before any call executes". The spec still warns "a synchronous tool body already executing in a worker thread cannot be interrupted and may complete its side effects."
  • 87d4d0a (#8542): opt-in session-scoped file access that "fails closed (ValueError) when neither a scope nor a session id is available." The default is still a shared store.

1.5 Google ADK main: another agent's confirmation, and a client secret in the session docs, source read, not executed

The problem: two agents share a session, and one resolves the other's approval, or reads the other's secrets.

No release in window (2.9.2, 18 Sept); about 120 Copybara commits on main. e19ce05 (23 Sept) in flows/llm_flows/tools/_confirmation.py: "If this confirmation request was authored by another agent, skip it to let that agent's processor handle it." The match is on event.author != agent.name, so two sub-agents with the same name still resolve each other's confirmations. 9b9aac0 (23 Sept) keeps the OAuth2 client secret out of session state: "Only new writes are affected. A session already persisted by a durable backend such as DatabaseSessionService or SqliteSessionService still holds the secret in clear text, so rotate any OAuth2 client secret." and "The end user's own tokens are still stored in clear text." b562ef4 (24 Sept) keeps credential-request events out of the compaction prompt, "including the credential-request pair that carries the end user's token, PKCE verifier and auth code." d42a3be (24 Sept): parallel tool calls that update a state list now keep the latest write, but only for list and dict keys; scalar keys are still last-in-model-order.

What it changes. If you persisted ADK sessions to a database before this lands, the OAuth2 client secret for your FHIR server is in that table now, and a compaction prompt sent to the model may have carried an end user's token. Rotate the secret, and search summarised sessions for credential events. Give every sub-agent a unique name before you rely on the confirmation fix.

  • a519b6f (21 Sept): server-supplied MCP tool descriptions are fenced before reaching the model, "MCP tools only; A2A agent cards and OpenAPI toolsets are follow-ups." It "causes a one-time Gemini context cache miss."
  • f425287 (23 Sept): signed URIs and HTTP options are redacted from errors and logs.

1.6 pydantic-ai 2.47.0 to 2.50.0: the PHI-on-span flag follows the capability that instruments the run docs, source read, not executed

The problem: your tool decides whether to put a patient id on a span by asking the run context, and the run context answers for a different instrumentation than the one writing the spans.

935fa97 (#8706, 23 Sept, in 2.49.0): "Make RunContext.tracer, trace_include_content and instrumentation_version follow an explicit Instrumentation capability". Comment in agent/__init__.py: "An explicit Instrumentation capability (agent- or call-level) replaces the one injected from instrumentation_settings ... so for_run hooks and metadata factories are shown the settings of the one that will actually instrument the run." Before this, with Agent.instrument_all(include_content=True) globally and Instrumentation(include_content=False) on the agent, ctx.trace_include_content was True and ctx.tracer pointed at the global provider, so a tool that honoured the flag wrote the patient id to a span on a different tracer provider than the run's own. 123bba5 (#8595, 2.47.0): passing a dict as the user prompt now raises; the comment says a dict "is walked as its keys, silently sending them to the model as the prompt", and that the same check "also runs when Pydantic deserializes message history, where a ValueError becomes a ValidationError." 604c06f (#8723, 2.50.0): RunContext.in_durable_context, "False inside a Temporal activity or DBOS step ... A Prefect task inherits its flow's context, so it is True there."

What it changes. Two records again: below 2.49.0 the run's spans obeyed the redaction you set on the agent and your own audit spans obeyed the global one, on separate providers. If you export both to one collector, PHI attributes from tools may be in it. The prompt change is a break you want: a FHIR resource passed as the prompt used to send its field names and nothing else. It also means stored message histories with such parts will no longer load; check before upgrading a replay store. The durable flag is a dedupe guard for audit writes, and it means different things on Temporal and Prefect.

1.7 FastMCP 4.0.6 to 4.0.9: a visibility check added, reworked and reverted in five hours docs, changelog and source, not executed

The problem: a completion endpoint suggests values for a resource template your caller is not allowed to list.

4.0.6 (0959c27, #5240): "A completion/complete request for a prompt or template hidden by disable(), component auth, or AuthMiddleware still ran the server's completion handler and returned its suggestions." 4.0.7 (94c5a21, #5244) reworked the check through typed list hooks. 4.0.8 (94c346f, #5250) reverted both, with the changelog line "Completion goes back to its 4.0.5 behavior ... in 4.0.7 that could let a response cache serve hidden prompts to other clients." All three shipped on 23 September; 4.0.9 followed on the 24th. Also in 4.0.6: 87b5c74 (#5208), json_schema_to_type "returned as soon as a string schema had a format, so minLength, maxLength and pattern were dropped for every format", which affects the client-side elicitation and structured-output types; 3e20bba (#5185) moves the Google provider's token from ?access_token= in the URL to an Authorization header. 4.0.8: 9949d9a (#5243), OAuthProxy now revokes "the token the authorization server actually issued, not the FastMCP-issued JWT wrapper".

What it changes. A resource template like patient://{mrn} with a completion handler can suggest identifiers to a caller who cannot list the template, on every FastMCP version except 4.0.6 and 4.0.7, and 4.0.7 could serve another client's hidden listing from a cache. Do not pin 4.0.7. Authorise inside the completion handler, or do not register completions on PHI templates at all. If you revoked sessions through OAuthProxy before 4.0.8, the upstream refresh token was not revoked; check the authorisation server.

1.8 OpenAI: a retry that sent an empty body and reported success docs, source read, not executed

The problem: an upload of a clinical document fails once, is retried, succeeds, and the file on the other side is empty.

openai 3.19.0 (6e0c2be, #3771, 22 Sept): "A one-shot iterable or non-seekable multipart file part may then send an empty body on the retry; if that retry succeeds, the SDK reports success without resending the original payload." The client now retries only when the body can be replayed; a non-seekable stream gets zero automatic retries and raises. 3.17.0 (69a2c1d, #3913): AgentSessionEnvironmentResetEvent, "Emitted after a hosted sandbox is replaced. Conversation history survives; changes to the previous sandbox's files and processes do not." 6332577 (#3909): admin.organization.external_storage with a customer-managed retention status; what the stored data covers is not documented in the SDK. On openai-agents main, unreleased: 40956e0 (#5112) redacts the default tool error text to "An error occurred while running the tool. Please try again.", with "Provide a custom failure_error_function to return application-approved error details."; bd91ae6 (#5119) moves the RunState schema to 1.18 and binds restored MCP calls to their server, "Start a new run to execute an MCP call if an older snapshot lacks these bindings."

What it changes. A document you uploaded through the Python SDK below 3.19.0, from a stream rather than a path, after a transient 5xx, may exist on the server as an empty file with a success in your log. If you batch-uploaded records for extraction, compare byte counts. The environment reset event is the sandbox version of this issue's theme: the transcript says the draft was staged, the sandbox that held it is gone. And when the agents SDK ships schema 1.18, every persisted approval of an MCP call from before the upgrade cannot be executed; plan a drain.

1.9 Anthropic 1.8.0: a pinned MCP tool list, a hot-swapped tool, and a path expansion no permission stops docs, source read, not executed

The problem: the set of tools the model can call changes under a session, and the record of which set was in force lives in a block you might drop.

anthropic 1.8.0 (22 Sept, b5cc700): betas inline-tools-2026-09-15 and mcp-client-2026-09-15. BetaMCPToolset.tools: "The server's tool listing, pinned: when present, the server is not asked for its tools before sampling and exactly these entries ... are the toolset's tools." A response returns an mcp_tool_listing block that pins the list when sent back. BetaCompactionBlock.tool_changes carries "the tool_addition and tool_removal blocks that take the request's tools to the tool set in effect at the end of the range ... Send the block back unchanged." 06d0a6b (#874): add_tools() on the tool runner, "A function tool is run straight away, in place of any tool of the same name, even for a call already in the message being handled." Platform notes: cache diagnostics GA on 23 Sept, "Responses from POST /v1/messages now always include the diagnostics field"; Opus 5.5 returns 400 for tool_choice types any and tool. claude-agent-sdk 0.2.158 (f7547d7, #1269): verbatim_prompts, default False. Commit body: "Claude Code expands an @/absolute/path token anywhere in a user message into the contents of that file. This happens before the model runs, outside the working directory, and without a tool call, so it is not stopped by tools=[], allowed_tools, or disallowed_tools=["Read"]."

What it changes. Pinning the MCP tool list is the closest thing this week to content-bound approval for tools: a server cannot change a description or schema mid-session without you seeing a different listing block. Store the block with the session. Two hazards. Dropping tool_changes from a compaction block silently reverts the tool set, so the transcript's tool set and the API's disagree from that turn on. And add_tools() replaces a same-named tool for a call the model has already emitted, so swapping a dry-run write_note for the real one mid-turn commits the call you were previewing. For any app built on the agent SDK that inlines patient-supplied text into a prompt, set verbatim_prompts=True or a pasted @/etc/passwd is read with no tool call and no permission.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. arXiv was read from the past-week listing pages for twelve categories (the export API returned 406 through the sandbox proxy) and medRxiv from its details API, so listing dates are the announcement day and may be the cross-list day for papers that appear in several categories.

Loopjacking: hijacking human-in-the-loop approval and Agent Approval Laundering: transitive effects beyond the approved invocation
arXiv 2609.21081 · submitted 17 Sept, listed 21 Sept · Adithyan Arun Kumar; arXiv 2609.28586 · submitted 23 Sept, listed 25 Sept · Zhang, Xia, Wu and others, Chinese Academy of Sciences

Two papers on the same seam this issue is about. Loopjacking studies a human approving operation A and the system executing B, through misrepresentation at approval time or mutation of workflow state after it; substitution was reproduced "in seven tested Agno AgentOS releases ending at 3.0.9 and in 12 tested versions of a conditional in-memory LangGraph Agent Server composition", while "OpenAI Agents SDK 0.22.0 and 0.22.2 provide a negative control: serialized continuation preserves exact per-call binding and rejects mutated B." Approval Laundering looks at what the approval record omits: the transitive effects an approved invocation triggers. "Across 111 fixed approval-object/trace pairs, residual records fall from 40 under explicit fields to 17 with command semantics and 13 with decision-time metadata"; binding predicted effects "cuts residual effects from 10 to 3." Implementation note: hash the complete canonical action payload at approval time and compare it byte for byte at execution, and record the predicted downstream effects (linked orders, notifications) in the audit entry beside the top-level call. Section 1.1 is the case where the payload matched and the count did not.

Synthetic Hospital: an open, verifiable, physician-validated longitudinal EHR benchmark
arXiv 2609.30027 · submitted 24 Sept, listed 25 Sept · Park, Chen, Dettmers

A fully synthetic longitudinal EHR, "1,268 longitudinal patients and 5,602 encounters", every finding coded to ICD-10-CM, SNOMED CT or LOINC with "a complete provenance chain back to its source", served through "a simulated hospital record system that mirrors real EHR infrastructure (standard interoperability APIs, role-based access and function-calling interface)". Physicians told its records from real charts "at near-chance rates (53%)". "The best model reconstructs a patient's longitudinal problem list with a severity-weighted F1 of 0.73, level with the mean of seven physicians on a matched subset but well below the best of them (0.89), and misses roughly half of clinically relevant findings when summarizing a chart." Implementation note: this is a PHI-free harness with a function-calling interface, which is what a CI job for a tool-calling EHR agent needs; gate chart summarisation on recall of findings, not on fluency.

Silent failures in agent-tool interaction: an audit of ToolUniverse
arXiv 2609.26836 · submitted 21 Sept, listed 24 Sept · Gopalan, Singh, Narayanan

Audits 15 biomedical tools for calls that appear to succeed and return incomplete or missing data with no signal to the agent, across seven failure loci. "We observed 91 failures ... most frequent of them being missing data or fields and inconsistencies in search, filtering or ranking criteria. Most of the 91 failures occurred in API layer (51) or wrapper layer (25)." Implementation note: check every tool response for expected fields, plausible result counts and that filters were applied before the agent may use it, and record a failed check as provenance on the answer. Section 1.2 is the write-side version: a success the tool never reported.

Mind the gap: emergent clinical risk at the interface of two individually safe AI systems in a multilingual ambient scribe
medRxiv 10.64898/2026.09.22.26363642 · posted 23 Sept · Bergman, Liu, Austin, Sanghera, Heidi Health

Two arms on a frozen synthetic corpus over 77 languages and five complexity levels: script to note (n=385) and speech transcript to note (n=2,302), discrepancies rated by three LLM raters. "Intrinsic note generation had a 3.4% serious-error rate"; "End-to-end serious errors rose steeply with complexity (L1 1% to L4/L5 24%) and language scarcity (high 7%, medium 10%, low 15%; OR 1.54 per tier...)"; "87% were ASR-derived and 7% note-originated; amplification exceeded correction threefold"; "Repeated generation showed moderate reproducibility (Fleiss kappa 0.42)". Vendor study of its own product*. Implementation note: evaluate the note the clinician sees end to end, stratified by language and complexity, and store the recognition transcript as provenance for every assertion in the note.

Language models reflect clinical evidence but fail to adapt it to patients
medRxiv 10.64898/2026.09.14.26363047 · posted 19 Sept · He, Joseph, Safari and others, Mass General Brigham emergency medicine

The NUMBERS benchmark, 16 model configurations on 1,300 evidence-linked questions, plus a direct-action experiment of 50 rules and 7,500 calls. "Models selected an incorrect action despite stating a cutoff that implied the correct action in 413 of 3,750 recall-arm calls (11.01%...)"; "Supplying the complete rule raised action accuracy from 85.63% to 99.41%"; supplying inputs and requesting calculation "raised patient-level near-target answers from 29.7% to 78.8%". Implementation note: never let the agent recall a threshold; inject the full rule and the patient inputs from a rules store, run the arithmetic as a tool, and check the chosen action against the model's own stated cutoff.

CliffCompaction: cost-efficient compaction for long-horizon coding agents (with DTOC: dynamic tool output compression)
arXiv 2609.26779 · submitted 22 Sept, listed 23 Sept · Nguyen, Cho, Chen, Dettmers; arXiv 2609.26121 · submitted 6 Aug, listed 23 Sept · Chaturvedi, Bhattacharya, Gopalkrishnan

CliffCompaction keeps compacted context faithful "by only truncating or dropping content, never rephrasing or rewriting it. We never compact a compaction—each pass operates only on original content", and "reduces cost by up to 50% under a bounded context while maintaining or improving performance on Terminal-Bench". DTOC stores full tool outputs externally behind restorable placeholders; "Ablation results show reversibility is critical: disable-only compression variants degraded performance." Both are coding-agent results. Implementation note: never let an LLM rewrite patient constraints (allergies, consent, payer rules) in the memory layer; truncate or drop, recompact from the original transcript, and keep dropped tool outputs retrievable by reference. Issue 02's constraint-loss result now has a design pattern beside it.

LLMs anchor on chief complaint and fail to integrate evidence in sequential clinical triage
arXiv 2609.22904 · submitted 19 Sept, listed 22 Sept, v2 24 Sept · Srirag, Zhao, Kumar and others

ESI level predicted from a growing prefix of a nurse-patient conversation at five checkpoints, six models, 425 simulated and 50 physician-authored conversations. "Every model... degrades from moderate-to-substantial agreement on completed records to fair-to-moderate agreement at every sequential checkpoint"; "Three expert clinicians on the same conversations reach a QWK of 0.887-0.929, while the best model reaches 0.295"; "models agree with each other more than with the ground truth, so ensembling worsens the failure." Implementation note: evaluate any incremental decision (triage, intake, prior-auth intake) on growing prefixes, force a fresh assessment when new evidence arrives, and do not expect voting across models to fix an anchoring failure they share.

A living benchmark for information retrieval from electronic health records (BRIE)
arXiv 2609.30205 · submitted 24 Sept, listed 25 Sept · Cahoon, Stanwyck, Somani and others, with Shah and Alsentzer

Question-answer pairs generated automatically from longitudinal notes by a generator 19 clinicians validated, so the set can be refreshed against leakage and carry multiple valid answers. No headline numbers in the abstract: "Across nine LLMs and five inference strategies, state-of-the-art systems frequently omit clinically important information, particularly for questions requiring synthesis across multiple documents and encounters." Implementation note: make omission on multi-encounter questions the primary metric for chart Q&A, and plan for a refreshable evaluation set rather than a frozen one.

Also read: an ICON-Bench study of 19 LLM judges for informed-consent communication (medRxiv 10.64898/2026.09.16.26363176, posted 22 Sept), "strong clinician agreement for safety screening and factual verification (Spearman ρ > 0.80) but weaker agreement for communication quality (ρ < 0.60). Safety-specialized guard models underperformed general-purpose models."; the CIRCA clinical-intent benchmark (2609.29479), where models label order type well "(85 to 91%) but get all four closed fields right only 18 to 35% of the time", request intent (plan against order) being the FHIR field they miss; and a decomposition of coding style (2609.24877) where two coding teams "agree on only 73% of codes". MedHELM and HealthBench published no dated leaderboard update in window.

The problem: your approval is a dict, and "aprove" is a rejection.

Synthetic data only. The "record" in 5.1 is deepagents' in-state virtual filesystem and in 5.2 an in-memory list; nothing writes to a FHIR server.

LinkedIn post candidate

The pharmacist approved two writes. One of them ran zero times. Nobody was told.

deepagents 0.7.16 shipped on Sunday with a sensible fix: if one model response carries two changes to the same file, the second is refused. I put the write tool behind human-in-the-loop, had a scripted model propose two care-plan writes, approved both, and counted. On 0.7.15: two approvals, two writes, the record holds Plan B. On 0.7.16: two approvals, one write, the record holds Plan A. The check runs after the approval middleware, so the reviewer signs a call the framework has already decided not to run. The model said "Both plans written." on both versions. No API key.

The same week llama-index-core 0.14.25 stopped executing a failing single-argument tool twice. Below that version, a tool that commits to the record and then raises was called again with keyword arguments: one call, one error, two rows. And Microsoft's Agent Framework team wrote, about checkpoint-and-recover hosting, "Recovery does not imply exactly-once execution of external effects."

Last week's question was what a yes is bound to. This week's is how many times it runs. Zero and two are both audit gaps, and both were reachable from a clean install. Reconcile approvals against tool results by call id, and make every write idempotent, because nothing between the yes and the record will do it for you. Code and diagram in the issue.
