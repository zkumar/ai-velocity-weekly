The approval policy named the write that needed a clinician and the read that did not. The server had a third tool, and for a tool nobody listed the answer was run

Issue 10 · week ending 6 November 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

An approval policy is a list, and a list has an outside. Somebody wrote always_require_approval: place_order and never_require_approval: read_chart for the pharmacy server, reviewed it, and shipped it. Then the team that owns the server added discontinue_order. The policy does not name it. What does the framework do with a write the policy has never heard of? I ran it on Microsoft Agent Framework 1.23.0 and on 1.24.0, uploaded late on 30 October, with a scripted model, a local MCP server and a file standing in for the chart. On both versions the unlisted write ran: no approval request, one row in the record, and a closing sentence from the model that reads exactly like the sentence for an approved write. 1.24.0 adds one FutureWarning at construction and one new key, "default": "always_require", which closes it. The same policy file on 1.23.0 is accepted without a word, the key is never read, and the write runs.

That is the week's shape. Three projects shipped an explicit setting for a case that until now resolved silently, a fourth fixed one outright, and in every one the silent resolution had been "go". pydantic-ai 2.66.0 makes a toolset's requires_approval=True cover prebuilt Tool instances; on 2.65.0 an instance inside an approval-required toolset simply ran, and I ran that too. The Claude Agent SDK gains on_failure="block" for hook callbacks, because until Monday a PreToolUse guard that raised an exception was counted as no decision and the tool ran. LangGraph 1.2.20 gives each interrupt() in a node its own id and adds an opt-in strict resume that refuses an answer to a question nobody is waiting on; without the key a stale answer is still accepted. And OpenAI's Python SDK grew a session setting, review: "auto_review", whose docstring reads "Deny manual approval fallbacks." Every one of those settings is opt-in, and the old behaviour is still the default.

Three checks against your own system. For every approval policy written as a list, find out what the framework does with a name that is on no list, and test it with a tool you add for the purpose. For every guard written as a callback, make it raise and watch whether the action runs. And for every setting you roll out to close one of these, confirm the installed version reads it, because this week's fix is a dictionary key and last week's package ignores unknown keys.

1.1 Agent Framework 1.24.0: the tool nobody listed executed

The problem: your approval policy for an MCP server is two lists of tool names, and the server's tool list is not yours to freeze.

agent-framework-core 1.24.0 on 30 October at 21:38 UTC, after Issue 09's sweep had found the changelog's Unreleased section empty; 1.23.0 is from 22 October. The changelog line: "Add an explicit default approval mode for local MCP tools and prompts outside the per-tool approval lists, and warn when never_require_approval leaves the default implicit while preserving the existing fallback", pull request #9828. In agent_framework/_mcp.py, read from both wheels, the per-tool resolver on 1.23.0 returned "always_require" for a name in always_require_approval, "never_require" for a name in never_require_approval, and None for anything else; FunctionTool.__init__ in _tools.py then reads self.approval_mode = approval_mode or "never_require". So the fall-through was "run", and it was two files away from the place the policy was written. 1.24.0 adds a third key to the MCPSpecificApproval TypedDict, default, routes the fall-through to a new _mcp_approval_default(), raises ValueError for any value other than the two modes, and warns once at construction when never_require_approval is set and default is not. The docstring now states the order: "a name in always_require_approval requires approval, otherwise a name in never_require_approval does not, otherwise default applies. Without default, a tool or prompt named in neither list does not require approval, which is the framework default."

class ScriptedChat(FunctionInvocationLayer, BaseChatClient):       # no model, no key
    async def _inner_get_response(self, *, messages, stream, options, **kwargs):
        results = [c for m in messages for c in m.contents if c.type == "function_result"]
        if not results:                                           # ask for the write nobody listed
            call = Content.from_function_call(call_id="call-1", name="discontinue_order",
                                              arguments=json.dumps({"patient_id": "pt-123", "order_id": "order-1"}))
            return ChatResponse(messages=[Message(role="assistant", contents=[call])])
        return ChatResponse(messages=[Message(role="assistant", contents=[f"Done. {results[-1].result}"])])

POLICY = {"always_require_approval": ["place_order"], "never_require_approval": ["read_chart"],
          "default": "always_require"}                            # the key 1.24.0 adds
pharmacy = MCPStdioTool(name="pharmacy", command=sys.executable, args=["pharmacy_server.py"],
                        approval_mode=POLICY)
reply = await Agent(client=ScriptedChat(), tools=pharmacy).run("Stop the apixaban for pt-123.")
print(len(reply.user_input_requests), len(rows(record)))          # approval requests, rows written

Observed, 1.23.0 then 1.24.0, five cases, each run twice from clean environments with byte-identical output. Lists only, the model calls the unlisted write: 0 approval requests and 1 row on both versions; 0 warnings on 1.23.0, 1 FutureWarning on 1.24.0. Lists plus "default": "always_require": on 1.23.0 the policy is accepted, the tool still resolves to never_require, 0 approval requests, 1 row, 0 warnings; on 1.24.0 it resolves to always_require, 1 approval request, 0 rows, and after the clinician's approval exactly 1 row. Control, the model calls place_order: 1 approval request and 0 rows on both. The always list supplied as one comma-joined string, "place_order,discontinue_order": 1 approval request and 0 rows on 1.23.0; 0 approval requests and 1 row on 1.24.0, where place_order itself also resolves to never_require. Wherever the write ran, the model's closing text was the same: Done. {"result": "ORDER DISCONTINUED order-1 for pt-123"}. Script test_af_mcp_unlisted_tool.py; the full output is in the lab README.

The third case needs a sentence of its own, because it runs the opposite way to the release note. On 1.23.0 the resolver tested name in always_require. When always_require is a list that is membership; when it is a string, which is what an environment variable or a YAML scalar gives you, it is a substring test, and "discontinue_order" in "place_order,discontinue_order" is true. The misconfigured policy worked by accident. 1.24.0's _mcp_approval_names() turns a bare string into a one-element tuple, on purpose ("A name list given as a single string is treated as one name"), the one name matches no tool, and every write behind that server falls through to the default. The upgrade that adds the gate for the unlisted tool removes it for a team whose list was a string.

What it changes. If you run local MCP tools through Agent Framework with a per-tool approval dict, every tool the server has added since you wrote the dict has been running without a question, and nothing in a reply or a log line distinguishes those writes from approved ones. Set "default": "always_require" and list the reads, so that the list is of what may skip the person and the outside of the list is the gate. Then check three things the release does not check for you. The key is honoured only from 1.24.0, so pin the floor in the same change that adds the key, and assert at start-up that every function the tool exposes resolved to the mode you expect (tool.functions carries approval_mode per tool, and the lab prints it). A name list must be a list; on 1.24.0 a comma-joined string protects nothing. And hosted MCP tools "do not read default", so a policy moved from a local tool to a hosted one loses the key again. Turn FutureWarning into an error in CI for this package, because it is the only signal on the path where behaviour did not change.

1.3 LangGraph 1.2.20 and SDK 0.4.14: an answer to a question nobody is waiting on docs, release pages, pull requests and wheel diff, not executed

The problem: a node asks the pharmacist two questions, and the approval screen posts the answer to the first one twice.

langgraph 1.2.20 on 5 November at 02:20 UTC; langgraph-sdk 0.4.14 on 6 November at 03:03. #9589: in langgraph/types.py a new _interrupt_id(ns, answered) hashes the task's checkpoint namespace together with the number of answers the task already holds, and interrupt() uses it. Before, every interrupt() inside one task shared one id, the hash of the namespace alone; the first question keeps that id, so a single-question node is unchanged, and the second and later questions get new ones. The lookup in pregel/_algo.py keeps a fallback with the comment "Older versions gave all of a task's interrupts the first id." #9574 adds a private configurable key, __pregel_strict_resume, and langgraph.errors.UnknownInterruptError with a reason of not_pending, empty_map or ambiguous and a pending_ids list; with the key set, a resume map naming an id that is not pending raises "Unknown or already-consumed interrupt" and, in the class docstring's words, "The error is raised before anything is written, so they can still be answered." #9599 exposes it on the SDK as strict_resume on runs.create, stream and wait: "Refuse a resume that answers an interrupt that isn't waiting, instead of ignoring the answer".

What it changes. Without the key nothing changes, and that is the point to carry away: by default a duplicated or late approval is still accepted or ignored without an error, and because of the first-id fallback an answer addressed to the old shared id still fills the task's next open question. If your audit table keys approvals by interrupt id, the second question in a node has a different id from this release on, so a join written last month matches one row where it used to match two. Turn strict resume on wherever an approval can arrive twice, which is anywhere there is a retrying client, and treat UnknownInterruptError as a logged event with its pending_ids rather than as a failure to hide.

  • langgraph 1.2.19 (30 Oct, 22:23 UTC), #9486: a node's trace_policy now applies to tracers only. _split_handlers() sends the reduced payload to BaseTracer handlers and the node's real input and output to every other callback handler; the TracePolicy docstring says it is "Not intended to redact secrets." A plain callback handler you wrote as an audit logger receives full payloads again, and a tracer does not. #9406: a tool paused on interrupt() is no longer emitted as a tool-error on the tools stream. docs
  • langgraph-sdk 0.4.12 (3 Nov), #9554: when a stream closed cleanly without an end or error event, the caller "got a cut answer and no error"; the client now fetches the run, and if it is still pending or running reconnects with Last-Event-ID. 0.4.11 warns that reconnecting without an event id means "events sent while disconnected are not replayed. Only runs created with stream_resumable=True send the event IDs a reconnect resumes from." 0.4.12 also reverses the priority docstring to "-5 runs first and 5 runs last". docs
  • langgraph-checkpoint-sqlite 3.1.3 (30 Oct) has no source change; it raises the checkpoint floor to 4.3.1, which carries last week's NUL-byte namespace fix. docs

1.4 Claude Agent SDK 0.2.177 and Claude Code 2.1.316 to 2.1.318: the guard that crashed, and the transcript that was not saved docs, changelogs, pull request and wheel diff, not executed

The problem: your PreToolUse hook checks an order against the chart, and on the day the chart service times out the hook raises.

claude-agent-sdk 0.2.177 on 3 November at 02:15 UTC, with Claude Code 2.1.317 (2 Nov, 23:57). The pull request, #1460, states the old behaviour: "a Python hook callback that failed was treated as no decision, so a PreToolUse guard that crashed let the tool run, and Python apps had no way to change that." HookMatcher in claude_agent_sdk/types.py gains on_failure: Literal["continue", "block"] | None, and the comment beside it defines failure widely: with "block", "a callback that raises, returns None (a path with no return), or returns a value the CLI rejects, such as permissionDecision "Deny", blocks the action, so a callback with no opinion must return {}." Stop, SubagentStop, TaskCompleted and TeammateIdle ignore the option. Connecting with "block" to a CLI that does not report hook_on_failure_supported raises CLIConnectionError, so the setting cannot be silently ignored by an old runtime, which is the property section 1.1's key lacks. Unset, a failure still counts as no decision. Whether the bundled CLI reports the capability was not checked against the binary. unverified

Claude Code's own changelog for the window is mostly about approvals and records that were wrong at the edges. 2.1.317: "Fixed claude -p exiting 0 when a full disk or quota lost its transcript or ~/.claude.json writes; it now prints an error and, in text and json output, exits 1", with a session_writes_lost system message in the TypeScript SDK; "Fixed claude -p run inside a cloud or self-hosted runner session sharing that session's ID: it wrote into the session's transcript, and a restart could resume the wrong conversation". 2.1.318 (3 Nov): "Fixed permission prompts being answered by keys typed just after sending a message, or before a slow prompt appeared"; "Fixed a shell command approved after a self-hosted runner or cloud session restart running in the session's start folder, not the folder it was asked in; if that folder can't be entered, it is not run"; "Fixed idle compaction replacing a conversation with a reply that was not a summary". 2.1.316 (31 Oct): "Fixed cloud sessions and cloud scheduled tasks not being marked as failed when auto mode stopped a turn because the server returned no safety verdict"; server-managed settings for Team and Enterprise logins "now apply without an approval prompt, and a stored copy that doesn't verify is refused".

What it changes. Every hook-based guard written before this week fails open on an exception, and still does unless you set on_failure="block" on its matcher. Set it on every matcher in front of a write, make callbacks with no opinion return {} rather than fall off the end, and spell the decision in lower case, because a capitalised "Deny" is a rejected value and therefore, under the new setting, a block for the wrong reason. Separately: an exit code of 0 from a headless run before 2.1.317 did not mean a transcript exists, and an approval given before a session restart could run its command somewhere else. If an audit relies on SDK transcripts, check their presence per run rather than inferring it from success.

1.5 openai-python 3.42.0 to 3.46.0 and anthropic 2.4.0 to 2.6.0: a review mode without a person, and a conversation the server keeps docs, changelogs and wheel diffs, not executed

The problem: the approval step in your design is a person, and the SDK now has a parameter for who else it can be.

openai 3.42.0 on 31 October at 00:27 UTC, #4217 "add agent session review and tool settings". types/beta/agents/session_create_params.py adds review: Literal["none", "auto_review"], documented as "auto_review - Review eligible actions automatically. Deny manual approval fallbacks."; on update, "Default action review for new root turns. Existing turns and their subagents keep their review mode." The same change lets sessions.update(agent={"tools": ...}) replace a running session's tools: "Functions and MCP servers change on the next model call. Built-in tools change by the next turn." #4209 adds compaction settings whose async option defaults to true: "Background compaction may increase token usage." Which actions are "eligible", and what does the reviewing, is not stated in the SDK, the pull request or the API changelog, which has no entry for any of it. unverified Also in the window: 3.42.0 pins a refreshed callable API key to its own request (#4216); 3.45.0 adds 12-hour cache lifetimes and cache-write usage fields; 3.46.0 adds Australia, India and Japan residency endpoints and the gpt-6-rosalind identifier.

Anthropic's message threads beta (release note 2 November, header message-threads-2026-08-12) moves conversation state the other way from last week's theme: "The API keeps the conversation on the server, so each later request sends only the new messages." The documentation is direct about what that is not: "A thread is best-effort."; "There is no API to list, read, or delete a thread."; "No response, to a create or a continue request, says whether the API stored that turn."; "Message threads are not ZDR eligible."; and an organisation with HIPAA readiness enabled receives a 400. anthropic 2.5.0 (4 Nov) adds the typed errors, ThreadAlreadyContinuedError, ThreadFingerprintMismatchError and others, and a separate fix: "keep the memory tool from renaming or deleting the /memories directory", where on 2.4.0 a delete of /memories/ passed path validation and reached shutil.rmtree on the root. 2.6.0 (5 Nov): "stop recording sampling parameters on OpenTelemetry spans", so gen_ai.request.temperature, top_p and top_k are no longer span attributes. 2.4.0 (2 Nov) adds tool_use_limit_reached_error and compaction_limit_reached_error session error types for Managed Agents.

What it changes. One enum value takes the person out of the approval path for a whole session, and the tool surface of a session can change between two model calls. Neither is wrong; both have to be in your record, written by your code at the moment you set them, because the session will not tell an auditor later which turns ran under which review mode or which tools existed when a call was made. For threads the vendor has said it for me: "Your application stays the source of truth for the conversation. Keep your own copy of every message, and build the replay path from the start." A healthcare organisation with HIPAA readiness on cannot use the feature at all, which settles the question for PHI and leaves it open for everything adjacent. And if your validation evidence includes the sampling parameters a clinical summary was generated with, the Anthropic span no longer carries them from 2.6.0; log them yourself.

1.6 Semantic Kernel 1.47.0, fastmcp 4.1.5, google-genai 3.0.0, and five security fixes with no advisory docs, release pages, pull requests and wheel diffs, not executed

The problem: your dependency scanner is the control that tells you a framework fixed something that mattered.

semantic-kernel 1.47.0 on 5 November at 10:58 UTC. #14668 and #14693: the OpenAPI plugin's allowed_base_urls check was a lower-cased string prefix match, so, in the pull request's words, "/api/../admin and /api/%2e%2e/admin matched an /api allowlist while httpx would request /admin"; a new _normalize_path() removes dot segments on the raw and percent-decoded forms and matching becomes case-sensitive. #14607: a ChatHistoryReducer attached to a ChatCompletionAgent was not applied, and the full history went to the model; get_response, invoke and invoke_stream now call await thread.reduce() first. #14658: truncation could keep a function result while cutting the call it answered; the cut now moves back until "a result in the retained tail cannot remain while its call starts before the cut". The release requires Python 3.11.

fastmcp 4.1.5 (1 Nov), #6130, labelled Security in the release notes: a mounted resource template dropped its list-query parameters, so a comma-joined {?param} list was screened by the parent's ResourceSecurity as one string; "The reported bypass reproduces on main and is blocked here across nested and namespaced mounts". 4.2.0a3 (3 Nov), #5727: LoggingMiddleware(methods=[]) logged everything, and an empty list now logs nothing. google-genai 3.0.0 (6 Nov, 02:29 UTC) is a major version about transport: "Default Gemini Developer API version is now v1 (was v1beta)", and "Default HTTP client is now httpx2 (was httpx)", which "uses the OS certificate trust store ... instead of certifi" when no certificate variables are set; nothing in the diff touches automatic function calling.

What it changes. Count them: Agent Framework's unpickler (#9825) and its .NET Mem0 scope check (#9827), Semantic Kernel's allowlist traversal (#14668) and its .NET address binding (#14719), fastmcp's screening bypass (#6130). Five fixes with a security consequence, zero advisories. OSV, queried on 6 November for 65 package names across PyPI, npm and NuGet, returned no record published in the window, and that includes the ten pydantic-ai published on GitHub two days earlier. A scanner will tell you about none of this until it catches up, and about five of them never. The changelog is the control. On Semantic Kernel, the reducer fix changes what the model sees after an upgrade, so re-run evaluations, and remember that a reduced thread is no longer the full record. On google-genai, a hospital TLS-inspecting proxy that worked through certifi overrides will behave differently, and except httpx.TimeoutException stops catching.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Dates are arXiv v1 submission dates and medRxiv posting dates read from the two APIs. 78 abstracts were read this week from 524 arXiv and 433 medRxiv records in the window; no full text was read, because the arXiv pages rate-limited every fetch, so every number below is the abstract's and the authors' own.

When neither side confirms: destructive tool approval across MCP servers and hosts
arXiv 2611.02527 · 2 Nov · Yao, Yang, Wang and colleagues

The paper to read beside section 1.1, because it measures the same seam across the ecosystem rather than in one framework. MCP splits approval between the server, which can annotate a tool or elicit a confirmation, and the host, which can prompt. The authors read the source of a 1,000-repository sample of the official registry and of 41 open-source hosts and agent SDKs. By their estimate 90% of destructive tools (95% CI 82 to 95) have no server-side confirmation, and 32 of the 41 hosts and SDKs have no approval step by default. Pairing the two halves, "60.7% of pairs have no enforced human approval by default", and in a live test four of five low-cost models executed an injected deletion in 479 of 960 runs. The counterfactual is the useful part: if hosts prompted for every tool not annotated read-only or non-destructive, the unapproved share would fall to 5.4%, while universal elicitation support on the server side would leave 56.7%. Implementation note: the host-side default decides almost all of it, and the right default is the one section 1.1 ends on. Prompt for every tool not explicitly marked read-only, and do not count on the server to ask.

Accessed, never disclosed: silent access to protected health information by medical artificial intelligence agents
arXiv 2611.02319 · 2 Nov · Lee, Banerjee, Lee

Canaries embedded in synthetic patient records, with every tool invocation linked to whether the canary reached the final answer, so that retrieving an identifier and revealing one are measured separately, on clinical tasks that need no identifiers, across five models, four boundary levels and seven attack frames. Three of the five models called the PHI tools when the task did not need them. Under the strictest policy the remaining access was confined to frames where the user overrode the policy or asserted approval, and a pre-execution gate that applied a task-necessity test nearly eliminated it. The abstract gives no rates. Its conclusion: "Output-only evaluation cannot verify minimum-necessary access". Implementation note: minimum necessary is a property of the tool access log, not of the answer. Put a task-necessity check in front of identifier-returning tools, audit from the log, and treat a user's in-chat "I approve" as untrusted text.

RECEIPT: measuring and repairing the return assumption of LLM agents in web service operations
arXiv 2611.01930 · 1 Nov · Yang, Yang, Zhang and colleagues

What happens when an agent runs a command that asks a question before it acts, and the harness has closed standard input. From 91,469 production tool calls and 89,047 public trajectories the authors build two test sets and run eight harnesses. With input closed, 11.5% of tested invocations returned status 0 without performing the requested action, and seven of the eight harnesses close input when no terminal is attached. Their repair keeps input open, reads from system calls what each process is waiting for, and hands that state to the agent; it reduced false claims of success by 73.5%. The sentence to keep: "Agent builders should report what each tool call did, not only how it ended". Implementation note: exit status 0 is not evidence of effect. Have every write tool return a post-condition verified by read-back, log that, and find out how your harness wires standard input for anything that can prompt.

The harness is the model: agent scaffolding changes a fixed LLM's compliance with banking conduct rules, unevenly across models
arXiv 2611.06116 · 4 Nov · Huyut · pre-registered

Four open-weight models, five harnesses each, 156 pre-registered cases in a simulated retail bank, 3,120 episodes scored deterministically from the executed tool trace. For one model the spread between its best and worst harness was 11.5 percentage points, enough to move it from first to last of the four. A same-model reviewer cut violations from 9.6% to 6.4% without raising over-refusals. And in an analysis the author labels exploratory, 26% of violations came with a customer message denying the action the agent had just executed, which a transcript-only review would have scored as a correct refusal. Banking, not healthcare, and only the abstract was read. Implementation note, in the author's words: "the unit of validation should be the model-harness pair". Version the pair, read the action log rather than the conversation when you test conduct, and re-validate on a framework upgrade as you would on a model change, which section 1 gives you five reasons to do this week.

When do summaries become instructions? Unsupported policy in LLM agents' self-written handoff summaries
arXiv 2611.06545 · 4 Nov · Chu

Synthetic tool-use tasks with a ground-truth permission ledger, so a compaction summary can be checked for permissions the record does not support. Across two open-weight models, 0.1% and 1.3% of readable summaries contained an authorisation nobody gave, and 1.2% and 2.4% a restriction nobody set. Replaying the successor with the false approvals replaced by neutral filler cut unauthorised actions from 24 to 7 of 120 held-out runs, a result the author marks post hoc. Rewording one system-prompt sentence, from a bare statement that some actions need approval to one that says where requirements come from, cut unsupported restrictions from 5.0% to 1.8% of development summaries. Two models, synthetic tasks. Implementation note: a summary must never carry approval state. Keep grants in a ledger outside the context, read it at every gated action, and say in the system prompt where an approval requirement comes from.

Benchmark of THReD: evaluating an LLM agent and its preprocessing tools for turning electronic health records into AI-ready datasets
arXiv 2611.02484 · 2 Nov · Alizadeh, Wu

A data-preparation agent whose proposed steps run only after the user confirms them, evaluated on 141 tasks over synthetic tables calibrated to a regional health information exchange and validated on real records from two chronic-disease cohorts. Over 2,550 episodes with Claude Haiku 5.5 the agent completed 92.7% of tasks on its first answer (95% CI 88.1 to 96.4), abstained on every request for advice, and never proposed an action requested by text planted in the data. Without a profile of the data in its context, completion fell to 58.0%. The audit result is the one to copy: "all 2,176 replays of 128 saved pipelines gave byte-identical files under pinned dependencies". One model, and a preparation agent rather than a point-of-care one. Implementation note: give the agent a compact profile of the data instead of rows, and persist each confirmed step as a replayable pipeline with pinned dependencies, so that the audit artefact is a replay and not a transcript.

Fidelity collapses with table size, not turn count: delivery architecture in a deployed tool-using agent
arXiv 2611.00442 · 30 Oct · Hoang · workshop paper

Two architectures over identical frozen tool payloads in a production agent. One feeds full record sets into the model's context for it to restate; the other keeps the records in session state, has the model translate a follow-up into arguments for a deterministic filter, and delivers the rows over a typed side channel. Across 24 dialogues and 339 scored turns per condition, the side-channel design was fully correct on 92.3% of turns and the in-context design on 45.7%. The in-context design went from near-perfect at ten rows or fewer to 8% or less beyond about 74 rows, with the threshold ordered by model capability. Travel, not medicine, and a small sample. Implementation note: do not have the model re-emit a medication list or a lab panel from context. Keep the rows in session state, have the model produce filter arguments, and render the rows through a typed channel the model cannot alter.
