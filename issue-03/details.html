AI Velocity Weekly

The approval policy was reading arguments the tool never ran, and this week's fix hands the same arguments to the clinician

Issue 03 · week ending 18 September 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Kumar

You have an agent that writes medication orders, and a rule that some of them need a clinician: anything IV, anything above a dose threshold. The rule is code, it runs before the write, and it passes review. Here is the question nobody asks at review: the rule inspects the tool call, but which tool call? The one the model wrote, or the one the tool will run after validation fills in defaults and normalises units?

Those are different objects. A model that omits route produces a call with no route; the tool's signature says route: str = "IV", so the order that reaches the FHIR server is IV. A model that sends 1.5 g produces a call your threshold reads as 1.5; the tool's validator turns it into 1,500 mg. If the approval rule reads the first object and the write uses the second, your audit table says "no clinician needed" for an IV order and a dose three times over the limit, and both statements are true of the call it looked at.

Issue 01 asked where a clinician's signature lives. Issue 02 asked who can answer before the clinician does: a clock, a server-side policy, a token audience. This week the frameworks worked on a narrower and harder question: what exactly a yes is attached to. OpenAI's Agents SDK stopped letting a conditional policy approve arguments that validation will change. LangChain stopped rewriting the model's tool call when a reviewer edits it, so the transcript and the execution now live in different places. Microsoft's Agent Framework made any post-approval change to an argument void the approval. The MCP specification wrote the same rule for remembered approvals of skills. Four answers, one week.

Three checks against your own system this week. For each write tool with a conditional approval rule, send a call that omits a defaulted argument and see what the rule was given. For each place a human can edit a proposed call, find which record your audit exporter reads. And for every redaction or strictness setting you rely on, write a test that tries to break it, because two of them were silently not enforced this month.

If this is your first issue, read the Start here page first; it sets out the obligations and the vocabulary used below.

The week in one paragraph. OpenAI Agents SDK 0.22.3 skips a conditional approval policy whenever validation would change the call, and sends it to a human instead (executed; the human is shown the unvalidated JSON). LangChain 1.4.2 keeps the model's proposal in the transcript and the reviewer's edited call in a private checkpoint key (executed). Agent Framework 1.19.0 binds approval to normalised arguments, voids it on repair, and in .NET refuses any approval it did not record itself. The MCP skills extension went Final with content-bound approvals. pydantic-ai closed an include_content=False bypass, and FastMCP restored strict validation it had been overriding since its SDK v2 migration. GPT-5.6 Sol's price in Issue 02 was wrong.

1.1 OpenAI Agents SDK 0.22.3: a conditional approval policy no longer sees arguments the tool will not run executed

The problem: your approval rule inspects the model's JSON; your tool runs on the validated, defaulted object. They can differ, and the rule approves the one that does not execute.

Commit 1d17ca4 (17 Sept, #5066, "align conditional approvals with validated tool arguments") adds src/agents/_function_tool_arguments.py and rewrites the needs_approval contract in src/agents/tool.py. The new docstring: "callable policies receive raw parsed arguments only when validation preserves their values, types, and dictionary order. Defaults, transformations, or arguments that cannot be inspected require manual approval. Application models, custom validators, and custom default factories require manual approval before validation runs." The check is can_prepare_without_user_code(), which inspects the Pydantic core schema and, per its own comment, will "never execute validation to discover whether it has effects"; even a str with a pattern is excluded because "Pattern constraints can invoke Python's backtracking regex engine". Then arguments_unchanged() compares the validated object with the raw JSON, floats by hex(). Anything that fails either test skips your policy and goes to a human.

async def needs_clinician(_ctx, params, _call_id) -> bool:       # the rule a CPOE team writes
    mg = params.get("dose_mg", params.get("dose", {}).get("amount", 0))   # doses are stored in mg
    return params.get("route") == "IV" or mg > 1000

@function_tool(needs_approval=needs_clinician, strict_mode=False)
def write_order(patient_id: str, rxnorm: str, dose_mg: int, route: str = "IV") -> str: ...

class Dose(BaseModel):
    amount: float; unit: str = "mg"
    @model_validator(mode="after")
    def to_mg(self):                                   # 1.5 g becomes 1500 mg
        if self.unit == "g": self.amount, self.unit = self.amount * 1000, "mg"
        return self

@function_tool(needs_approval=needs_clinician, strict_mode=False)
def write_order_v(patient_id: str, rxnorm: str, dose: Dose, route: str = "PO") -> str: ...
# agents.testing.ScriptedModel emits one call per case; state.approve() plays the clinician.

Observed, four scripted calls per version, no model key. 0.22.2: case B (route omitted) the policy received {'patient_id': 'pt-123', 'rxnorm': '860975', 'dose_mg': 500}, did not pause, and the FHIR stub recorded route: 'IV'; case D (1.5 g) the policy received {'amount': 1.5, 'unit': 'g'}, did not pause, and the stub recorded dose_mg: 1500.0. Summary line: "policy-required approvals missed=2 of 2 | approvals added on safe calls=0 of 2 | unapproved writes=2". 0.22.3: case A ran without a pause after the policy saw the explicit call; cases B, C and D printed "policy not called" and paused; after approval B was written IV and D 1,500 mg. Summary: "missed=0 of 2 | approvals added on safe calls=1 of 2 | unapproved writes=0". The scripted model said "Order placed." in all eight runs. Script test_oa_approval_arguments.py.

What it changes. The fix is right and it is fail-closed: a rule can no longer approve a call it did not see. But look at what the clinician is handed. The interruption's raw_item.arguments is the model's JSON: in case B, {"patient_id": "pt-123", "rxnorm": "860975", "dose_mg": 500}, no route at all; in case D, {"amount": 1.5, "unit": "g"}. The clinician signs, and the order is written IV, or at 1,500 mg. The gap has moved from the policy to the screen. Build the approval view from the validated arguments with defaults filled in, and store that rendered view with the signature. Second cost: every tool with an application-model argument (case C) now pauses on every call, so your conditional rule for it is dead code. Flatten the arguments of tools that need a conditional rule, or budget for approval fatigue, which is its own safety problem.

  • FunctionToolApproval.check_invocation raises "Function tool invocation changed during approval evaluation." if the tool, its invoker or the argument string changed between policy and execution. Log it; it means something mutated the call mid-decision.
  • Invalid arguments now go to a human too, and "validation errors follow the tool's failure policy only after approval, without invoking its body". A clinician can be asked to approve a call that will then fail validation.
  • Same release: d59fdb8 (#5017) fixes a tracing exporter that cached a missing OPENAI_API_KEY as None and then logged "skipping trace export" on every export. If your traces went quiet, check the key was present when the process started.
  • 9f6f6b1 (#5064) docs: UnixLocalSandboxClient "On Linux, this backend adds no OS-level confinement".

1.2 LangChain 1.4.2: when a pharmacist edits a call, the transcript keeps the model's version executed

The problem: a reviewer changes a proposed order before approving it, and later someone needs to know both what the model asked for and what actually ran.

Commit 5bf6a15 (18 Sept, #40463), shipped in langchain 1.4.2 (confirmed in the wheel). In libs/langchain_v1/langchain/agents/middleware/human_in_the_loop.py an edit decision no longer returns a new ToolCall; _process_decision now says "Keep the model's own call in the message; wrap_tool_call substitutes the reviewer's at execution time." The reviewer's call is stored under hitl_edited_tool_calls, annotated PrivateStateAttr, which is omitted from the agent's input and output schemas but persisted in the checkpoint. A default _EDIT_NOTICE is prepended to the ToolMessage and an edit_notice constructor argument can switch it off. An edit may also redirect to a different tool; the ToolMessage name then differs from the AIMessage's.

hitl = HumanInTheLoopMiddleware(interrupt_on={"write_medication_request": {"allowed_decisions": ["approve", "edit", "reject"]}})
agent = create_agent(model=scripted, tools=[write_medication_request], middleware=[hitl], checkpointer=InMemorySaver())
agent.invoke({"messages": [("user", "Start metformin for pt-123")]}, cfg)            # model proposes 1000 mg
out = agent.invoke(Command(resume={"decisions": [{"type": "edit", "edited_action":
        {"name": "write_medication_request", "args": {"patient_id": "pt-123", "rxnorm": "860975", "dose_mg": 500}}}]}), cfg)
ai = next(m for m in out["messages"] if isinstance(m, AIMessage) and m.tool_calls)
print(ai.tool_calls[0]["args"], RECEIVED, agent.get_state(cfg).values.get("hitl_edited_tool_calls"))

Observed. 1.4.1: transcript tool call dose_mg: 500, tool received 500, checkpoint key absent, "transcript args == executed args : True". 1.4.2: transcript tool call dose_mg: 1000, tool received 500, ToolMessage begins "Note: a human reviewer replaced this tool call before it ran. The call recorded in your message is the one you produced, not the one that executed." and ends "Executed instead: write_medication_request with arguments {... "dose_mg": 500}", checkpoint {'call_1': {'name': 'write_medication_request', 'args': {... 'dose_mg': 500}}}, invoke() output keys ['messages'], "transcript args == executed args : False". With edit_notice=None the ToolMessage is just "MedicationRequest written: 500 mg" and the checkpoint key is the only place 500 appears. Script test_lc_hitl_edit.py.

What it changes. Preserving the model's proposal is the right call for review: under 1.4.1 the edit erased what the model had asked for, so you could never measure how often a pharmacist corrected it. The cost is that the executed arguments are now outside the message history. An exporter that reads AIMessage.tool_calls as "what ran" was correct last week and is wrong this week, with no error. Write the audit row from the checkpoint key (via get_state, since it is not in the output) and the ToolMessage name, keep the notice on, and store the proposal and the execution as two columns. That pair is the correction-rate metric a medication-safety committee will ask for.

  • The source resets the key between turns "so an earlier turn's edits cannot survive into this one", and a new test, test_reused_tool_call_id_does_not_replay_a_previous_turns_edit, checks that a reused call id cannot replay an old edit. In my run the key still held the edit after the final text turn, so read it right after the tool step if you export per turn.
  • A reviewer redirect to a tool that is not available raises ValueError inside the tool node. Log it as a rejected decision, not a crash.
  • 1.4.1 (c01de7f, #40414): MCP tool arguments typed as an open object are kept open during provider conversion. A free-form gateway argument defeats any approval rule written against argument fields; force such tools into interrupt_on.
  • New experimental package langchain-typesafe 0.0.1a2 (17 Sept): AutoModeMiddleware, whose docstring says "This middleware blocks risky calls; it does not request human approval", at a fixed 0.5 threshold, with classifier inputs omitted from traces by default. Put it behind human approval, not in place of it.
  • Unreleased on LangGraph main (448a763, #8886): interrupt(value, response_schema=...) validates a resume value against a Pydantic model "before it is committed". When it ships, define the approval as a typed Decision with approver id and reason.

1.3 Agent Framework 1.19.0: an argument repaired after approval voids the approval docs, source read, not executed

The problem: middleware that fixes a malformed argument after the clinician has approved the call has changed what was approved.

Released 18 Sept. 216e761 (14 Sept, #8288) lets function middleware repair arguments, and docs/specs/004-python-function-calling-loop.md sets the rules: "Argument-repair middleware must precede security or policy middleware so enforcement observes the effective, normalized invocation", and changing arguments after security middleware has processed them "fails closed with MiddlewareFailure". An approval binds to "the normalized middleware-entry representation" compared float-bit-exact; "a changed approval-bound call executes zero times" and yields a replacement request with the same occurrence identity and a fresh generation, which "requires a second approval". 381e8e4 (#8449): "An unrelated user turn delimits standalone batches", so a stateless approval from one turn cannot be combined with a result from a later one. d5749bc (#8453) adds allow_concurrent_invocation (default True); a code comment warns a synchronous tool already running in a worker thread "cannot be interrupted and may complete its side effects" while its result is discarded with the batch.

What it changes. This is the strictest answer of the week: the approved arguments and the executed arguments must be the same value, and any change produces a second signature event. Note the contrast with 1.1: Agent Framework lets ordinary Pydantic coercion complete in one approval round because it binds after normalisation; the OpenAI SDK refuses to run a policy at all when validation changes anything. Order your middleware as the spec says, record replacement requests as their own rows, and set allow_concurrent_invocation=False for any agent whose tools write to a record.

  • .NET went further (024eb65, #8375, breaking): an AgentSessionStore is "required for approvals", and approval requests replayed in the inbound message history "are deliberately not trusted as the pairing authority". Python still offers a stateless mode. Same repository, two answers to where approval authority lives.
  • 4d5c63a (#8235): a tool's exception is replaced by the marker "FunctionInvocationError" in every serialised surface. Good for PHI; it also means stored history no longer holds the root cause. Capture context.result.exception in middleware.
  • cd9f4cc (#8358): an OpenAI background-mode continuation token was not cleared after a resumed stream, so "every iteration retrieved the same response again and ran its tools again until max_iterations". If you use background mode, check for duplicate writes from before this release.
  • 5d5fa52 (#8371, breaking): framework-created MCP, A2A and AG-UI HTTP clients no longer persist response cookies; "AG-UI thread IDs are correlation identifiers, not authentication boundaries."

1.4 MCP: the skills extension binds a remembered approval to a digest; FastMCP restores strict types docs, not executed

The problem: a host remembers "the user approved this", and the thing approved changes underneath the memory.

SEP-2640, the Skills extension, merged as Final on 13 Sept (1eb5bbe8; seps/2640-skills-extension.md). Its security section: "Skill content is untrusted input"; hosts "MUST apply the same approval gate to code-execution tool calls issued while the model is acting on an MCP-served skill"; the allowed-tools field "MUST be ignored for MCP-origin skills unless the user has explicitly approved that grant"; and "Content-bound approval. When a host persists any per-skill user approval, it MUST be bound to the entry's resources set (every uri and digest) observed at the moment of approval", with a changed set treated as revoked and re-prompted. It also says "Digests are not a security boundary."

FastMCP 4.0.5 (17 Sept, 053f128, #5141): "Tool parameters declared strict with Field(strict=True), StrictInt, or a strict model config are honored again ... Since the SDK v2 migration the server's lax default overrode them and silently coerced values." 4.0.4 (784ae75, #5106) stops logging argument values in validation warnings ("they may contain private client data"), and a01f835 (#5119) rejects self-contained ID-JAG tokens when identity assertion is not configured.

What it changes. Apply content-bound approval to tools, not only skills: key any cached human approval on a hash of the tool's name, description and input schema, and re-prompt when it changes. For FastMCP, a strict field on a dose or a patient id is part of the validated contract, and it was not enforced from 4.0.0 to 4.0.4. Add a test that "42" is rejected for each strict field. Whether an ID-JAG token could actually be minted against a server without the flow configured is unverified; the changelog files it as security hardening.

1.5 pydantic-ai 2.44.0: include_content=False could still export instructions docs, source read, not executed

The problem: you switched off content in telemetry because the prompts carry PHI, and some of it was exported anyway.

de4e615 (16 Sept, #8428), "Close two include_content redaction bypasses". In models/fallback.py the old line include_content=include_content_ctx.get() is not False exported content whenever the context variable was unset, which is the case in a FallbackModel refresh and in streamed consumer tasks. The replacement, span_include_content(span), "Fails closed on every answer but 'this span's own request wanted content'". Request parameters that could only be serialised as a string are now dropped: "There is nothing to redact in a string, so that is reported as unredactable rather than exported." Companion 255a109 (#8419) checks every content channel at once.

What it changes. If you run pydantic-ai with a fallback model or streaming and export OpenTelemetry with redaction on, instruction text may be in your collector. Upgrade, then search spans from those runs since redaction was enabled. A leak you cannot bound is a breach-assessment question for your privacy officer, not a bug ticket.

  • 2.44.0 5f43723 (#8269): AgentRunResult round-trips with run and conversation ids and trace context. Persist it, not only all_messages().
  • 2.44.0 8ca8238 (#8395): a capability @durable_operation called from a per-request hook was "silently running it inline", so not recorded in the durable history and re-executed on replay. Rerun replay tests on DBOS, Temporal or Prefect.
  • 2.46.0 (uploaded 19 Sept, built from in-window commits) b679e6d (#8082): dispatch uses the live tool_def, so an approval flag set by a prepare function now holds at execution.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. arXiv listings were read to the first fifty entries per day, so coverage of 12 to 16 September is incomplete.

Same Patient, Different Order: action-level reliability of clinical LLM agents under repeated runs
arXiv 2609.13582 · submitted 11 Sept, announced in window (date estimated from the listing) · Bellibatlu, Singh, Han, Zhang

The same MedAgentBench scenario run repeatedly with identical input, comparing the orders written (doses, tests, referrals) rather than pass or fail. 1,000 evaluations across 50 tasks. With an 8B model at temperature 0.7, "all 43 ordering groups emit a different set of orders across five identical runs", while benchmark scores were identical. Implementation note: add a five-run repeat with fixed input to your clinical-agent evaluation and fail it on any difference in the orders or arguments emitted, not on the task score.

Compositional Policy Violations: when step-level compliance fails in agentic AI workflows
arXiv 2609.18820 · 16 Sept · Kurady, Grandhi, Gupta, Mamoria

Defines violations where every step passes its own check and the run as a whole breaks policy, in four patterns: authority creep, threshold laundering, cumulative sum violation and context collapse. Proposes a provenance-tracking runtime that evaluates policy over the full execution trace. No quantitative results in the abstract. Implementation note: keep running totals per patient and per encounter across the trace (total dose, total units billed) and check limits there, in addition to the per-call rule from section 1.1.

Who Audits Whom, on What Substrate, with What Evidence? An independence-graded audit protocol for agentic AI
arXiv 2609.18272 · 16 Sept · Mohamed Chahine Ghanem

Grades audit independence on three axes: who controls the auditor, whether it shares the agent's technical substrate, and whether evidence is attestable or self-reported, using the beta-factor common-cause model from reliability engineering, with a seven-step protocol and a Monte Carlo study. A conventional internal audit "surfaces 5.9% of the faults it could in principle see and none at all in half the fault classes." Implementation note: write audit evidence to a store the agent cannot write to, and read it with tooling that does not share the agent's model or logging stack.

CliniCIRCA: constructing longitudinal mental-health patient journeys from raw EHR narratives
arXiv 2609.19585 · 17 Sept · Zhang, Ishfaq, Chandra, ..., De Choudhury

A modular pipeline that extracts clinical events from discharge summaries and assigns each a time even without event-level timestamps, then compresses them into a dated record. Built from 14,882 MIMIC-III mental-health admissions; the gold set is 52 summaries with 15,891 time-tagged events after clinicians corrected 629 errors; compression 1.52x; instruction tuning beat zero-shot and few-shot on every task. Implementation note: before summarising a long record, bucket events by date so the summary cannot lose or reorder when things happened.

HPOQuest: a rare-disease diagnostic agent using active phenotype acquisition
arXiv 2609.18431 · 16 Sept · Zaripova, Navab, Farshad, Marsico

Training-free: keeps a probabilistic ranking of candidate diseases from observed HPO phenotypes and asks the clinician the most informative next question. Across four cohorts, "gains of up to 30% points at Recall@1 and 45% points at Recall@5" from sparse initial phenotypes. Implementation note: when input is sparse, let the agent ask a ranked clarifying question before committing, and log the question and answer as evidence for the conclusion.

K-Bench: a clinically calibrated benchmark for LLMs in high-risk mental-health conversations
arXiv 2609.15855 · 14 Sept · L. M. Vowels, M. J. Vowels and others · leaderboard

200 multi-turn dialogues (suicide, self-harm, domestic violence, substance misuse, low-risk controls), 125 configurations of 33 base models. "A frozen GPT-4o judge achieved 94.2% exact agreement with clinician consensus across 6,751 eligible item comparisons." Reasoning modes did not raise the average; therapeutic prompting helped weaker models. The test set is held back. Implementation note: score risk assessment separately from supportiveness for any patient-facing agent, and do not assume a reasoning mode makes escalation safer.

Ask the Tool, Don't Guess: agent tool calls hold their progress, and the serving system should read it
arXiv 2609.18849 · 16 Sept · Liu, Zhang, Li, Zhang

Tools report progress while running, and the serving system uses it to decide whether to keep or evict the agent's KV cache during tool waits; about 21% lower p90 time-to-first-token than LRU eviction, near the oracle. Implementation note: for self-hosted inference, have long tools such as FHIR bulk export emit progress the scheduler can read.

Also in window: a University of Michigan medRxiv study of LLM-derived symptom clusters from 2,728 MIMIC-IV colorectal-cancer notes, where the systemic cluster predicted in-hospital mortality (OR 1.33) (10.64898/2026.09.15.26363148). Nothing new in window on compaction losing constraints; Issue 02's Tencent result stands.

Reading about a failure mode is not the same as watching it happen, and only one of those changes what you build. Both scripts run twice, on the week's release and the release before it, from one run_all.sh with no API key. Package: issue-03/lab.

5.1 The policy, the screen and the write

The problem: you have never compared what your approval rule was given with what your tool wrote.

test_oa_approval_arguments.py, openai-agents 0.22.2 and 0.22.3, agents.testing.ScriptedModel. Four calls through two write tools with the same rule. Watch case B on 0.22.2 (IV written, no approval) and on 0.22.3 (paused, and the clinician is shown a call with no route). Then change one thing: render the validated arguments on the approval screen and check that case B now displays route: IV.

5.2 Two records of one edited order

The problem: your exporter reads one record of an edited call, and since Friday it may be the wrong one.

test_lc_hitl_edit.py, langchain 1.4.1 and 1.4.2, a scripted chat model and InMemorySaver. The model proposes 1000 mg, the pharmacist edits to 500 mg. It prints the transcript's tool call, what the tool received, the ToolMessage, the output keys and the checkpoint key, then repeats with edit_notice=None. Then change one thing: write your audit row from the checkpoint key and assert it equals what the tool received.

Synthetic data only. RxNorm 860975 is used as an illustrative metformin code; the tools write to an in-memory list, not a FHIR server.

LinkedIn post candidate

My approval rule said IV orders need a clinician. The agent wrote an IV order and nobody was asked.

The model left out the route. The tool's default route was IV. The approval rule read the model's JSON, saw no route, and let it through; the tool ran on the validated arguments and wrote IV. Same with a dose sent as 1.5 g that a validator turned into 1,500 mg. I ran it with a scripted model and no API key on OpenAI's Agents SDK 0.22.2: two writes the rule should have stopped, zero approvals.

0.22.3, released on Thursday, fixes it properly: if validation would change the call, the rule is skipped and a human decides. Both writes now pause. But the human is shown the model's JSON too: no route, 1.5 g. They sign, and the order goes in IV at 1,500 mg. The gap moved from the policy to the screen.

The same week LangChain started keeping the model's proposed call in the transcript and the pharmacist's edited call in a private checkpoint key, and Microsoft's Agent Framework made any post-approval change to an argument void the approval. The question is no longer only who approves. It is what, exactly, they approved. Code and diagram in the issue.
