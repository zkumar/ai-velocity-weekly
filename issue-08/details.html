AI Velocity Weekly

The pharmacy agent stopped for the pharmacist, its parent was handed an empty string, and the clinician was told the order was placed: this week the gate sat inside a tool

Issue 08 · week ending 25 October 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

You build the sensible thing. A clinician-assistant agent does not write orders itself; it delegates to a pharmacy agent, and the pharmacy agent's place_order tool requires a pharmacist's confirmation. Two layers, one gate, the gate on the tool. Now wrap the pharmacy agent as a tool of the assistant, because that is how the framework says to compose agents. The child pauses for the pharmacist. The question that decides whether this is a safe system is what the parent is handed at that moment. On the release before Thursday's, the answer was {"result": ""}. No request reached the caller, the record held no row, and the parent, with an empty string and nothing else, told the clinician the order was placed. I ran it twelve times.

Google ADK 2.13.0, uploaded on 23 October, is the one I executed. AgentTool runs the child in a session it discards when the child's run ends, so a pause for confirmation inside the child has nowhere to go; 2.12.0 returned whatever text the child's last content had, which for a paused child is nothing. 2.13.0 tracks the child's unanswered long-running calls and returns a named error instead. That is better, and it does not make the gate reachable: on both versions, a confirmation requested inside an AgentTool cannot be answered by anyone. The documented alternative, the child under sub_agents with mode="single_turn", surfaces the pause on both versions, and on 2.13.0 the answered turn routes back to the agent that delegated, where on 2.12.0 it ended in the child. A second check, a hold appended to nested session state, was absent from the persisted session on 2.12.0 and present on 2.13.0.

The same seam, what a parent is told about a child, moved in four other places this week, which is why the theme is delegation rather than one bug. pydantic-ai 2.58.0 stops harness sub-agents from handing approval requests to a parent that cannot resolve them, and 2.61.0 carries a sub-agent's cancellation across the durable tool boundary as a failed tool result. The Claude Agent SDK 0.2.170 fixes session messages that dropped tool calls made in parallel because only one branch of a forked transcript was read. deepagents 0.7.30 lets an async sub-agent push status, completion and cancellation to the agent that started it. And Microsoft's Agent Framework 1.23.0 fixes an AG-UI thread snapshot that kept only the last of several approval results released together, so the next turn replayed a call with no result beside it.

Three checks against your own system. For every agent you have wrapped as a tool, find out whether anything inside it can pause for a person, and if it can, what the parent is handed and whether the person can be reached from the caller. For every store that holds approval answers, find out what happens when two answers arrive on different resumes and are released together. And for every piece of state a tool writes into rather than assigns, diff what the session service holds afterwards against what the tool saw.

1.1 Google ADK 2.13.0: the pause inside the tool, and the hold that never reached the store executed

The problem: you composed agents the way the framework shows, child as tool, and put the human step on the child.

google-adk 2.13.0 on 23 October. In google/adk/tools/agent_tool.py, read from both wheels, AgentTool.run_async creates a runner and an empty session for the child, iterates the child's events, closes the runner, and builds its return value from the child's last content. On 2.12.0 the last branch was return last_error_message or '' when that content held no text parts. A child that pauses for confirmation ends its run on a function-call part (adk_request_confirmation) and a function-response part carrying the tool's error dict, neither of which is text, so the parent received an empty string. 2.13.0 adds a pending_tool_ids set fed from every event's long_running_tool_ids, subtracts any id answered by a function response before the run ends, and if the set is non-empty logs a warning and returns Error: agent 'pharmacy' stopped waiting on unresolved long-running tool call(s) (pending call ids: [...]), which AgentTool cannot resume. The new comment in the source states the design: "HITL or remote input_required pauses do not" resolve in the same run, and the warning text says what to do instead, "Configure the agent under sub_agents (e.g. with mode='single_turn' for LlmAgent) if it needs to pause and resume." The changelog line is "surface HITL pauses in AgentTool instead of returning """, closing #7245.

pharmacy = LlmAgent(name="pharmacy", model=ScriptedPharmacy(),
                    tools=[FunctionTool(place_order, require_confirmation=True)])
parent = LlmAgent(name="clinician_assistant", model=ScriptedParent(),
                  tools=[AgentTool(agent=pharmacy)])              # the finding
# alternative, what 2.13.0's warning tells you to do:
pharmacy.mode = "single_turn"
parent = LlmAgent(name="clinician_assistant", model=ScriptedDelegator(), sub_agents=[pharmacy])

async for ev in runner.run_async(user_id="u", session_id=s.id, new_message=user):
    ...   # collect long_running_tool_ids, the parent's tool result, the final text
print(len(RECORD))

Observed, scripted BaseLlm subclasses for both agents, record counted after each run. AgentTool, 2.12.0: the parent's tool result was {"result": ""}; no adk_request_confirmation reached the caller's events; the parent's final text was Apixaban 5 mg BID ordered for pt-123 via the pharmacy agent.; the record held 0 rows. AgentTool, 2.13.0: the tool result was the error string above; the parent's final text began The pharmacy agent could not complete the order:; no confirmation reached the caller; 0 rows. sub_agents with mode single_turn, both versions: the caller's events carried the confirmation request with its id; answered with {"confirmed": true}, the order was written, 1 row. On 2.12.0 the turn after the answer ended in the pharmacy agent; on 2.13.0 it continued in the parent, which saw {"result": "Pharmacy: {\"status\": \"ORDER PLACED order-1 ...\"}"} (changelog: "route the turn after a paused single_turn sub-agent to its delegator", closes #7602). Direct, both versions: paused, confirmed, 1 row. Script test_adk_agenttool_pause.py; full table in section 5.

The second check is google/adk/sessions/state.py. A tool that does tool_context.state["patient"]["holds"].append("apixaban") mutates a container in place; on 2.12.0 State.__setitem__ was the only path into the delta, so the event's state_delta held only the top-level control key and the persisted session had "holds": []. 2.13.0 keeps a deep copy of every container a read hands out (_take_snapshot) and, when the flow reads ctx.actions to build the event, compares each with its copy and records the changed ones (_record_nested_writes), unless the container has no JSON form equal to itself, in which case it logs at debug and records nothing. Observed: the delta on 2.13.0 was {"holds_written": 1, "patient": {"id": "pt-123", "holds": ["apixaban"]}} and the session service held the hold; on 2.12.0 the delta was {"holds_written": 1} and the service held no hold. Script test_adk_nested_state_delta.py.

What it changes. The parent's sentence was a correct reading of an empty string and a false statement about the record, and nothing between the two was a bug in the usual sense: the child paused as designed, the tool returned as designed, the model read what it was given. If you have wrapped any agent that can pause for a person as an AgentTool, that pause has never been answerable, on any version; 2.13.0 only tells the parent so. Move the child under sub_agents with mode="single_turn", or lift the gated tool to the parent, and search transcripts from 2.12.0 and earlier for an AgentTool result of "" followed by a success sentence, because each is a decision made with no information. The state finding is the provability obligation in miniature: the tool's own view said the hold existed, the system of record said it did not, and no exception marked the difference. Until 2.13.0 is everywhere, write holds and flags as top-level keys, and in every test diff the persisted session against what the tool saw.

  • Also in 2.13.0, the batch from Issue 07 on ADK's side: "keep finished parallel tool results when a sibling raises" (closes #7428) and "preserve completed sibling tool responses on NodeInterruptedError". Not executed this week; the pydantic-ai run in Issue 07 is the reference for what the failure looks like. docs
  • "recover the correct occurrence of reused compacted tool calls", "load the whole session when rewinding", "retry a rejected dynamic child instead of replaying it", "send adk run queries as messages after a pause is answered", "stop persisting an OAuth2 credential whose code was never redeemed", and "isolate event compaction by isolation_scope" are each one line in the changelog and each a resume or history behaviour that changed without a flag. docs
  • Breaking: telemetry defaults to the OpenTelemetry GenAI v2 schema (otel_semconv_1_44) and drops the call_llm span; ADK_TELEMETRY_SCHEMA_VERSION_OPT_IN=otel_semconv_1_36 keeps the old one. Tool call content is reported under the semconv attributes and compactions are counted per workflow. If your audit pipeline keys on call_llm, it goes dark on upgrade. docs
  • Twelve experimental features are promoted to stable; MongoDbSessionService and MongoDbMemoryService arrive experimental; a TypesafeClassifier and ClassifierNode route workflows on a decision model's calibrated probabilities. docs

1.2 pydantic-ai 2.58.0 to 2.61.0: the sub-agent's request, two advisories, and a history that records which tools existed docs, release pages and advisories, not executed

The problem: the same delegation seam as 1.1 on a different runtime, plus a client path to a tool that bypassed the model.

Four releases in nine days. 2.58.0 (20 Oct), #10497: "Stop harness sub-agents from returning DeferredToolRequests to a parent that cannot resolve them." 2.61.0 (24 Oct), #11163: "Carry a sub-agent's RunCancelled across the durable tool-call boundary as a failed tool result." Between them, 2.60.0 (23 Oct) changes the shape of the history: #9405 records "every mid-run tool population change as a ToolAvailabilityDeltaPart"; #8094 deprecates RetryPromptPart "in favor of ToolReturnPart(outcome='retried') and RetryFeedbackPart"; #10958 keeps "streamed model deltas out of durable execution histories" and replays the final response instead; #9982 and #10452 store each message once in the Sqlite, Postgres and Mongo step stores instead of repeating the history in every snapshot; #11137 keeps dict key order on reload so a resumed run keeps its prompt cache. #10727 shows the ApprovalReviewer and ToolCallJudge "the arguments as written". From the ApprovalReviewer pull request (#10143), read this week for Issue 07's open question: the reviewer answers one yes, no or unsure risk question per approval request, "no approves the call on the person's behalf", anything else leaves it for a person, it "never denies a call, never runs one itself", reviews are durable operations under Temporal, DBOS and Prefect, and a review tool approval span carries the decision with arguments only behind trace_include_content. Whether the approval is written into the message history as a part naming the reviewer is not visible on the page. unverified

Two advisories with 2.58.0. GHSA-5pfm-2g3g-gh85: with non-empty server-side message_history and the default manage_system_prompt='server', "Vercel AI and AG-UI adapters could execute an available tool with client-chosen arguments without a model request." The advisory adds, "Approval-required tools are not executed by this path." GHSA-xv4x-g8mx-ch56, medium: provider-native MCP configuration could expose server URLs, authorization tokens and custom header values in OpenTelemetry request traces, even with include_content=False; fixed in 2.58.0 and 1.107.8, with a recommendation to restrict access to historical traces and rotate exposed credentials. 2.59.0 (21 Oct) carries a high advisory on HTML conversion in web_fetch, GHSA-4whf-38hw-pxxh, and #10544, which escapes the SummarizingCompaction transcript "so tool output can't forge messages", the exact failure section 3's first paper measures.

What it changes. A harness sub-agent's approval request used to surface at a layer that could not answer it, which is 1.1 again with the parent told rather than fed an empty string; now it stops where it can be resolved. The first advisory is the clearest argument this series has had for the approval requirement as a boundary rather than a courtesy: a client could choose a tool call and the server ran it, and the one thing that kept a tool out of that path was requires_approval. Put it on every write tool. The second advisory means trace exports from before 20 October may hold MCP tokens; rotate them. The history changes are schema changes: a reader that branches on RetryPromptPart will miss retries, and ToolAvailabilityDeltaPart is worth logging on its own, because an approval given while a tool was absent is a different approval from one given while it was present.

  • 2.58.0 adds a whole-run timeout= with RunContext.deadline (#10070), the budget seam Issue 02 executed; #10343 reorders Planning status events for DBOS recovery with a note that in-flight workflows "may not recover after upgrading; let in-flight workflows finish first". 2.60.0 adds RelevanceCompaction, which "keeps, reduces or drops each older history step" by a judge model (#11026), and per-run MCP auth and headers as functions of the run context (#10846). 2.61.0 makes the durable engine extension surface public (#11088) and closes fail-open paths in guardrails (#10841). docs
  • 2.60.0, #10892: an opt-in MetadataMemoryStore records "who wrote a memory file". That is the first field for an author on a persisted artefact in this series; it is on memory, not on approvals. docs

1.3 Agent Framework 1.23.0: the snapshot that kept one result, and a scope the store must now be given docs, changelog and pull requests, not executed

The problem: two approvals answered on different requests, released together, and a snapshot built from the last request only.

agent-framework-core 1.23.0 on 22 October. #8851, "Keep every queued approval result in the AG-UI thread snapshot", closing #8789, merged 15 October: with ToolApprovalMiddleware, approval decisions collected across separate AG-UI resumes are released as one batch; both calls run and both TOOL_CALL_RESULT events stream, but the MESSAGES_SNAPSHOT and the persisted thread snapshot kept only the result whose approval arrived in the final request, because results were restored by matching an approval response in the current request and earlier decisions had no match. "The next user turn then replays both calls with one result, leaving an orphaned call in history." The runner now records each native approval result as it streams and persists it "after the assistant message that issued its call, in call order"; later commits make the history sanitizer occurrence-aware for reused call ids, give an abandoned call that reuses an earlier id a skipped result, and state that "Settled approvals no longer protect a later reused call ID." #9413, breaking: AG-UI thread ids are "client-owned protocol correlation values, not authorization boundaries", so every endpoint registration must now supply an authorization_scope_resolver, the older snapshot_scope_resolver, or single_user=True; the scope "feeds snapshot, internal session, workflow/checkpoint, detached-run, and approval-state boundaries" and an invalid scope fails before any protected state is touched. #9535, "Improve settled approval matching", one line from its author; the review summary on the page says it prevents "duplicate approval IDs from enabling execution without an authoritative session".

What it changes. An approval answered one request earlier left no result in the record the next turn was built from, so the next turn saw a call with no outcome and ran it again: Issue 04's double execution with the approval store as the cause rather than the retry. And until this release the store that holds approval state had no owner unless you configured one; now the server refuses to start without being told whose it is. Before upgrading, add the resolver to every AG-UI endpoint, and search persisted threads for a call with no result beside a sibling that has one. Those are the replays.

  • #9476: when an outer stream failed, every ContextProvider.after_run still ran and InMemoryHistoryProvider "saves the partial response as a completed turn"; the error was recorded only on the outer stream, so telemetry treated the run as successful. A history that holds a failed turn as a completed one is Issue 07's lost return in the other direction. docs
  • #9583: a caller-owned MCP connection that lost its link used to retry "on the same ended object", which "could send a second request without actually reconnecting"; it now raises and asks for a replacement. #9592 removes gen_ai.tool.description and per-invocation gen_ai.tool.call.id from metrics dimensions. #9442: a background completion waiter could "take the newer continuation instead" of the one it waited on; waits are now bound to execution identity. docs
  • #9236, breaking, "Add the MCP 2.x compatibility foundation": requires MCP SDK 2.x, removes the Tasks surface, deprecates MCPWebsocketTool. The changelog lists it as shipped in 1.23.0 while the pull-request page rendered as open with review findings outstanding; which is current could not be settled from this machine. unverified
  • #9193: A2AExecutor accepts forwarded function-invocation and client arguments from request metadata through two separate allowlists that default to accepting nothing, so a tool-context key cannot be injected into client arguments. docs

1.4 LangGraph 1.2.16 and 1.2.17, LangChain 1.4.7, langchain-core 1.7.0, deepagents 0.7.27 to 0.7.32: a resume that does its work once docs, release pages, not executed

The problem: an approval answer passed to a resume has an effect on state, and you have never counted how many.

langgraph 1.2.16 was uploaded on 16 October at 22:11 UTC, after Issue 07 closed. Four lines: "apply a resumed Command's update once" (#9322); "save a resumed exit run's pending writes once" (#9314); "stop a subgraph from rerunning its finished tasks on resume" (#9315); "let other tasks finish when a resume value is invalid" (#9265), the companion to 1.2.15's invalid-resume fix in Issue 07. PostgresSaver and AsyncPostgresSaver gain prune (#9290). 1.2.17 (24 Oct) applies an explicit recursion_limit equal to the default and bumps certifi. langchain 1.4.7 (21 Oct) reads tool-call-delta in stream consumers and bumps mcp to 2.2.0; langchain-core 1.7.0 (22 Oct) emits "tool-call-delta for streamed tool-call args" instead of block-delta snapshots of the arguments so far, with the note "To keep snapshots, pin langchain-core<1.7." No change to HumanInTheLoopMiddleware in window. deepagents: 0.7.27 (16 Oct) tells the main agent about async sub-agent status updates (#6853); 0.7.30 (22 Oct) queues follow-ups "without interrupting active work" (#7082), adds notify_parent (#7132) and a webhook (#7072) to AsyncSubAgent, reports runs cancelled on the server (#7060), and drops "reasoning blocks bound to history a summary replaced" (#7127); 0.7.31 exposes execution output retention metadata in tracing (#6876) and removes the handoff mode alias (#7165).

What it changes. Four separate ways a LangGraph resume could do work twice, or stop work unrelated to a bad answer, close in one release, and none of them is a feature. If a graph resumes into a write on 1.2.15 or earlier, compare the count of state updates after each resume with the count of answers given, per thread. The streaming change matters to anyone who shows a reviewer the arguments as they arrive: a preview built from block-delta snapshots now has to accumulate slices, or pin. The deepagents lines are the parent's side of 1.1: a child that can push its status and its cancellation is one whose silence means something.

1.5 Claude Agent SDK 0.2.170 and Claude Code 2.1.305 to 2.1.310: the branch nobody read, and the MCP call sent twice docs, changelogs, not executed

The problem: the transcript an audit reads is assembled from a forked tree, and the assembler followed one branch.

claude-agent-sdk 0.2.170 (21 Oct), #1422: get_session_messages and get_session_messages_from_store "now return every tool call and result from turns that ran tools in parallel. Previously only one branch of the forked transcript was followed, dropping some calls and results." The Claude Code changelog carries no dates; the version range is inferred from the SDK's bundled CLI versions and PyPI dates. 2.1.307: "Fixed HTTP MCP tool calls being sent twice when the connection closed mid-call; only read-only or idempotent tools are now retried"; a claude_code.safety_event OpenTelemetry event "for each tool call a permission rule, auto mode, a safety check, a hook or the sandbox stopped, prompted or sent back"; subagent transcripts no longer record placeholder token usage for streamed responses; and /claude-api api-version moves code to API version 2026-10-21. 2.1.309: a self-hosted session that moves to a new runner "now sees the tool call that was interrupted, marked as outcome unknown"; PowerShell hooks that exit 2 now block, and PreToolUse and PermissionRequest hooks on Windows no longer fail open without Git Bash; sandboxed commands can no longer modify the MCP config passed with --mcp-config; teammates inherit the leader's tool deny rules. 2.1.310: a timed-out MCP call with an unanswered elicitation "now tells Claude that no answer came and not to repeat the call". TypeScript SDK 0.3.307 adds wakeup_source and scheduled_for to the lifecycle frame of a scheduled wakeup "so a host can tell which one fired".

What it changes. Any session transcript exported from the SDK before 0.2.170 that held parallel tool use is missing whole branches: re-export before anyone audits it. A write over HTTP MCP could run twice on a dropped connection; now it is not retried unless the tool declares itself idempotent, so declare it or expect a single attempt and a reconciliation. And the SDK now has three sentences for what the model is told about a call that did not complete: "outcome unknown" for an interrupted call on a moved session, "no answer came" for an unanswered elicitation, and the safety event for a stopped one. Those are the names section 5's empty string lacked.

1.6 OpenAI and Anthropic SDKs: a decision endpoint, a twelve-hour cache, and an API version that removes temperature docs, changelogs and migration guide, not executed

The problem: the platform under the agent changed its contract this week, in two places that a validation file names.

openai 3.32.0 to 3.37.0 (16 to 22 Oct): Decisions in Live sessions (#4088), an ultrafast service tier for Agents (#4101), 30-minute cache-write usage counts (#4111), compaction trigger ids (#4122), Vertex AI support for the Responses API (#4139), and in 3.37.0 a breaking change to the Decisions types: a question's instructions "can now be a string or a list of structured text, image, or JSON parts". API changelog: 12-hour prompt caching for Responses (20 Oct), with "12-hour cache writes cost 2.5x the input token price"; projects restricted to named service tiers (21 Oct); the Decisions API generally available on gpt-6-luna with 400 questions per request (22 Oct). The deprecations page reads "Access to these models was shut down on October 23, 2026" for the GPT-4 family, o1, o3-mini, o4-mini and gpt-image-1, with gpt-5.6-sol and gpt-5.6-terra as the named substitutes. @openai/agents-core 0.21.0 (20 Oct) moves saved run state to schema 1.23 with backward reads and removes the Runloop sandbox provider.

anthropic 2.0.0 (21 Oct) adds "support for new API version 2026-10-21", and the SDK changelog says no more about what breaks; the migration guide does. On the new version, temperature, top_p and top_k are removed and a request sending them returns 400 "even at default values"; document blocks in assistant messages and citations in user messages return 400; sampling uses the defaults. In the SDK regardless of version: the API key is sent as Authorization: Bearer rather than X-Api-Key; a client holds one credential; MessageParam becomes a union by role and can no longer be called; client-side compaction is removed from the TypeScript and Ruby tool runners in favour of server-side context_management with a trigger of at least 50,000 tokens; Text Completions are gone; the SDK and CLI move to Apache 2.0. 1.16.0 and 1.17.0 (20 Oct) add organization webhooks, user-profile enforcement events and RBAC error codes; 2.2.0 (23 Oct) adds message threads and four tool-runner fixes, one of which leaves "the tool runner's history to the caller after append_messages()". Platform release notes: Claude on Google Cloud, Anthropic-managed, on 22 October; user profiles general and organization webhooks in beta on 20 October. Nothing in window on Managed Agents sessions or approvals.

What it changes. A validated prompt with a non-default temperature cannot move to 2026-10-21 unchanged; either re-validate under the defaults or pin the old version per request, and write the version into the validation file beside the model id. A proxy or gateway that reads X-Api-Key breaks on 2.0.0. Compaction moving server-side means the summary that rewrites your history is now produced where you cannot read its code, which section 3's first paper makes a question worth asking of the vendor. On the OpenAI side, a twelve-hour cache is long enough for a shift, at a write price the model table's cached column does not include; and a decision endpoint at general availability is the cheapest possible "is this an order?" check, with no stated semantics for state or approval.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Identifiers and dates were read from the arXiv API's published field and the medRxiv details API; full texts were not read this week, so every number below is the abstract's and the authors' own.

Compaction laundering: provenance destruction in context-compacting coding agents
arXiv 2610.29869 · 21 Oct · Pixee

The paper to read beside section 1.6. Harnesses that flatten a typed conversation into one string with labels such as "[User]:" before summarising destroy message provenance, so content the agent merely read can be written as a user turn and come out of the summary as a standing instruction. "The forged approval launders into the agent's memory 87–100% of the time" across five flattening harnesses and "0% of the time" across four role-typed ones, up to a 908,000-token context; a code-level provenance check "catches 77% of laundering while demoting 2% of legitimate summary content". Implementation note: a compacted history is a place an approval can be invented, not only lost, and the summarizer is the party that signs it. Keep role typing through every summary step, keep clinical approvals in a typed, signed channel the summarizer never reads, and ask of any vendor-side compaction what it does with roles; pydantic-ai's #10544 is a framework closing the same door.

Local allow, global deny: why per-action authorization does not compose in LLM agents
arXiv 2610.27620 · 20 Oct · affiliations not shown on the record

Individually authorized tool calls can jointly violate a policy over intent, purpose, provenance, consent and delegation. The authors prove relational purpose violations are a 2-safety hyperproperty invisible to any per-action monitor, synthesize minimal two-call witnesses with a solver and no model, and find that "across nine LLM judges the per-action view approves the synthesized witness almost without exception", while the same judges flag it when shown both executions together; none of six surveyed guardrails monitors across executions. Implementation note: the per-call gate this series has measured for eight weeks cannot see a read for one purpose followed by a disclosure for another. Add a session-scoped monitor over pairs of calls to one patient record, and give any reviewer, human or model, the prior calls beside the one it is judging.

Write once, check many: reusable ledgers for post-hoc policy compliance auditing of agent trajectories
arXiv 2610.24483 · 17 Oct · affiliations not shown on the record

A writer model converts each trajectory once into a policy-independent ledger of actions and outcomes; any later policy is checked against the ledger alone. On 900 trajectories a 12B reader of ledgers "can either match or in fact achieve higher AUC" than the same model reading full trajectories, beats a 31B trajectory reader on multi-fact policies at .777 against .713, and "ledgers use about 5x fewer tokens, including the cost of writing them"; ledgers "can miss evidence in long tool outputs". Implementation note: the audit question a payer asks next year can be answered from a record written at run time, but write the ledger from the tool layer, in the layer's own voice, not from a model summarising the transcript, and keep the long tool outputs it points to.

ClinGuard: a governance framework for reliable, transparent and auditable clinical coordination
arXiv 2610.31354 · 22 Oct · perspective, accepted at npj Health Systems; authors include Robert M. Califf

A model-agnostic governance layer treats clinical coordination as "patient-scoped, policy-bound transactions rather than free text"; an independent sentinel "validates and governs agent-proposed actions, escalates when needed, and executes approved actions through limited-privilege connectors", every transaction linked to a "tamper-evident audit record", demonstrated retrospectively on MIMIC-IV-FHIR for skilled-nursing placement. No quantitative results; the authors separate the retrospective demonstration from a proposed prospective evaluation. Implementation note: it is the closest thing this week to a reference architecture for an agent that writes to the EHR, and its sentinel is exactly the layer section 1.1's parent did not have.

When is a memory safe enough to act on? Action-conditioned verification for long-lived agents
arXiv 2610.31446 · 22 Oct

Frames re-verification as a stopping problem: given a candidate, possibly irreversible action, decide which remembered premises to re-check and whether to proceed, verify or abstain, using bounded value of information. On ToolSandbox the gate "lowers mean verification cost by 33.9% while keeping 100% safe-proceed recall and 0% Gate harmful"; on AppWorld it "lowers verification cost by 21.3% at a small cost in safe-proceed recall". Implementation note: scale the re-read of allergies or the chart to the consequence of the write about to happen, not to how stale the cached fact looks.

Symbolic constraint agents: mining formal tool-call constraints to prevent agent errors
arXiv 2610.25552 · 18 Oct

Mines programmatic constraints on tool calls from API documentation, refines them against execution traces, and checks each call with an SMT solver at run time; a violation yields a warning or, when the valid replacement is unique, a repair. "Refinement raises error-detection F1 from 37.0 to 58.3 on GPT-5.5 traces and from 39.3 to 61.9 on Qwen3.5-27B traces"; repair removes "59–87% of failed calls across models". Implementation note: derive argument-level preconditions for your FHIR write tools from the specification, the encounter must exist before the DocumentReference that references it, and enforce them in code before the call.

Evaluating context compaction on the questions that come later
arXiv 2610.27301 · 19 Oct

Scores compaction on later questions over the same context rather than the one that triggered it. Keeping sentences judged necessary for the current question "raises its accuracy on that question by 11.4 points at 25% of the tokens", but on the later questions "no method that selects sentences for the current question does detectably better than deleting sentences at random"; on tau-bench trajectories "whose later tool calls need exact identifiers", sentence selection beats random. Implementation note: score your compaction on identifier retention, patient, encounter and order ids, and on the next ten tasks, not the current one.

RITE: evaluating end-to-end resilience to silent tool errors in e-commerce agentic systems
arXiv 2610.27777 · 20 Oct

Injects semantically plausible wrong tool returns with no failure signal into frozen workflow prefixes; 501 instances across nine workflows. "Across 10 recent LLMs, silent errors roughly halve task success and are consistently harder than explicit failures. Recognition, use of an available verification path, and integration of the resulting evidence form successive bottlenecks." Implementation note: not healthcare, but an empty string from a paused child is a silent error of exactly this kind. Build the verification path and test that the agent uses it.

A general-purpose System One decision model for clinical records
arXiv 2610.27099 · 19 Oct

CS1-4B, a 4B decision model trained on "12.4 million questions and answers from 3.6 million patients", answers typed questions over records in one forward pass with a probability "that can route uncertain cases to human review". "On 963,408 held-out patients, CS1-4B outperformed open decision models up to 27 billion parameters on 13 of 14 tasks"; in trial screening it placed "four times as many judged-eligible patients among its top 20 candidates as keyword search while using 690-fold fewer language-model tokens". Implementation note: for long-context EHR work, push repeated record reading into a small calibrated model with an explicit abstention threshold and let the generalist agent formulate questions.

Decision language models as affordable and rapid alternatives to LLM judges of clinical generative AI
arXiv 2610.28826 · 20 Oct · authors affiliated with the Jev vendor, treat as vendor-authored*

Compares a decision language model against twelve LLM judges on four clinical evaluation tasks. On 118 paediatric answers its agreement with physicians' ratings "matched or exceeded that of seven of 12 LLM judges, including Claude Opus 5.5 (0.49) and GPT-6 (0.38)"; it matched the HealthBench reference judge on 91% of criteria; "Frontier judges cost 73–294 times more than Jev and took 7–57 times longer". Implementation note: a cheap structured judge can be the first tier for grading agent actions at volume, with frontier judges on disagreements, after you validate it against your own clinician labels.

From clinician review to measurable human oversight of AI-drafted paediatric discharge documents
medRxiv 10.64898/2026.10.20.26365977 · 22 Oct · Montpellier University Hospital · NCT07874659

153 paediatric emergency discharges randomised to template assembly or drafting by an on-premises open-weight model, both validated by the discharging clinician. Family understanding "did not differ (difference −0.01; 95% CI −0.12 to 0.10)"; "clinicians edited 48 of 58 drafts, removing 18 of 22 unsupported additions but only 6 of 22 incorrect abbreviation expansions". Implementation note: human review catches invented content far better than substituted content, so flag expansions and normalisations for targeted review and log the draft-to-delivered diff as the oversight metric.

Decision-only medical AI: early evidence and pairing with language models
medRxiv 10.64898/2026.10.21.26366149 · 24 Oct · Beth Israel Deaconess, Harvard, Mount Sinai

Two decision-only models and one LLM tested for sensitivity to added labels and pressure cues with findings held constant, "across 2,134 case presentations and 2,483,222 model calls"; cue additions changed 13.4 to 14.0 decisions per 100, and pairing a decision model with the LLM "reduced this to 2.6", with triage accuracy near 81 to 82% and a cost of "at most US$0.77 per 1,000 entries". Implementation note: a cheap decision model beside the LLM can flag the sentence that swayed a decision for human review.

Also read: EGIP, an evidence-grounded interaction protocol that lifts evidence-supported correct answers from 10.20% to 36.55% under clinician review (arXiv 2610.24539, 17 Oct); multi-agent collaboration "buys task performance but not lower hallucination as a rule" (arXiv 2610.27027, 19 Oct); PROVISO, provenance-typed memory that decides which proposed action to commit before execution (arXiv 2610.27115, 19 Oct); VerifierBench, where generated verifiers "consistently reject invalid solutions more reliably than they accept valid ones" (arXiv 2610.28679, 19 Oct); SIM-UT on three deployed WhatsApp triage bots, whose key failure is de-escalation of emergencies (arXiv 2610.30412, 21 Oct); and a Vanderbilt report on delivering enclave-derived case-finding models through FHIR, SMART on FHIR and CDS Hooks, where counterexample review found "treating unavailable data as absent" among five failure classes (medRxiv 2026.10.20.26365982, 21 Oct). No in-window paper on prior-authorization automation or on duplicate actions was found; the nearest is a revenue-cycle denial-pattern study (arXiv 2610.27684).

LinkedIn post candidate

The pharmacy agent stopped for the pharmacist. Its parent was handed an empty string. The clinician was told the order was placed.

You build the sensible thing: an assistant that does not write orders itself but delegates to a pharmacy agent, whose order tool needs a pharmacist's confirmation. Then you compose them the way the framework shows, child as tool. I built that in Google ADK with no model and no API key, and let the child pause for its pharmacist.

On 2.12.0 the parent received {"result": ""}. No request to approve anything reached the caller. The record held no row. And the parent, with an empty string and nothing else, told the clinician the order was placed. 2.13.0, out on Thursday, hands the parent an error naming the pending call instead, which is better and still unanswerable: a gate inside an agent-as-tool cannot be reached by anyone on either version. Wire the child as a sub-agent and the pause surfaces; on 2.13.0 the answer even comes back to the agent that delegated. A second check: a hold appended to nested state never reached the session store on 2.12.0.

The same seam moved elsewhere this week. pydantic-ai stopped sub-agents handing approval requests to a parent that cannot resolve them. The Claude Agent SDK stopped dropping whole branches of parallel tool calls from session transcripts. Agent Framework stopped a thread snapshot from keeping only the last of several approval results. When you wrap an agent as a tool, ask what the parent is handed the moment the child stops for a person. Code in the issue.
