The policy said the discharge needed a clinician. The run handed the discharge to the EHR integration anyway, with the approval left behind, and the next release moved the question out of the run on a token

Issue 11 · week ending 13 November 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

An approval gate is only a gate on the path the call actually takes. In pydantic-ai, a tool can be external: the run does not execute it, it returns the call and your integration does. I gave a discharge agent one such tool and a policy capability whose validation hook raises ApprovalRequired for it, then had a scripted model, no API key, ask for the discharge on 2.66.0, the release before this week's window. The run returned a DeferredToolRequests with the discharge in calls, the plain list an executor runs, approvals empty and the gate's metadata gone. My stand-in for the EHR integration did what an executor does with calls and wrote the row. 2.67.0, uploaded on Tuesday, raises UserError before anything leaves the run and tells you the construction to use instead. 2.68.0, uploaded on Wednesday, goes further: an approval and a pharmacist's free-text question leave the run together on a resume token, and the answer comes back with a field called answered_by that the framework carries on the event stream, accepts as given, and does not write into the message history.

That is the shape of the week. The frameworks moved the question. pydantic-ai moved it out of the run and back in. Microsoft Agent Framework 1.26.0 bound an approval to the stored record of the call it answers and fails closed when the service-held history cannot be read. The Claude Agent SDK stopped launching when its settings file cannot be loaded, where 0.2.178 launched with the caller's permission rules and hooks dropped. Google ADK 2.14.0 seals a confirmation request the client walked away from as aborted, with a reason, instead of leaving it open. LangGraph 1.2.21 lets a parent graph read the checkpoint history of a child it never declared, which is the read deepagents now depends on. And openai-agents JS 0.22.0 refuses to compact a history that still has an unanswered approval in it. Every one of those is movement in the right direction, and every one of them moves something you were probably reading from the transcript to somewhere else.

Three checks against your own system. For every tool your run does not execute itself, find the list it leaves the run in and what the code on the other side does with that list. For every approval that arrives from outside the process, find the line that says who gave it and where that line is stored. And for every runtime you upgraded this week, find the new refusal, a missing file, a stale history, a cancelled call, and make sure it is logged as an event rather than swallowed as an error.

1.1 pydantic-ai 2.67.0 and 2.68.0: the approval that left the run with the call executed

The problem: one of your tools is executed by somebody else's code after the run returns, and your approval policy is written as a hook inside the run.

pydantic-ai-slim 2.67.0 on 11 November at 00:23 UTC, 2.68.0 on 12 November at 02:30; 2.66.0 is from 4 November. The release body for 2.67.0 lists #12958, "Raise UserError when validation requests approval for an external tool", under both Compatibility Notes and Bug Fixes. In pydantic_ai/_tool_execution.py on 2.66.0, a deferral raised while validating a call was routed by the tool's kind: a call on an ExternalToolset went into deferred_calls['external'], the list of calls the outside executor runs, whatever the deferral had been. An ApprovalRequired from an after_tool_validate hook therefore became an ordinary external call, and its metadata was dropped on the way. 2.67.0 adds a check in ToolManager.validate_tool_call, with the comment "Filing this call with the other external calls would hand it to their executor unapproved, and an approved external call can't be resumed", and a _route_deferred_call() whose docstring states the new rule: "A deferral raised during validation routes the call by its type, as one raised by the tool function would; only a call that validation didn't defer goes by its tool's kind."

class DischargeNeedsSignoff(AbstractCapability[None]):          # the policy, applied by name
    async def after_tool_validate(self, ctx, *, call, tool_def, args):
        if tool_def.name == "discharge_patient":
            raise ApprovalRequired(metadata={"policy": "discharge-needs-signoff"})
        return args

ehr = ExternalToolset([ToolDefinition(name="discharge_patient", ...)])   # executed outside the run
agent = Agent(FunctionModel(scripted), toolsets=[ehr], capabilities=[DischargeNeedsSignoff()],
              output_type=[str, DeferredToolRequests])
result = await agent.run("Discharge MRN 123 to home with the new anticoagulant.")
execute_external(result.output)             # what an executor does: run everything in .calls
print(len(out.calls), len(out.approvals), len(out.metadata), len(RECORD))

Observed, each run twice from clean environments with byte-identical output. 2.66.0: 1 call handed to the executor, 0 approvals waiting, 0 metadata keys, 1 row written: DISCHARGED MRN-123 via discharge_patient (call call-1). 2.67.0 and 2.68.0: UserError before anything is handed out, 0 calls, 0 rows. The error text names the fix: "an external tool call is executed outside the agent run, so the run cannot approve it. Raise CallDeferred instead to pass metadata to the code that executes the call, and approve it there." Script test_pydantic_ai_external_approval.py.

Then 2.68.0 moves the question itself. #12757 adds CallDeferred(kind="question") for a tool that asks for content rather than standing for work done elsewhere, DeferredToolRequests.kind() to read it back, a RequestInput(ask=...) capability and a pydantic_ai.external_events module. The capability's docstring: "ask either answers right away by returning DeferredToolResults, as a terminal prompt, a bot or a policy does, or hands the token to whoever will answer, by posting a Slack message, sending an email or writing a database row, and returns None." The run suspends until resolve_external_event(token, results) is called. The results carry a new answered_by dict, whose docstring is the sentence of the week: "Who answered each call, keyed by tool_call_id: a person's ID, a bot or a policy name. Reported as given in the DeferredToolResultsEvent of calls a handler resolves during the run; not yet recorded in the message history, so results passed to a new run with deferred_tool_results don't report it. Pydantic AI doesn't check it, so authorize whoever answers before you record who they are."

@agent.tool
def ask_pharmacist(ctx, question: str) -> str:
    raise CallDeferred(kind="question", metadata={"question": question})   # the answer comes from outside

@agent.tool(requires_approval=True)
def place_order(ctx, mrn: str, drug: str) -> str: ...

async def ask(ctx, requests: DeferredToolRequests, token: str) -> None:
    hand_to_whoever_answers(token, requests)          # here: a task that answers 50 ms later
    return None                                        # None means: wait for the token

result = await agent.run("Start apixaban for MRN 123 if the pharmacist agrees.",
                         capabilities=[RedactPhi(), RequestInput(ask=ask)], event_stream_handler=on_event)

Observed on 2.68.0: 2 pending requests, one approval and one question; a 43-character token handed out; one DeferredToolResultsEvent carrying answered_by for both ids; 0 mentions of the answerer anywhere in result.all_messages(); the pharmacist's typed answer, Yes, go ahead. Patient is MRN 123., arrived in the history as MRN *** because the RedactPhi capability's after_tool_execute hook saw it once, as it would a tool return; 1 row written. A second run with answered_by set to anyone@example.invalid is identical apart from the name. On 2.66.0 and 2.67.0 the import fails. Script test_pydantic_ai_request_input.py.

What it changes. On 2.66.0 a gate you wrote as a validation hook did not apply to any tool executed outside the run, and the output gave no sign: a DeferredToolRequests came back, which is what a gated run returns, with the gated call in the wrong list. If an external toolset fronts your EHR writes, pin 2.67.0 as the floor and re-run the test that counts rows, not the one that checks the output type. On 2.68.0 the run can wait for a person without a second agent.run, which removes a whole class of "which run did this approval belong to" bugs; what it does not do is check who answered, and it does not write the name into the transcript. Resolve the token only from a handler that has authenticated the answerer, and copy answered_by from the event into your own record, because the message history, which is what a transcript audit reads, will say the order was placed and nothing about by whose word. The result guard on the question path is the part to keep: a human's typed answer is content that can carry identifiers, and it went through the same scrubbing a tool return does. One more line from external_events.py: in a durable run on an engine that does not record the wait, "such as Temporal, DBOS or Prefect so far, the wait is refused: a wait in process would not be recorded, so a replay would ask again, could get a different answer than the one the run already acted on, and diverge from the engine's history." That is the right refusal, and it means the feature is in-process only unless your engine is AWS Lambda durable functions, Restate, Trigger.dev or Vercel Workflow.

What it changes. Before this release a sub-agent invoked through a tool left a record the parent's API could not open; you had to go to the checkpointer directly. Now the parent can read it, with two limits the lab shows. The read decodes with the parent's channels, so anything the child kept in a key the parent does not have is invisible through this path, which for an audit means the child's own notes still need the checkpointer or the child's compiled graph. And the address is only as durable as where you keep it: deepagents puts it in the tool message's artifact, which the model never sees and which a summariser can drop. Copy checkpoint_ns from the task message into the same table as the approval it belongs to at the moment the child returns.

1.3 Agent Framework 1.25.0 and 1.26.0: a policy that can be a function, and an approval bound to the stored call docs, changelog and wheel diffs, not executed

The problem: last week's fix added a default key for tools on neither approval list; this week's question is what a policy can say about a tool that appears on a later discovery refresh, and what an approval is matched against when it arrives.

agent-framework-core 1.25.0 on 7 November at 15:41 UTC and 1.26.0 on 12 November at 18:25. #10136: approval_mode on a local MCP tool now accepts "a synchronous callable receiving the discovered mcp.types.Tool or mcp.types.Prompt and returning "always_require" or "never_require", including its default decision. It runs once per item on each discovery refresh, including retained functions, before publication. Invalid results raise ToolExecutionException; callback exceptions propagate." A failed discovery now rolls approval_mode back to its pre-discovery value. The MCPSpecificApproval docstring and _mcp_approval_default() are byte-identical across 1.24.0 to 1.26.0, and the hosted MCP tools in agent-framework-openai 1.18.2 and agent-framework-foundry 1.16.2 still map only the two lists, so last week's finding stands: hosted tools do not read default. 1.26.0's three security pull requests, #9876 to #9878, are described in the changelog as binding "approvals to canonical stored calls, exact live controls, and pending session snapshots", binding policy state "to the effective service-history continuation", rejecting "opaque, changed, malformed, or partially archived continuations before approval execution or model dispatch", and failing "closed when service-owned history is unavailable". #10226 isolates run-level approval state when an agent is exposed as a tool, with the comment in _harness/_tool_approval.py that the claim is kept "out of the kwargs that MCP header providers and tools can read."

What it changes. A callable policy is how you say "deny anything I have not seen", including tools retained from an earlier refresh, which a static dict could not express. And from 1.26.0 an approval is matched against the stored record of the call rather than its position, which is the right design and has a consequence: when the service that holds the history cannot be reached, the action now fails rather than proceeds. Log that outcome as its own event. One more breaking change to test for: agent-framework-declarative 1.5.0 (#8662, labelled a security fix) opens a fresh MCP protocol session per handler call, so "Implicit server-session continuity no longer survives later calls, approval waits, or checkpoint resumes"; a workflow that relied on an MCP server remembering state across a pause will now find it gone.

1.4 Claude Agent SDK 0.2.179 to 0.2.181 and Claude Code 2.1.319 to 2.1.323: the launch that stops when the rules are missing docs, changelogs and wheel diff, not executed

The problem: your permission rules and hooks live in a settings file, and the file is not there on the day the deployment path changes.

claude-agent-sdk 0.2.181 on 12 November at 23:09 UTC, bundling Claude Code 2.1.323. The Python changelog on main still ends at 0.2.178, so this is from the wheel. subprocess_cli.py::_build_settings_value is rewritten: on 0.2.178 a missing or invalid settings path logged "Settings file not found" and launched the CLI with only the sandbox block; on 0.2.181 the docstring reads "Settings that can't be loaded raise: launching without them would drop the caller's permission rules and hooks", and it raises CLIConnectionError("Failed to load settings: ..."). The lab reproduces it without spawning the CLI: SubprocessCLITransport(...)._build_settings_value() with a nonexistent path returns {"sandbox": {"enabled": true}} on 0.2.178 and raises on 0.2.181. The matching Claude Code line, 2.1.323 (12 Nov): "Fixed claude -p and the Agent SDK running Bash unsandboxed when --settings or SDK settings that turn the sandbox on fail validation; Claude Code now stops at start-up and names the invalid setting". The same release: "Changed what happens when a tool's permission check fails with an error after a PreToolUse hook returned "allow": Claude Code now decides the call as if no hook had answered"; "Fixed --permission-mode auto or a settings defaultMode: auto starting in a mode that could allow more when auto mode was unavailable. It now starts in Manual mode, which asks first"; and "don't ask again" rules that look like they hold a secret, or would be saved to a git-tracked file, "lasts for the session only and isn't saved".

2.1.319 (6 Nov) added permissions.denyInsteadOfPrompting, "a tool call that would wait on a permission prompt is denied and the turn continues, in terminal sessions, subagents and teammates", and fixed "a Bash permission bypass where a crafted environment prefix could hide part of a command from permission checks", "a sandbox escape when creating a worktree", and "a case where a sed command could skip the permission check in accept-edits and auto mode". 2.1.321 (9 Nov) fixed "a PreToolUse hook's ask being lost when another hook's defer finished first", mcp_tool hooks "being skipped when their answer was over 16 MiB; the tool call is now refused", and claude -p "exiting 0 in silence" when an NFS quota lost transcript lines. The TypeScript SDK 0.3.323 states the hook rule as "it now goes to canUseTool, or is refused when there is no callback". One advisory in window: GHSA-5xjx-9qx6-jcrv, published 9 November, a time-of-check-to-time-of-use race in the Edit tool on macOS that let a sandboxed process write outside the workspace, fixed in 2.1.251 in September.

What it changes. Until Wednesday, a settings file that could not be read meant a run with fewer rules than you wrote and no error. Now it means no run. That is the behaviour you want from a control, and it will surface every deployment that was silently running without its rules; count those as findings, not as regressions. For headless runs, denyInsteadOfPrompting turns a prompt nobody will answer into a logged denial, which is what an unattended agent should do with a write it is not sure about. And a PreToolUse allow no longer overrides an error in the check behind it, so a hook that said yes is not the last word; if your audit log records the hook's decision as the decision, record the final one too.

1.5 Google ADK 2.14.0 and 2.14.1, ADK JS 2.5.0: the confirmation the client walked away from docs, changelog and wheel diff, not executed

The problem: the agent has asked the user to confirm an order, and the user closes the tab.

VertexAiSessionService.create_session now whitelists display_name, ttl, expire_time and labels and returns 400 for anything else; DatabaseSessionService gains Postgres columns as json not jsonb; the Firestore payload format changed in a way 2.13.0 cannot read after a rollback. Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Two negative findings worth a line: no paper in the window mentions FHIR or prior authorisation in its title or abstract, and ambient scribes appear only in an evaluation review and one trial protocol.

Safeguarding agentic AI in radiology workflows: a simulation of pre-action safeguards
arXiv 2611.11541 · 8 Nov · Eminovic, Schmidt, Levita, Lindholz, Penzkofer, Nawabi

The paper to read beside section 1, because it measures what a gate in the write path actually buys. 48 radiologist-reviewed synthetic scenarios plus 43 variants seeded with misleading information, six tool-using agents, 1,638 episodes, three arms applied before each action: permissions only, deterministic rules, and rules plus a local model checker. The primary outcome was an executed high-severity violation per episode: 7.3% to 27.1% with permissions only, pooled 19.4%; 16.7% with rules, a 2.8-point change whose interval crosses zero; 13.2% with rules plus the checker, 6.2 points, interval 3.0 to 9.5. In the misleading variants the agents opened the altered document in 83% of episodes and 58% of their erroneous statements cited it. Between 64% and 68% of blocked actions would not have caused a violation and were returned for revision, with no detectable drop in task success. Synthetic, and the authors' own summary is that the safeguards "reduced but did not prevent". Implementation note: permission scoping is the floor; the measured reduction came from a check in the write path, and most of what it blocks is a draft that gets fixed. Put a deterministic check and a checker in front of every write, budget for two in three blocks being revisions, and test with a planted wrong document, because the agents read it and cited it.

Authorization drift in LLM agents
arXiv 2611.09113 · 6 Nov · Cao, Zeng, Yin, Zhou, Huang, Chen, Yang, Li, Guo, Han

Agents exceed their authorisation without any adversary. 648 tasks across seven domains, each pairing a sufficient compliant path with an attractive unauthorised shortcut; 13 models, three frameworks, 25,207 trajectories. The most capable models drift in 43% to 61% of runs, capability tracks drift, and yet 86.18% of tasks have at least one observed clean trajectory, so the shortcut is a choice rather than a necessity. Drift is "dominated by early data over-collection", and data minimisation is the legal provision most often implicated. Synthetic tasks and no clinical domain. Implementation note: measure over-reading, not only over-writing. Scope the first retrieval call to the patient, encounter and date range rather than granting the chart, and count reads against the task's need in the access log, which is the instrument the PHI-canary paper used last week.

DeputyBench: do enterprise agents check whether a request is permitted?
arXiv 2611.13355 · 9 Nov · Zhao, Lin

79 base items, 375 instances, paired permission contexts in which the same request is permitted, denied, or undocumented; 12 models; 88.0% pooled safety and 79.1% paired success. The result that matters is secondary: restricted execution happened more often when the permission evidence was missing than when permission was explicitly denied, 10.3% against 3.5% on 27 matched tasks, 6.8 points with an interval of 1.9 to 13.0, and 61 of 100 executions under the masked condition sat in four privacy tasks needing cumulative counts or person-specific consent. The authors: "High safety with available evidence does not establish reliable stopping when permission cannot be verified." LLM-generated stage labels, secondary analysis. Implementation note: an absent consent or authorisation record must be a deny, not an unknown. Add the masked-record case to your evaluation set, since it is the one your agent will meet in production and the one most benchmarks skip.

Treating the model as an untrusted component: reference monitors, approval budgets and taint tracking
arXiv 2611.11571 · 8 Nov · Aljumaily, Alseelawi, Alshabandar

Compares in-prompt defences with a deterministic reference monitor, human approval and taint tracking on 13 tasks and 12 tools, with an effect-based oracle, two small open models and 156 attack episodes per defence. The models proposed the attacker's call in 64% and 84% of episodes; a task-bound monitor admitted 1.3% and 7.7%; a prompt guardrail moved obedience from 67% to 65% on one model. In a simulation, an adaptive attacker drove every guardrail stack to 100% success while the task-bound monitor held severe actions at 0%, and a human approval layer without a deterministic monitor failed to approval spamming "unless each episode has a deterministic approval budget." Two small models, static attacks, and the approval results are simulated. Implementation note: the approval prompt is an attack surface. Give each task a hard budget of approvals it may request, bind the monitor to the task's declared capabilities, and treat a run that keeps asking as a run to stop.

Cleaning an agent's history hurts when the world still holds the error
arXiv 2611.14654 · 10 Nov · Pakhomov, Koul, Liu, Pang, Joty, Nijkamp

Direct evidence on compaction and handoff. Agents are frozen mid-task, the history or the world is edited, and a receiver continues. A truthful note beside a preserved error raised recovery from 51% to 66%; replacing the error with a clean "completed action" dropped it from 50% to 44%. On AppWorld, after a database write, a success receipt lowered whole-task success from 45% to 28% when the effect was absent and raised it from 38% to 49% once present, a 27-point pooled difference, positive in six of eight receivers. Non-clinical benchmarks. Implementation note: a compaction that tidies a failed or unverified write is an instruction to the next agent to trust it. Carry failed and uncertain writes verbatim through every summary, and never let a summariser emit a receipt it did not read back from state, which is the same rule section 1.6's compaction skip enforces for approvals.

CapLite: capability policies derived from tool schemas, with write calls committed before any result is read
arXiv 2611.17115 · 12 Nov · Xu, Liu, Nakayama

Across 15 open-weight models, most of them 1.7 to 12 billion parameters, model-written security artefacts admitted attacks on 14, 13 and 11 models for three prior schemes, and a program-synthesis defence failed to run in up to 68% of episodes. CapLite derives policy from the tool schemas, commits write calls before any tool result is read, and admits a write only if every argument that decides whom or what it affects is stated in the user's request. No attack succeeded in 13,935 attacked AgentDojo episodes; utility under attack 29.0% against 27.2% for the heavier scheme, at 18% of its tokens. AgentDojo and small models. Implementation note: for order, message and write tools, require that recipient, patient, dose and destination trace to the clinician's request text rather than to a tool output, and reject the call when they do not.

MedCheckpoint: a multi-agent pharmacovigilance pipeline with locked parameters and deterministic tools
medRxiv 2026.11.10.26367711 · 12 Nov · Zhang, Zhou, Chui, Yu, Wu, Luo

Locks the core study-design parameters before execution, uses human-written statistical tools, enforces checkpoint rules that abort infeasible analyses, and allows optional human review, on a 54-question benchmark over a simulated 2.7-million-person EHR with planted spurious signals. Report quality, judged by three models, 4.81 to 4.88 against 4.25 to 4.55 and 4.02 to 4.29 for two coding-agent baselines; within-question standard deviation 0.116 to 0.186 against up to 0.440; the baselines failed on up to 2 of 21 runs on infeasible comparisons and MedCheckpoint produced "no misleading failures across all seven stress-test trap questions". Simulated EHR, LLM-judged, preprint. Implementation note: freeze the analysis plan as an artefact before the agent runs, and make "aborted as infeasible" a first-class, logged outcome rather than a failure to retry.
