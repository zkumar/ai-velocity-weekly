AI Velocity Weekly 06

AI Velocity Weekly

The pharmacist answered once and the record holds three pharmacy signatures: this week the pause turned out to be state that nobody was reading correctly

Issue 06 · week ending 9 October 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

A discharge needs two signatures, a pharmacist's and a physician's. Your agent pauses and asks both. The pharmacist answers first. Until the physician answers, the workflow is neither running nor finished; it is waiting. Here is the question nobody asks at design review: while it waits, what does the system believe is still open, and what has it already done? This week five frameworks changed their answer to that, and I ran all five.

In LangGraph below 1.2.13, the paused thread went on listing the pharmacist's question as open after it was answered. That is a display problem until you look at the record. When the approval gate was a node that signs and returns nothing, the framework did not consider it finished, and ran it again every time anyone resumed the thread. One pharmacist, one answer, three pharmacy signature rows. A second reviewer who answered the stale item with a rejection was accepted without error and ignored. 1.2.13 fixes both, for threads that start after the upgrade. A thread paused before it wrote the signature again when I opened it on the new version.

The other four are the same seam from different sides. Agent Framework 1.21.0 now runs a local write that arrives in the same model response as a question for a human, before the human answers, unless you give it a session. FastMCP 4.1.0 reports a timeout for a tool call whose write committed. OpenAI's JavaScript Agents SDK 0.20.0 runs the approved tool and then throws because the turn budget is spent. pydantic-ai 2.54.0 moves the audit hooks inside the wrapper, so a cache hit leaves no audit row. Each is a defensible change. Each moves what your system says happened away from what happened, in a different direction.

Three checks against your own system. Build your approval inbox from your own table of asked and answered questions, keyed by interrupt id, and treat the framework's pending list as a hint. For every write that can arrive beside a question in one model response, decide whether it may run before the answer, and test which one your version does. And for every tool result marked error, timeout or exception, ask the system of record whether the write is there before anyone retries.

If this is your first issue, read the Start here page first; it sets out the obligations and the vocabulary used below.

Framework changes, read from source

You want an agent to stop and wait for a person, and you want the waiting to be safe: nothing runs that the person has not seen, nothing runs twice, and what the system reports as open is what is open. Everything below is what the frameworks did this week to the state of a paused run.

1.1 LangGraph 1.2.13: the answered question that stayed in the inbox, and the gate that ran again executed

The problem: two people must approve, one has, and you ask the paused thread what is still waiting.

PR #9103, released in langgraph 1.2.13 on 5 October, adds langgraph/pregel/_task_status.py. Its docstring: "This module is the single place that turns that log into task status." Before it, execution, state snapshots and resume validation each read the checkpoint's pending writes on their own. The new rule: "A task is therefore treated as finished if and only if it has an output write", and when a task finishes with no state update the runner now adds a NO_WRITES marker. The docstring is plain about what came before: "Writes recorded before rule 1 existed may describe a finished task with no output using only control writes. Those tasks read as unfinished. The executor treated them the same way before and runs them again."

def pharmacy(state):
    decision = interrupt("pharmacy: approve apixaban 5 mg BID?")
    sign("pharmacy", decision)      # one signature row in the record; the node returns no state update

app.invoke({"patient": "pt-123"}, cfg)                           # both gates pause
ids = {i.value: i.id for i in app.get_state(cfg).interrupts}     # the approval inbox
app.invoke(Command(resume={ids[Q_PHARM]: "approve by rph-7"}), cfg)
print([i.value for i in app.get_state(cfg).interrupts])          # what is still waiting?

Observed. 1.2.12: after the pharmacist's answer the inbox still listed both questions. A second answer to the pharmacy item, "REJECT by rph-9", was accepted with no error; the pharmacy node ran again with the first answer and wrote a second row. When the physician answered it ran a third time. Two approvals, four signature rows. 1.2.13: the inbox listed the physician's question only; the second answer was accepted with no error and changed nothing; two rows. Control: with each gate also returning one state key, both versions wrote two rows, and 1.2.12 still showed the stale inbox item. Upgrade in flight: a thread paused and half-answered on 1.2.12 with a sqlite checkpointer, opened by a new process on 1.2.13, listed the pharmacy question again with next=('pharmacy', 'physician'), and wrote the pharmacy signature a second time when the physician answered: three rows. Script test_lg_pending_interrupts.py; full output in section 5.

What it changes. Two separate faults shared one cause. The stale inbox item affected every parallel approval below 1.2.13. The repeated execution needed one more condition, a gate that finishes without writing state, which is exactly what a node that only calls an API looks like. If you run parallel approvals on 1.2.12 or earlier, search the record for duplicate writes from any node that follows an interrupt() and returns nothing. Upgrading does not clean up a thread that is already paused: drain in-flight approvals before you deploy 1.2.13, or make the write idempotent first. And on both versions a resume addressed to an already-answered interrupt id is accepted silently, so your approval service must refuse the second decision itself.

  • Same release, PRs #9165 and #9170: update_state or a replay against a checkpoint the thread has moved past no longer leaks the edit into sibling branches of a DeltaChannel. Threads that already leaked keep the leaked write, and Command(resume=...) at a superseded checkpoint still does not fork. Read from the pull requests, not reproduced. docs
  • Per PR #9103 a bare Command(resume=value) now also raises when several interrupts are pending inside a subgraph task. The top-level case already raised on 1.2.12; the subgraph case I did not run. unverified
  • langgraph-sdk 0.4.6 (6 Oct, #9213) percent-encodes thread_id and assistant_id in thread-stream requests. An id containing /, ? or # used to alter the request path. If thread ids derive from MRNs or encounter ids, upgrade. docs
  • langgraph 1.2.14 (6 Oct) changes one line, the dependency floor langgraph-sdk>=0.4.6. No checkpointer package released this week.

1.2 Agent Framework 1.21.0: the write that travels with a question executed

The problem: the model asks a clinician a question and writes to the record in the same response.

PR #9050 (fixes #8898), released in agent-framework-core 1.21.0 on 8 October. Before, one model response carrying a declaration-only tool, which the host answers, and a local tool turned the whole batch into a user-input pause; the local call never ran. Now the batch is split. In _tools.py the executable siblings are stored under deferred_function_calls when the run has an authoritative AgentSession, and released once the host results arrive. Without a session they run at once.

ask_clinician = FunctionTool(name="ask_clinician", description="...", func=None, input_model={...})   # host-owned

@tool
def hold_medication(patient_id: str, drug: str) -> str:
    RECORD.append((patient_id, drug)); return "hold written"

r = await Agent(client=scripted, tools=[ask_clinician, hold_medication]).run("Review pt-123 potassium.")
print(r.user_input_requests, len(RECORD))      # what is the human shown, and what is already written?

Observed, one scripted response with both calls. 1.20.0: both calls returned as user-input requests, zero writes, with or without a session. 1.21.0, no session: only ask_clinician was shown to the human and the hold was already in the record. 1.21.0, with agent.create_session(): zero writes while the question was open; after the clinician answered "No. Do not hold; recheck K+ first." the deferred hold ran, one write. Script test_af_mixed_batch.py. The final text "Lisinopril held." is the stub's scripted line.

What it changes. On 1.20.0 the human saw a write as a request and it never ran. On 1.21.0 the human no longer sees the write at all. Without a session it has already happened when the question appears. With a session it waits for the answer and then runs whatever the answer was, because the framework orders the calls and does not read the reply. If a write must depend on a clinician's answer, the model has to see the answer and propose the write in a later response, behind its own approval. Check whether every production path passes a session; a stateless endpoint is now the path where the write goes first.

  • #9180 (fixes #9177): DevUI kept pending approvals keyed by request_id across the whole executor, so another conversation could consume one. Each entry now stores conversation_id and a mismatched response is rejected; entries with no recorded id keep the old behaviour. docs
  • #8853: with as_tool(propagate_session=True), provider-owned continuation keys are filtered in both directions, and a custom loop that cannot establish ownership fails closed on a non-empty session. docs
  • #9032 (fixes #8909): two providers sharing one AgentFileStore could lose an edit while both reported success. The new lock is per process; the cross-process case (#8912) is open. docs
  • .NET Microsoft.Agents.AI 1.24.0 (7 Oct), titles only: #8834 "Bind MCP approval headers to approved invocation", #8873 "Fix Foundry MCP approval replay IDs", #8855 "Validate handoff request lifecycle before routing", #8877 "Preserve A2A run errors when session save fails". docs

1.3 FastMCP 4.1.0: the result that arrived after the deadline executed

The problem: a tool has a timeout, the downstream system is slow, and the write lands after the clock runs out.

PR #5379 (fixes #5378), in fastmcp 4.1.0 on 8 October: a result that arrives after the tool's timeout is rejected. A synchronous tool declared with @mcp.tool(timeout=0.2) sleeps one second, appends an order to the record and returns.

Observed through the in-memory client. 4.0.11: is_error=False, content "ORDER PLACED", one row. 4.1.0: is_error=True, "Tool 'place_order' execution timed out after 0.2s", one row. The caller waited about one second on both; the synchronous body is not interrupted. Script test_fm_late_result.py.

What it changes. The old behaviour ignored the timeout you set. The new one honours it in the report and not in the world: the caller is told the call failed, and the order exists. An agent that sees an error retries. Treat a timeout on any write tool as "outcome unknown", look the write up by its idempotency key before retrying, and never let the model's retry be the reconciliation.

  • #5455, breaking: MultiAuth returns a source-qualified client_id and keeps the original in original_client_id. Existing sessions and tasks start new ownership scopes, so a task pending across the upgrade no longer belongs to the client that started it. Drain first. docs
  • #5229, breaking: http_session_idle_timeout defaults to "auto", the SDK's 30-minute idle expiry. It used to never expire. A human approval that takes 31 minutes now meets an expired session unless you set FASTMCP_HTTP_SESSION_IDLE_TIMEOUT=none. docs
  • 4.0.11 (4 Oct) security fixes: transforms, enabled state and auth are applied to hashed tool lookups (#5415), and component-manager routes use the server's auth provider (#5425). No advisory id is listed. docs

1.4 pydantic-ai 2.54.0: the audit hook moved inside the wrapper executed

The problem: your audit counter lives in a before-request hook, and a caching layer wraps the request.

PR #7053, in 2.54.0 (PyPI upload 3 October; the GitHub release page is dated 2 October): wrap_* hooks now enclose the whole stage lifecycle for run, node, model-request, tool-validate and tool-execute stages.

Observed with FunctionModel and one capability that logs both kinds of hook. 2.53.0: order before, wrap-enter, MODEL, wrap-exit, after; when the wrapper answered from a cache and never called the handler, before and after still ran, two audit rows. 2.54.0: order wrap-enter, before, MODEL, after, wrap-exit; on the cache hit neither ran, zero audit rows for an answer the caller received. Script test_pai_wrap_hooks.py. The pull request adds that a skipped provider call records no usage and no span attributes. docs for that last sentence.

What it changes. Any authorisation check, redaction or audit row placed in before_* or after_* can now be bypassed by a wrapper that returns early, and a cache or a guard is precisely the wrapper that does. Put mandatory checks in the outermost wrapper, or outside the agent. Add a test that a short-circuited request still produces your audit row.

  • 2.53.0 (2 Oct) carries a High advisory, GHSA-6fqq-452j-qhrp: ConcurrencyLimitedModel leaks slots on streamed requests, affected from 2.10.0. The workaround is agent-level max_concurrency. docs
  • #9434: an unexpected exception in a background tool now ends the run and cancels its siblings; before, the model was told "failed" and carried on. Raise ModelRetry or ToolFailed for anything recoverable. docs
  • #9041, harness: a ToolCallJudge lets a second model block or escalate selected tool calls. Its on_verdict callback is invoked again on durable replay, so an audit row written there needs the tool call id as its key. docs

1.5 OpenAI Agents SDK for JavaScript 0.19.0 and 0.20.0: approved, executed, then failed executed

The problem: the reviewer says yes, the tool runs, and the run that carried it does not finish.

0.20.0 (8 October), #2032: the model call that follows an approval resume now counts toward maxTurns.

Observed with a scripted Model, a tool with needsApproval: true, a round trip through RunState.toString() and a resume with maxTurns: 1. 0.19.0: the tool ran once, the model was called a second time, the caller received "Discharge signed." 0.20.0: the tool ran once, then MaxTurnsExceededError: Max turns (1) exceeded; one write, one model call, an exception. Script test_oa_maxturns_after_approval.mjs.

0.19.0 (5 October), read from the changelog, is the larger change for anyone holding paused runs. docs The RunState schema moves from 1.20 to 1.21; 1.20 still loads. On a durable resume the current approval policy is evaluated again rather than the stored decision (#1948). A resumed MCP call is bound to its original server, and an older pending call without that provenance throws "Original function tool is unavailable; restore its configuration or start a new run." (#1963). Checkpoints that lack initialInputGuardrailsCompleted, which includes every older snapshot past turn zero, are rejected (#2012). In 0.20.0, when a run is aborted before output validation the checkpoint's tool output is replaced with "Tool output discarded because the run was cancelled before output validation." (#2036).

What it changes. "The tool ran and the run failed" is now an ordinary outcome of a tight turn budget, and the exception carries no hint that a write happened. Catch MaxTurnsExceededError on a resume and reconcile before reporting failure. Before upgrading past 0.19.0, count the paused runs you hold: some will not restore, and those that do will have their approvals judged by today's policy, which is the right behaviour and a different one from what the reviewer saw.

  • openai for Python 3.25.0 to 3.26.1 (6 to 8 Oct), #4028: client.beta.agents.sessions.stream(..., on_tool_error=...) receives an AgentToolError with tool_name, call_id and a stage of arguments, execution or output. The local exception is never sent to the model and nothing is logged for you. Wire the callback to your audit log. docs
  • API changelog: the chat-latest alias moved on 7 Oct; pin model ids. Deprecations dated 1 Oct remove gpt-5.1, gpt-5.3-codex and gpt-5.4-nano on 1 April 2027, and existing evals become read-only on 31 October 2026. docs

1.6 Google ADK: a signature on every function call docs, changelog and source, not executed

The problem: a function call is stored in session history, and something edits its arguments between the model writing it and the tool running it.

google-adk 2.11.0 reached PyPI on 2 October at 00:46 UTC, hours before this window, and @google/adk 2.2.1 brought the same feature to JavaScript on 6 October (#979). ToolCallIntegrityPlugin(secret_key, *, allow_unstamped_calls=False) HMAC-stamps each function call into custom_metadata. The stamp covers app, user, session, invocation, branch, author, name, id and arguments. Stamps are verified before the run, and before_tool_callback refuses any call without a valid one with ToolCallIntegrityError. Tools run as workflow nodes are not checked.

What it changes. This is the first framework-shipped answer to substitution after approval: the call that runs is provably the call the model emitted, inside one session, under a key you hold. It does not sign what the reviewer saw, and it skips workflow-node tools, which is where ADK's confirmation flow lives. Turn it on, keep the key out of session state, and record the stamp in your approval row. Python 2.11.0 also seals a call aborted through the new abort_signal with a synthetic response, error_code='INVOCATION_ABORTED', and does not replay it on resume: one more place where an error result says nothing about whether the tool body finished.

1.7 Anthropic: an approval callable in the SDK, and a fetch tool that only follows links it has seen docs, release notes and changelog, not executed

The problem: the agent drives a browser or fetches a URL, and the gate is whatever your callback returns.

anthropic 1.12.0 (7 Oct) adds beta browser and computer toolset classes that take a confirm callable; every call is shown to it before running, and per the docstring any exception from it that is not a ToolError declines the call. Managed Agents, same day: web_fetch fetches only URLs already present in the session and returns url_not_in_prior_context otherwise; allowed_hosts now applies to both web tools; session creation returns 400 if allowed_domains is not inside allowed_hosts. The TypeScript agent SDK fixed three permission paths: deny and ask rules written with wildcards missed aliased tools (0.3.290), a subagent with a declared auto permission mode was decided by the classifier instead of canUseTool when auto mode was unavailable (0.3.292), and a permission answer with more than 4,096 updatedPermissions entries now counts as a denial (0.3.295).

What it changes. A confirm callback that fails closed is the right default, and it also means a bug in your callback reads as a clinician saying no. Log the exception separately from the decision. The fetch restriction is an exfiltration control worth copying in your own tools: an agent that can only fetch what it was shown cannot be talked into posting PHI to a new address. If you wrote Bash*-style deny rules in the TypeScript SDK before 0.3.290, some aliased tools were not covered; re-test them. Haiku 5.5 rejects budget_tokens with a 400, and claude-sonnet-4-5-20250929 retires on 30 November 2026.

1.8 LangChain 1.4.4: a compaction retry that drops the middle docs, wheel diff, not executed

The problem: the summariser itself overflows the context window.

langchain 1.4.4 (8 Oct), #41159. Before, SummarizationMiddleware re-sent the identical prompt three times after a ContextOverflowError. Now it retries once with a shortened prompt that keeps the head and the tail and inserts "[... middle of conversation omitted ...]", budgeted at half the tokens and capped at 40% of max_input_tokens. The event is logged at DEBUG. langchain-core 1.6.9 lets with_retry(retry_if_exception_type=...) take a predicate (#41158), which is how the middleware now skips errors marked non-retryable.

What it changes. A summary that silently omits the middle of a long chart review is a provenance problem if the summary is what the next step reasons from. Raise that logger to INFO for clinical agents, or wrap the middleware and record when the fallback fired, alongside the summary it produced.

  • langchain-core 1.6.8 (8 Oct, #41151) hardens the SSRF policy for IPv6: with SSRFPolicy(block_private_ips=False), ::127.0.0.1, ::169.254.169.254 and ::1%lo were allowed on 1.6.7 and are blocked on 1.6.8. IPv4-compatible addresses are now unwrapped and judged as IPv4, so re-test any blocklist written as an IPv6 ::/96 range. Checked by calling validate_resolved_ip on both versions during research; not in this week's lab package. No advisory is attached to the PR. docs
  • deepagents 0.7.22 (5 Oct, #6552): skill tools load only once the skill is read, tracked in a checkpointed state key, and if compaction drops the read the tool disappears. The set of tools the agent could call at step N is now state, so an audit of it must read the checkpoint. docs

1.9 Semantic Kernel 1.45.0: the HTTP plugin stops reaching private addresses by default docs, wheel diff, PR numbers unverified

The problem: a general-purpose HTTP tool can be pointed at your internal network.

semantic-kernel for Python 1.45.0 (6 Oct), read by diffing the 1.44.1 and 1.45.0 wheels because the release page would not open. HttpPlugin gains allow_private_network_access: bool = False; non-public addresses and DNS failures are blocked unless that or allow_all_domains is set, and the docstring says the check does not pin the resolved IP, so DNS rebinding remains possible. MCP server export gains use_plugin_names: bool = False; a duplicate bare tool name now keeps the first function and warns. Postgres filters are parameterised rather than inlined.

What it changes. If an agent reached a FHIR server on a private address through HttpPlugin, it stops working on upgrade until you allow it, and you should allow it by domain list rather than by the blanket flag. If two plugins export a tool with the same name over MCP, the second one is no longer callable; turn on use_plugin_names and check what your clients have been calling.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Identifiers, dates and numbers were read from the arXiv and medRxiv abstract records; full texts were not read this week, so every number below is the abstract's.

Do tool calls execute as intended? Measuring and repairing intent-execution correspondence in LLM agents
arXiv 2610.04375 · 3 Oct · Yanshan, Zhejiang, Nanjing and Aalto universities

The closest paper to this issue's theme. In 47,828 production shell calls, one coding agent's shell tool altered 12.0% of calls that carried code, escapes or long text, and 80.7% of the calls altered by backslash handling ran the wrong action with no error. All ten harnesses tested altered at least one call. The repair the authors propose recovers 79.2%, measured by them on their own tool*. Implementation note: log the call as received at every hop, model output, harness, wrapper, tool, and diff the hops. A transcript that records only what the model emitted cannot show this.

NOMOS: compiling written policies into statically verified tool-call gates for LLM agents
arXiv 2610.11030 · 8 Oct · affiliation not confirmed

Natural-language policy compiled into deterministic gates that sit in front of tool calls, evaluated on τ²-bench and AgentDojo. Violations among state-changing calls fell from 66.3% to 2.6% in the airline domain and from 30.8% to 6.9% in retail. The number to remember is the other one: a development version of one binding wrongly refused 95.9% of valid calls until the gates were replayed over past transcripts. Implementation note: enforce payer and clinical policy in code outside the model, and replay every new gate over recorded traffic before it ships, because a gate that refuses everything also has zero violations.

CHI-Bench: can AI agents automate end-to-end, long-horizon, policy-rich healthcare workflows?
arXiv 2605.16679 v3 · 30 Sept (first posted 15 May) · actAVA.ai with Johns Hopkins Medicine, Wellstar, Stanford, CMU, UCSD

Provider prior authorisation, payer utilisation management and care management, in a simulator of 20 healthcare applications behind 87 MCP tools, with an operations handbook of more than 1,290 documents. The best of 30 harness and model configurations resolves 28.0% of tasks; none clears 20% on the strict three-of-three measure; putting all tasks in one session drops the best to 3.8%. The benchmark is vendor-authored and scores third-party models. Implementation note: one case per session, and report pass-on-every-repeat rather than a single-run success rate for anything that touches prior authorisation.

MedicalHarness: a controlled evaluation of LLMs and agent harnesses on medical tasks
arXiv 2610.05778 · 5 Oct · Northwestern

107 tasks in four domains, five open-weight models crossed with five harnesses, with ablations of context management, planning and tool exposure. The harness and the interaction between model and harness explain about a quarter of the variance in outcome, and no harness is best across models. Implementation note: a validation result belongs to a model and harness pair. Swap either and re-run it; this week's five framework changes are five harness changes.

EHR-RobustGym: benchmarking and training agents for robust clinical reasoning
arXiv 2609.39371 · 30 Sept · Zhejiang University and Ant Group

MIMIC-IV with 5,486 paired clean and noisy tasks, solved by executing SQL and Python. Average success falls from 62.2% on clean inputs to 37.9% on noisy ones, and most models stay under 50% when a task must pass four times in four. The fine-tuning gains reported are for the authors' own models*. Implementation note: add cases where the evidence is absent, and require the agent to say so instead of answering.

Trajectory-derived confidence for reliable, resource-aware clinical text-to-SQL agents
arXiv 2610.04156 · 2 Oct · UCLA

A classifier over the agent's reasoning, code and database outputs with three stopping points: refuse before running, halt mid-run, withhold at delivery. On EHRSQL, delivered accuracy rises from 54% to 69% as coverage falls from 84% to 55%, with 13 to 28% fewer steps. Implementation note: an abstain-and-escalate gate is a pause, so everything in section 1 applies to it. Tune the threshold to the cost of a wrong answer in your workflow, and record each abstention as a decision.

A living benchmark for information retrieval from electronic health records (BRIE) and TRACE
arXiv 2609.30205 v2 · 1 Oct · Stanford; arXiv 2604.16364 v2 · 1 Oct

BRIE's revision keeps its finding, frequent omission of clinically important information, worst when the answer spans documents and encounters. The companion, TRACE, removes duplicated note text using metadata and cuts chart text by 47.3%, about 220,167 fewer tokens per patient, with F1 moving within roughly ±0.02. Implementation note: de-duplicate copied-forward note text before you reach for a summariser. It is deterministic, it is auditable, and it is where half the tokens are.

Beyond token savings: a systematic study of context compression in LLM agents
arXiv 2609.32961 · 26 Sept · UT Austin

Nearly 35,000 runs across three open-weight models on coding benchmarks, not clinical ones. Policies that used about a third of the tokens took 20 to 80% longer than no compression on Terminal-Bench with one model. Implementation note: judge a compaction policy on wall-clock time and task success for your model, not on tokens saved, and read it beside the LangChain change in 1.8.

Also read: CLAIRE on administrative form completion, where removing validation halved stress-suite success to 0.500 (arXiv 2609.32787); a local OCR-plus-LLM pipeline on 200 synthetic faxed referrals with weighted accuracy 0.990 and 0 of 11,993 facts fabricated (medRxiv 10.64898/2026.10.03.26364667, UT Austin, 5 Oct). No FHIR-agent benchmark paper appeared in the searches run this week.

5.2 The write that goes first

The problem: a question for a human and a write share one model response.

test_af_mixed_batch.py, agent-framework-core 1.20.0 and 1.21.0, a scripted chat client. The problem: your retry policy treats a timeout as "did not happen".

test_fm_late_result.py, fastmcp 4.0.11 and 4.1.0, in-memory client. Success and one row on 4.0.11; error and one row on 4.1.0.

5.4 An audit hook a cache can skip

The problem: the audit row is written by a hook, and something wraps the hook.

test_pai_wrap_hooks.py, pydantic-ai-slim 2.53.0 and 2.54.0, FunctionModel. Audit rows on a cache hit: 2, then 0.

5.5 Approved, executed, thrown

The problem: your caller treats an exception as "nothing was done".

test_oa_maxturns_after_approval.mjs, @openai/agents-core 0.19.0 and 0.20.0, a scripted model object. One write and a final answer on 0.19.0; one write and MaxTurnsExceededError on 0.20.0. Needs Node; run_all.sh skips it if Node is absent.

Synthetic data only. Every "record" is an in-memory list or a local sqlite file; nothing writes to a FHIR server. The models are stubs, so any sentence a "model" says in the output is a scripted line.

LinkedIn post candidate

The pharmacist approved once. The record holds three pharmacy signatures.

A discharge needs two approvals, pharmacy and physician, so the agent pauses and asks both. I built that in LangGraph with no model and no API key: two parallel gates, each of which signs the order and returns nothing. The pharmacist answered. On 1.2.12 the paused thread still listed the pharmacist's question as open. A second reviewer answered it again, with a rejection; it was accepted without error and ignored, and the gate signed again. When the physician answered, it signed a third time. Two approvals, four rows.

LangGraph 1.2.13, released Monday, fixes it: one question left in the inbox, two rows. But a thread that was already paused when I upgraded wrote the pharmacy signature again on the new version. The fix is real and it does not reach back.

Four other frameworks moved the same seam this week. One now runs a write before the human answers the question that came with it. One reports a timeout for a write that committed. One runs the approved tool and then throws. One lets a cache skip the audit hook. A paused run is state. Keep your own list of what was asked and what was answered, make the write idempotent, and after any error ask the record before you retry. Code in the issue.
