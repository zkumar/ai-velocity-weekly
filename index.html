AI Velocity Technology Update

A weekly technical brief for people building healthcare AI systems. Vijay Kumar.

An assistant answers. An agent acts. The moment software writes a medication order, submits a prior authorisation or files a regulatory document, you owe someone an approval, a proof of what happened, and evidence the system is under control. The frameworks were not built for that, and every release quietly moves where approval, state and audit live. Each week I read the source, run the mechanism, and report where the distance moved between what the audit trail says happened and what actually happened.

The gate inside the tool: what a parent agent is handed when its child stops for a person

Issue 08 · week ending 25 October 2026

A clinician-assistant agent delegated an apixaban order to a pharmacy agent wrapped as a tool; the pharmacy agent paused for the pharmacist, the parent was handed an empty string, and the clinician was told the order was placed. No request to approve it ever left the tool, on either release. This issue is about delegation as the unit: what the layer above receives when a child pauses, cancels or runs in parallel, which store records an approval answered on an earlier resume, and whether a write into nested state reaches the record at all.

While it waits: what a paused run reports as still open, and what it has already done

Issue 06 · week ending 9 October 2026

A discharge needed a pharmacist's and a physician's approval; the pharmacist answered, the paused thread kept listing the question as open, and the gate signed the order three times for one yes. How an issue is laid out

Two layers. Architect Intelligence, summary.html, is the two-minute scan: the week in one line, five tagged changes, WHAT CHANGED and WHAT TO CHANGE per card, and the mechanism of the week, as a web page and as a square carousel for LinkedIn. The long-form edition, details.html, carries the detail it links to: framework and API changes read from source with runnable code, a model table priced on one real workload, papers with an implementation note each, what the architects shipped, and the lab.

Claims carry a tag. Executed means the mechanism was run in a sandbox and the quoted output is what came back. Docs means the documentation or source was read but not run. Unverified means it could not be confirmed from a primary source. An asterisk on a number means the vendor reported it; unasterisked numbers come from a named independent measurement.

Running a lab

Every issue ships the code behind its findings with pinned versions. Synthetic data only, and no model key is needed for any script.

git clone https://github.com/zkumar/ai-velocity-weekly.git
cd ai-velocity-weekly/issue-02/lab
bash run_all.sh

That builds a clean virtual environment, installs requirements.txt, and runs every script. Each lab's README records the output observed when it was written, so you can tell at once whether your run matches.

Corrections and licence

Errors are corrected in the next issue with a note saying what changed. In Issue 01 a list of risk-adjustment category codes was wrong by one entry; the rerun caught it and the text was corrected. Quiet edits are worse.
