The allergy lookup failed, the order beside it went in, and the transcript said neither had happened: this week the batch became the unit of failure

Issue 07 · week ending 16 October 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

A model asks for two things in one breath: check the allergy list, and place the apixaban order. Your agent runs both at once. The order is written in milliseconds. The allergy service is down and raises three hundred milliseconds later. The framework does the defensible thing and fails the run. Now ask the question that decides whether this is a safe system: what does the history you are holding say about the order? This week the answer, on the release before Friday's, was that it said nothing, and on resume it said the order had been interrupted before a result was produced. The record said otherwise. I ran it eight times.

pydantic-ai 2.55.0, uploaded on 9 October, is the one I executed. Under its ordered-events execution mode, which the fix's author notes DBOS durable runs use by default, a tool that had finished lost its return when a sibling raised or the run was cancelled. A resume from that history filled the gap with "The tool call was interrupted before a result was produced." and the scripted model, reading that, ordered again. Two apixaban orders for one patient, and the model's final sentence was identical in the run that wrote one. 2.55.0 keeps the completed return in the interrupted request. The default parallel mode never lost it.

The same seam moved in four other places this week, which is why the theme is the batch rather than one bug. OpenAI's Python Agents SDK 0.24.0 stops dropping completed tool outputs from session history when a sibling fails, and stops compacting a history that still holds an unresolved approval. LangChain 1.4.6 lets a human-in-the-loop gate pause once per tool call instead of once per model turn, with each answer validated before it is saved. Agent Framework 1.22.0 stops a client's shared state, or a stored snapshot of it, from replacing the server's record of what was approved. And pydantic-ai 2.57.0, out this morning, adds a harness reviewer that lets a model approve low-risk tool calls before a person sees them, which is the first time this series has watched a framework hand the gate to a model on purpose.

Three checks against your own system. For every tool that writes, find out what your framework keeps when a sibling in the same batch fails, and test it with a sibling that raises and with a caller that cancels. Treat "interrupted" or "no result" in a replayed history as "outcome unknown" and look the write up by its idempotency key before anything acts on that history. And wherever an approval is stored, list who can write to that store: the reviewer, the client, a snapshot, and now possibly a model.

If this is your first issue, read the Start here page first; it sets out the obligations and the vocabulary used below.

Everything below is what the frameworks did this week to a batch of tool calls and to the store an approval sits in.

1.1 pydantic-ai 2.55.0: the return that did not survive its sibling executed

The problem: one model response asks for a read and a write, the read fails, and you resume from the history you kept.

PR #10049, closing issue #9942, in pydantic-ai-slim 2.55.0 on 9 October. The tool executor's ordered-events mode, parallel_ordered_events, runs calls concurrently and settles their results in emission order only once every call is done. If the call at index 0 raised during settlement, the exception propagated before index 1 was recorded; if the run was cancelled while waiting, nothing was recorded. Per the pull request, "a tool that had already finished lost its return from the interrupted ModelRequest", the resumed history filled it in with "The tool call was interrupted before a result was produced.", and "the model then re-ran a tool that had already completed, such as a write." 2.55.0 records every task in the segment that finished successfully after cancel_and_drain in both the CancelledError and BaseException handlers, emits no event for them, and leaves the exception unchanged. The same function is byte-identical in 2.57.0.

@agent.tool
async def lookup_allergies(ctx, patient_id: str) -> str:
    await asyncio.sleep(0.3); raise RuntimeError("allergy service 503")

@agent.tool
async def place_order(ctx, patient_id: str, drug: str, dose: str) -> str:
    RECORD.append((patient_id, drug, dose)); return f"ORDER PLACED order-{len(RECORD)} ..."

with agent.parallel_tool_call_execution_mode("parallel_ordered_events"):   # the DBOS default
    with capture_run_messages() as messages:
        try: await agent.run("Start anticoagulation for pt-123.")       # one response, both calls
        except Exception as e: print("raised", e)
history = list(messages)                                                  # what you would persist
await agent.run("Continue.", message_history=history)                     # what a resume does with it
print(len(RECORD))

Observed, scripted FunctionModel, record counted after each run. 2.54.0, ordered events, sibling raises: run 1 raised RuntimeError: allergy service 503; one row in the record; the captured history held no tool return at all. At run 2 the model was shown return[lookup_allergies]='The tool call was interrupted before a result was produced.'; return[place_order]='The tool call was interrupted before a result was produced.', emitted place_order again, and the record held two rows. 2.54.0, ordered events, caller cancels (asyncio.wait_for(..., timeout=0.1) while the lookup is still running): the same, two rows. 2.55.0, both cases: the history held return[place_order]='ORDER PLACED order-1 apixaban 5 mg BID for pt-123', the model answered in text, one row. Default parallel mode: one row on both versions in both cases. The final text, Apixaban ordered; allergy check still pending., was the scripted line in all eight runs. Script test_pai_sibling_failure.py; full table in section 5.

What it changes. The run failed, which is correct, and the failure erased the one fact a safe retry needed. Nothing in the exception says a write happened, and the history you would persist for a durable resume said the opposite. If you run pydantic-ai under DBOS or any setup that selects ordered events, and any tool in a batch writes, search the record for duplicate writes with an "interrupted" return in the transcript on 2.54.0 and earlier. On every version, treat that sentence as "outcome unknown": before a resumed run may act on it, look the write up by its idempotency key and put the real result into the history yourself. Upgrading fixes new runs; a history already saved without the return is not repaired.

  • Also in 2.55.0, three writes that used to repeat on a durable retry are now recorded as durable steps: Memory tool calls (#9832, "so forked DBOS workflows don't repeat writes"), Planning plan-store calls (#9789) and the tool requests of harness capabilities (#9705, listed as breaking). The default run_id and conversation_id now stay stable when a durable run re-executes (#9701, breaking), so an audit row keyed by run id no longer forks with the retry. docs
  • #9819 fixes history repair for a tool_call_id repeated within one response, the case Issue 05 executed on 2.53.0; and #8745 records every failed FallbackModel attempt with model, timing, error and usage, so the model that answered is no longer the only one in the trace. docs
  • 2.55.0 requires Python 3.11; 3.10 resolves to 2.54.0, which is the version above with the lost return. Pin explicitly. 2.56.0 (13 Oct) adds PGTaskDurability and keeps tests passing on DBOS 3; 2.57.0 (16 Oct) makes the waits between continuation polls durable DBOS.sleep steps (#10383). docs

1.2 pydantic-ai 2.57.0: a model in front of the human docs, release notes, not executed

The problem: reviewers are flooded with low-risk calls and someone proposes a triage step.

pydantic-ai-slim 2.57.0, uploaded 16 October at 03:50 UTC, #10143: "Adds a Harness ApprovalReviewer that lets a model approve low-risk tool calls before a person sees them." The release page gives no more than that line, and the source was not read for this issue. What is already knowable from the sentence is the shape: a second model reads a proposed call and decides whether a person needs to see it.

What it changes. This is a gate with a model on the approving side, and an approval it grants is a decision with no credentialed person behind it. Read it with section 3's paper on tool-call judges, which found judges "favored a visible incorrect value over a correct value whose source was hidden." If you adopt it, the risk tiering that decides which calls it may see belongs in code you own, every call it approves should be recorded as model-approved with the reviewer's model id and version beside the decision, and a write to a patient record should not be in the low-risk tier at all.

1.3 OpenAI Agents SDK for Python 0.24.0: the sibling, the compaction and the approval docs, release notes and pull requests, wheel read, not executed

The problem: the same batch failure as 1.1, on a different runtime, plus a background process that rewrites history while a question is open.

openai-agents 0.24.0 on 15 October. #5332, closing issue #5327 "Finished tool call is dropped when a parallel tool's guardrail trips", merged 14 October: client-managed runs now keep accepted call and output pairs, with their reasoning and replay state, through session history, error details, streamed results and RunState recovery when another tool in the same turn fails. "The run still reports the failure, and rejected input or tool output is not published." The accepted output is recorded after tool-output guardrails and provider conversion but before custom-data extraction and end hooks, so a failed run can keep an output whose optional metadata is incomplete. The author lists what it does not do: no recovery when on_llm_end raises before tool execution, server-managed continuation keeps its existing path, and "exactly-once external side effects across crashes or failed persistence" are out of scope. #5318 does the same for outputs after a callback failure.

#5363, merged 13 October, fixes issue #5340: automatic Responses compaction ran while a tool approval was unresolved, "sends the unresolved call to the API", and the API returned 400 before the approval request reached the caller. The tool-group integrity check now applies to complete automatic histories, hosted MCP approvals are matched by request id, and compaction waits until the call and its output are both present. Alongside: deferred approval history persists across resumes (#4828), pending input is rejected when a completed stop tool ends a resume (#5366), approved tools are traced inside the resumed agent span (#5294), and RunState snapshots move to schema 1.21, which older SDKs cannot read.

What it changes. On 0.23.1 a guardrail tripping on one tool could remove a finished sibling from the history the next turn is built from, which is 1.1's failure with a different cause. On 0.24.0 the record of the accepted call survives, and the caller is told which tool failed. The compaction fix closes a quieter gap: an approval that was still open could be the thing a background rewrite removed, and the caller saw an HTTP error rather than the question. Before you upgrade, count the paused runs you hold; schema 1.21 is one-way. After you upgrade, handle tool_error_formatter calls with kind="tool_exception" explicitly, because that is now how a tool's own exception reaches your formatter.

  • openai for Python 3.27.0 to 3.31.0 (9 to 14 Oct): agent environment suspension and expiration (#4046), prewarmed hosted environments (#4043), beta session spending limits (#4058) and a billing_not_active session error code (#4052). A session that stops on a spend limit or a suspended environment is one more stop that is not a completion; make sure your audit row distinguishes it. docs
  • API changelog, 15 Oct: GPT-Live sessions can call the Decisions API natively on gpt-live-1 and gpt-6-luna, so a typed classification can run on transcript deltas while a person is still speaking. For an ambient-scribe flow that is the primitive for an "is this an order?" check before the end of the sentence. docs

1.4 LangChain 1.4.6 and LangGraph 1.2.15: one pause per call, and the answer the tool swallowed docs, wheel and pull requests, not executed

The problem: a reviewer answers one question for a whole batch, and an invalid answer to a single call vanishes.

langchain 1.4.6 (14 Oct), #41062, read from the installed wheel: HumanInTheLoopMiddleware(interrupt_mode="per_call"). The default stays "batched", one interrupt per model turn carrying every gated call, with decisions in a separate list matched by position and not checked before they are saved. In per-call mode each gated call raises its own interrupt of type tool_approval, with a response_schema that lists the decisions that tool allows; reviewers answer by interrupt id; LangGraph validates each answer against the schema before saving it; an edit cannot switch tools and its arguments must match the tool's Pydantic schema; a bad answer raises ValidationError and nothing is saved; a gated call with no tool call id raises before pausing; each answered call resumes on its own and unanswered calls stay paused. The pull request warns that middleware listed before HITL runs again up to the pause, and that if one answer in a multi-answer resume is invalid, the others may already have run. The minimum langgraph rises to 1.2.12, the first with interrupt response_schema.

langgraph 1.2.15 (12 Oct). #9232: interrupt(response_schema=...) raises a pydantic ValidationError on an invalid answer, and ToolNode treated any ValidationError from a tool as bad model arguments, sent the model an error asking it to fix the call, and the interrupt was no longer pending. "The human never saw the problem." The error is now marked, langgraph.errors.is_invalid_resume() identifies it, and ToolNode re-raises it whatever handle_tool_errors says; a GraphInterrupt under wrap_tool_call with non-default error handling now propagates too. Also in 1.2.15: astream_events no longer drops control and interrupt events on v1 and v2 (#9219); a cached node's writes are saved as if the node had run (#9259); a drain requested before an interrupt_before breakpoint stops at the breakpoint (#9281); no checkpoint is saved past a failed DeltaChannel write (#9235). langgraph-checkpoint 4.3.0 shipped the same evening; its release page would not open, so its contents are unverified.

What it changes. Per-call mode is the first time LangChain's gate matches the unit this issue is about: one approval, one call, one validated answer, one resume. Batched mode will remain the default until the next major, and in batched mode a decision list matched by position is exactly the binding Issue 03 found fragile. Turn per-call on for any agent whose gated tools write, and treat the pull request's warning as a design rule: nothing before the HITL middleware may have a side effect, because it runs again. On 1.2.14 and earlier, a tool that pauses with a schema and gets a malformed answer resumed as if the human had said nothing; search for model turns that contain a validation-error message following an interrupt.

  • langchain 1.4.5 (12 Oct, #41225) lets SummarizationMiddleware take a summarizer callable, which is where section 3's source-judged compaction result can be applied. langchain-core 1.6.10 (12 Oct, #41180) declares mid-conversation support in model profiles. docs
  • @langchain/langgraph 1.5.0 (12 Oct) and deepagents 0.7.24 to 0.7.26 (12 to 15 Oct) released in window; their notes were not readable from this machine. unverified

1.5 Agent Framework 1.22.0: the client that could write the approval docs, changelog and pull requests, not executed

The problem: a UI sends shared state back to the server, and the server merges it into the session the approval middleware reads.

agent-framework-core 1.22.0 on 15 October. #9368, breaking, merged 15 October: AG-UI copies client Shared State into AgentSession.state minus a set of server-owned namespaces, and that set came from optional attributes a wrapper could hide. For a wrapped agent, "Client Shared State, including state replayed from a stored Thread Snapshot, could supply or replace the approval state the middleware reads", covering rules, queued approval requests and collected approval responses. Now any top-level client value holding a non-empty rules, queued_approval_requests or collected_approval_responses list is not merged, restored server state is authoritative over client values, and a bounded warning names the ignored keys. The author chose the wide trigger deliberately "because narrower item-shape checks can be bypassed by other encodings." #9316 and #9365, also breaking, enforce fail-closed trust boundaries on AG-UI requests and bind workflow continuations and interrupts to the resolved thread id. #8819 discards pending workflow state after a failed or interrupted superstep; its description calls the old behaviour "silent state corruption", where writes staged by a failed run could be committed by a later successful run() on the same instance.

What it changes. Until 1.22.0 a browser could, in the specific wrapped-agent case, tell the server which calls were approved. That is an approval store with the client on its write path, and it is the kind of thing that only shows up when you list the writers. The fix is shape-based and will also drop a legitimate client key that happens to carry one of those three names, with a warning; grep your client state for them before upgrading. The release carries a persisted-state warning of its own: 1.22 can read older records, older runtimes cannot read records containing hosted or merge_mode, so do not run mixed workers against one store and do not plan on a downgrade.

  • The core fix list for 1.22.0 includes "correlate mixed-pause host responses" (#9079) and "preserve concurrent workflow steps across pauses" (#9291), the pause shape Issue 06 executed on 1.21.0, and "redact sensitive telemetry, omit tool arguments from metrics" (#9361, #9288). If your audit relied on tool arguments appearing in metrics, they no longer do. docs
  • #8886, breaking: content identity, hosted execution, replay and stream-merge semantics are consolidated across providers; the changelog's compatibility note covers chat histories, session stores and checkpoints that embed serialised content. docs

1.6 Google ADK 2.12.0: a hook on the way back, a confirmation on every node, a delivery id on every trigger docs, changelog, not executed

The problem: the tool answered, the model has not seen the answer yet, and nothing stands between them.

google-adk 2.12.0 on 13 October. after_tool_callback screens tool output before it reaches the model (closes #6966), the mirror of the before_tool_callback that 2.11.0's integrity plugin used. require_confirmation now works on @node and FunctionNode, extending the workflow-node pause Issue 05 executed on ToolNode. Auth credentials are kept out of the caller's tool arguments (closes #7162). A trigger's delivery id is exposed "so tools can detect redeliveries" (closes #7322). Sibling tools are cancelled on a child-originated cancellation (closes #7172), id-less responses are counted when resuming parallel calls (closes #7387), and sub-branch interrupted tool calls are replayed when is_resumable is false. The Sensitive Data Protection path continues with de-identified text when only SDP matched (closes #7369), Google credentials in session state are encrypted, and the mutating /dev and agent-builder endpoints are restricted to local clients by default.

What it changes. Three of those lines are the batch again from ADK's side: what happens to siblings when one call is cancelled, how a resumed parallel batch counts responses that carry no id, and whether an interrupted call on a side branch runs again. None of them is a feature you turn on; they change what a resume does. A delivery id on triggers is the idempotency key this series keeps asking for, handed to you by the framework for the first time: store it with the write. And after_tool_callback is where a FHIR response can be checked against the request before the model reads it, which is verification outside the model with a named place to live.

1.7 Anthropic: spans by default, an identity on the agent, and a hook whose edits are now checked docs, changelogs and release notes, not executed

The problem: the audit trail is whatever your own code wrote, and the SDK writes nothing.

anthropic 1.14.0 (14 Oct): native OpenTelemetry tracing, on by default when the application registers a global tracer provider, with trace-context headers from the global propagator; off with open_telemetry=False or ANTHROPIC_OPEN_TELEMETRY=false. The same release adds execution_identity to Managed Agents agents and telemetry destinations to the Admin API; 1.13.0 (9 Oct) adds workflows, multi-agent configuration and thread status filtering to Managed Agents; 1.15.0 (15 Oct) adds a speed parameter with usage.speed and returns an organisation's usage-tier spend cap. Platform release notes: dynamic workflows for Managed Agents in beta (9 Oct), OpenTelemetry export for Messages requests and sessions in beta with the destination set in the Console (14 Oct), and a Compliance API endpoint that returns members' saved instructions (15 Oct, Enterprise). The TypeScript Claude Agent SDK, 0.3.300 (14 Oct): updatedInput returned from PreToolUse and PermissionRequest hooks "is now validated like Claude's own input and unknown keys are dropped"; 0.3.301 (15 Oct): per-tool permission policies on SDK MCP server configs, always_ask or always_deny.

What it changes. A span per request with propagated context is the cheapest audit trail a compliance team will accept, and it now appears without a line of code, which also means it appears in places you did not plan for it; decide where PHI in prompts must not be exported before the upgrade. The hook change matters to anyone who stamped approval metadata into a tool's input from a hook: an extra key you added to carry the approver's id is now dropped silently. Keep the approval record beside the call, not inside its arguments. An execution_identity on a managed agent is a field for who the agent runs as; it is not a field for who approved.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Identifiers, dates and numbers were read from the arXiv abstract records, several through a mirror because arXiv rate-limited this machine; full texts were not read this week, so every number below is the abstract's.

Judges follow the reference: the derivation gap in verifying tool-call arguments
arXiv 2610.18497 · 13 Oct · affiliations not shown on the record

The paper to read beside 1.2. Tool-call judges accept a correct argument value less often when the input does not state what the value should be, and across all seven judges tested they "favored a visible incorrect value over a correct value whose source was hidden." A derived reference, produced by a separate model from the full history without seeing the candidate, lifts controlled-test AUROC "from chance or below to between 98.40 and 99.59", the authors' own measurement*. Implementation note: a model that approves write arguments must see how the value was derived or be handed an independently derived reference; otherwise it approves whatever is visible, which is what the model that proposed the call made visible.

Prune the summary, not the history: source-judged compaction for long-horizon agents
arXiv 2610.20927 · 14 Oct · University of Virginia

In a widely used structured compressor, 83% of failed runs traced back to an action that carried out a specific summary entry, most with no supporting environment output. Scoring each summary entry for provenance and dropping the unsupported ones, one judge call per compaction, improves reliability on AppWorld and OfficeBench by 2.1 to 8.9 points with no extra agent tokens. Implementation note: this is 1.1 at the summary layer. A compacted history that asserts an order was placed, or was not, with no tool output behind it is the same gap; LangChain 1.4.5's summarizer hook is a place to put the provenance check.

Auditing escalation reliability in healthcare LLM agents: a perturbation-controlled benchmark of workflow-state failures
arXiv 2610.21270 · 15 Oct · Washington University in St. Louis, Southern Methodist University

400 synthetic healthcare workflow episodes; models choose answer, clarify, abstain or escalate under a declared 5:1 cost for a missed escalation. Five open-weight models at 1.7B to 9.7B reach clean accuracy of 0.97 and, when prompted to use their uncertainty, miss 32% to 97% of required escalations; verbalised confidence has an ECE of 0.10 to 0.54, and a confidence-only policy "yields no utility gain." A workflow-aware controller cuts missed escalations to 0.12 to 0.24, but its rule detectors fall from recall 1.00 on trigger phrases to 0.00 on unseen paraphrases. Labels are single-author. Implementation note: do not gate escalation on a model's stated confidence; make escalation explicit workflow state in the harness and paraphrase-test it.

MedHarnessBench: a unified benchmark for healthcare agent evaluation
arXiv 2610.15714 · 11 Oct · HKUST (Guangzhou)

342 executable tasks across FHIR and EHR operations, administrative interfaces and multimodal clinical tools, more than 16,000 controlled executions, scored on seven process dimensions including clinical auditability, closed-loop verification and conduct boundaries, with an intervention trace that records whether runtime support was available, activated, delivered, adopted and carried forward. No headline percentages in the abstract. Implementation note: it is the first benchmark in this series that scores the harness separately from the model; borrow its seven dimensions as the acceptance rubric for an agent that writes to FHIR.

Verification turns capability gaps into routing decisions: small language models for clinical documentation
arXiv 2610.19169 · 13 Oct · Optum

A fixed four-evaluator verification stack with refinement; swap the generator between a 4B QLoRA model and a frontier model. Claim-level factual entailment 0.984 against 0.992; a small-by-default route that escalates on verifier rejection reaches 99.6% verified acceptance across 250 encounters against 98.4% frontier-only, sending 62 encounters up. Without refinement, acceptance is 26.8% for the small model and 74.8% for the frontier one. The frontier provider refused two trauma transcripts the on-device model handled. Numbers are the authors' on their own pipeline*. Implementation note: put the provability in the verifier and keep its acceptance record; the generator then becomes a cost decision.

Which metadata matters for LLM tool selection in MCP? Evidence from controlled factor-level interventions
arXiv 2610.14334 · 9 Oct · affiliations not shown on the record

Metadata of 367,174 MCP tools analysed; across five models and five tasks, changes to the parameter schema "produced the largest and most consistent shifts in selection", models favour separate top-level parameters over composite ones, and when only one schema met an explicit requirement all five models chose it despite position bias. Implementation note: the write tool you want chosen is the one whose schema matches the task; flat top-level parameters with explicit descriptions, or the model routes to a sibling.

ProgAgent: learning tool orchestration through programmatic training
arXiv 2610.14774 · 10 Oct

Programmatic tool calling keeps tool outputs in runtime variables rather than the model's context; on 215 tasks at four environment scales, a 14B model reaches a 30.7% pass rate at 64k tokens of environment state where the baselines score zero, the authors' own benchmark*. Implementation note: for long-context chart work, pass the FHIR bundle as a handle and keep it out of the window.

When pleasing the user compromises care: AI sycophancy in caregiver-mediated healthcare
arXiv 2610.14360 · 9 Oct · Stanford, Texas A&M

Across veterinary, paediatric and eldercare settings, a stated inferior preference from the patient or the caregiver "substantially increase[s] switches from appropriate to inappropriate care", and the failures accumulate across turns. No numbers in the abstract. Implementation note: an agent that takes instructions through a proxy needs a policy gate that does not read the requester's preference at all.

Also read: a trained per-step confidence that lifts failure-prediction AUROC from near chance to 0.68 to 0.85 (arXiv 2610.18614, 13 Oct), which pairs with the escalation paper above: a trained signal is usable, a prompted one is not; "Same context, different agents", where compaction makes investigator-type agents repeat steps (arXiv 2610.20959, 14 Oct); TRACER, a multimodal harness over hospital video and records (arXiv 2610.21266, 15 Oct, Stanford); and, just before the window, a study of 127,833 clinician queries across 6,342 clinicians finding documentation and administration at 36.2% of use and diagnosis at 3.7% (arXiv 2610.11069, 8 Oct). No medRxiv agent preprint was found in the searches run this week.

5.1 The write that finished beside a tool that failed

The problem: you have never asked what your framework keeps in the history when one call in a batch fails, or counted writes after a resume from that history.

test_pai_sibling_failure.py, pydantic-ai-slim 2.54.0 and 2.55.0, FunctionModel. One response carries lookup_allergies, which raises after 300 ms, and place_order, which writes one row. The run fails; the captured history is resumed; the scripted model orders again if the history says the order was interrupted. LAB_MODE selects the execution mode and LAB_CANCEL=1 replaces the raising sibling with a caller that cancels the run after 100 ms.

5.2 The model table

build_models.py regenerates models.json from the prices in section 2 and prints the table. Change the workload constants to your own document mix.

Synthetic data only. The "record" is an in-memory list; nothing writes to a FHIR server. The model is a stub, so any sentence a "model" says in the output is a scripted line.

LinkedIn post candidate

The allergy check failed. The order beside it went in. The transcript said neither had happened.

A model asks for two things at once: look up the patient's allergies, and place the apixaban order. The agent runs both. The order is written in milliseconds; the allergy service is down and raises a moment later. The framework fails the run, which is right. I built that in pydantic-ai with no model and no API key, then did what any durable executor does after an error: resumed from the history I had kept.

On 2.54.0, under the ordered-events mode DBOS uses by default, that history held no return for the order. The resume told the model the call had been "interrupted before a result was produced." The model ordered again. One patient, two apixaban orders, and the model's closing sentence was word for word the same as in the run that wrote one. 2.55.0, out last Friday, keeps the return. The default mode never lost it. A caller that cancels the run gets the same result as a sibling that raises.

The same seam moved elsewhere this week. OpenAI's Agents SDK stopped dropping a finished tool's output when a sibling's guardrail trips, and stopped compacting a history with an approval still open. LangChain's gate can now pause once per call instead of once per turn. Agent Framework stopped a browser's shared state from overwriting what the server thinks was approved. And a framework shipped a reviewer that lets a model approve low-risk calls before a person sees them. When a batch fails, ask the record what happened before the history tells the model.
