The audit gap

Start here. What this weekly is about, who it is for, and how to read it. Vijay Kumar, Wipro HCLS and ER&D.

Every week I read the source of the frameworks we build healthcare agents on, run at least one mechanism on my own machine, and report where the distance moved between what a system's audit trail says happened and what actually happened. That distance is the audit gap. It is where healthcare AI will fail, and almost nothing written about agents is looking at it.

The problem this publication is about

An assistant answers. An agent acts. That sounds like a small distinction until you put one in a clinical or payer workflow, where acting means writing a medication order, submitting a prior authorisation, updating a design history file, or filing something a regulator will later read. The moment software takes an action on a patient's record, you inherit three obligations that no chatbot ever had.

Someone must approve it

A named human, with credentials, at the right moment, before the action happens and not after. Not a checkbox in a prompt: a real gate the system cannot route around.

You must be able to prove what happened

Months later, to an auditor, a medical director, or opposing counsel. Which model, which version, which prompt, which approval, which write, in what order.

You must show it is under control

That the thing running today is the thing you validated, that you notice when it changes, and that you measure it continuously rather than once at go-live.

None of the frameworks we build on were designed for those three obligations. LangChain, the Microsoft Agent Framework, MCP, the model APIs themselves: they were built to make assistants that answer, and they are now retrofitting approval, durable state and audit at speed, under competitive pressure, in releases that ship weekly. That retrofitting is honest work and mostly good work. The difficulty is that it keeps moving where approval, state and audit actually live, and it moves them in changelog lines that read like housekeeping.

Which brings us to the failure this publication is named after.

Your audit table records that Dr Rao approved a metformin order at 10:41 and the agent wrote it. Your FHIR server has no order. Nobody lied, nothing crashed, no exception was raised. The two records simply disagree, and you find out weeks later.

That is not hypothetical and it is not rare. In the first two issues I hit it twice, by running the code rather than reading about it. In one case an approval carrying a forged identifier was correctly rejected by the framework, the write never happened, and the model, called again with its tools withdrawn and no tool result to go on, cheerfully reported "Order placed." In the other, a clinician's approval that arrived after the agent's new wall-clock budget was dropped in silence, with one log line at INFO, and the model said the same thing. Both behaviours are defensible in isolation. Both produce a system whose narrative and whose database disagree, and in both cases the seam was invisible from the documentation.

So the working assumption here is simple. The model's text is never your source of truth for whether something happened. The gap between the story and the record is an engineering artefact you can find, measure and close, and finding it requires reading source and running it, not reading announcements.

What I do each week, and what you get

Every Friday I sweep the repositories and release feeds of the agent frameworks, model APIs and healthcare interoperability standards, clone what changed, install it, and run the mechanism that matters on synthetic data. The issue that comes out has the same five parts every time, so you can skip to the one you need.

Framework changes, read from source

What actually changed, with file paths and commit ids, not the marketing note. A short runnable snippet framed on a healthcare task. What it does to state, approval and audit in your loop. The gotchas visible in the code. At least one mechanism every week is executed end to end and tagged as such. This section has twice contradicted a vendor's own release notes.

A model table, priced on one real workload

Ten thousand clinical documents at four thousand input and five hundred output tokens, with and without caching, so the comparison is in money rather than leaderboard position. Licence and context alongside, because an open-weight model with the wrong licence is not a candidate for on-premise PHI.

Papers, with the implementation note

Five to eight from the week, each with the method and its numbers, then a line saying what a builder should do differently on Monday. If a paper does not change what you would build, it does not appear.

What the architects shipped

Technical output only, from the people building this infrastructure. Never job moves. If someone shipped nothing this week I say so, because an empty week is information too.

A lab you can run in thirty minutes

The code behind the week's findings, packaged with pinned versions and a single script that builds a clean environment and runs everything. Synthetic data only, no API key needed for most of it. Reading about a failure mode is not the same as watching it happen on your own machine.

There is also a five-line news sidebar, because releases and regulatory moves matter, and five lines is all they need. Anything longer belongs in one of the many good healthcare AI digests that already exist. This is not one of those.

Standing positions

Some conclusions do not change week to week, so I state them here once and the issues do not repeat them. Each issue reports only what moved against these positions.

Own the gate. The place a clinician approves an agent's action must be in a layer you control, not a vendor policy, a hosted runtime or a clock. A framework may offer a gate; you still write the transcript.

The model's text is never proof a write happened. Only the system of record can say an order, a claim or a note exists. Every executed finding in this series checks the record, not the reply.

No frontier model has an independent medical score. Every health number a vendor publishes for its own model is the vendor's own until an outside benchmark measures it. Model slides report price on one fixed workload and say which numbers are independent.

Verification lives outside the model. Retrieval targets, authorisation constraints and tool-output checks belong in code between the tool and the model, because the model believes what it is handed.

Regulation is an architecture constraint, not a news item. A comment window, a named regulator or a funded reference architecture changes what a compliant deployment has to look like. Issues report the change; the obligation is standing.

How to read an issue

Claims carry a tag. Executed means I ran that mechanism in a sandbox and the output quoted is what came back. Docs means I read the documentation or the source but did not run it. Unverified means I could not confirm it from a primary source and am telling you rather than resolving it quietly. An asterisk on a number means the vendor reported it; unasterisked numbers come from an independent measurement, and I name which one.

Where I get something wrong I correct it in the next issue and say what changed. In Issue 01 a list of risk-adjustment category codes was wrong by one entry; the rerun found it and the issue text was corrected. That will keep happening, and the alternative, quiet edits, is worse.

Research and code execution for this are done with Claude. The judgement, the corrections and the things I am willing to put my name to are mine.

Who this is for

Solution architects, engineering leads and hands-on engineers putting agents into healthcare workflows: risk adjustment, prior authorisation, clinical documentation, regulatory and quality systems, evidence generation. It assumes you can read Python, that you know roughly what FHIR is, and that someone is going to ask you to sign off on a system that writes to a patient record.

It is not for executives who want the market view, and it is not a newsletter about what AI might do to medicine. Those exist and some are excellent. This one is about the seams.
