AI Velocity Weekly

A clinician's approval that lands after the agent's time budget is dropped without a trace, and the model says "order placed"

Issue 02 · week ending 11 September 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Kumar

You want to put an agent inside a clinical or payer workflow, and you want it to do more than talk. It writes the order. It submits the prior authorisation. It files the document. The moment it acts you pick up three obligations a chatbot never had: a named human has to approve the action, you have to prove afterwards what happened, and you have to show the system is under control and validated. The failure to worry about is not a wrong answer. It is this: your log says the clinician approved and the order went in, and the FHIR server has no order. Your audit record and your system of record disagree, and nothing tells you which one is lying.

That gap does not sit still. The frameworks everyone builds on were not designed for approval, durable state and audit, and all three are being retrofitted release by release. Where the human step lives, where run state is held, what reaches the trail: it moves, and it moves in changelog lines that read like housekeeping. A bounded loop. A resumption fix. A permission default.

This week the frameworks put clocks, budgets and audiences around the human step. One now bounds the whole tool loop by wall time and counts the clinician's thinking time against that budget, so an approval that arrives late is dropped silently while the model says the order was placed. One lets a tool server check that the token it was handed was minted for it. One added a permission decision taken before a human ever sees the call. One changed what a resumed workflow does with a step that failed after its side effect, so work you thought was done runs again.

Three checks against your own system this week. Find every timeout between your agent and your humans, and ask what the audit trail records when the human answers after it has expired. Present a token from one tool server to a different one and see whether it is refused. Then, for anything that resumes after a failure, prove that a replay cannot write twice.

If this is your first issue, read the Start here page first; it sets out those obligations and the vocabulary I use below.

1.1 Agent Framework 1.18.0: the tool loop gets a wall clock, and the clinician is on it executed

The problem: you put a human approval step in front of the write, and nobody asked how long the human is allowed to take.

python/CHANGELOG.md section [1.18.0] - 2026-09-10 lists "a maximum-duration bound and stop-reason signal to the tool invocation loop" (#7772). The mechanism is in python/packages/core/agent_framework/_tools.py: FunctionInvocationConfiguration.max_duration_seconds (line 1493), checked in _apply_batch_limit_decision after each batch of tool calls. When exceeded, options["tool_choice"] = "none" and the model is asked for text. The docstring is explicit: "The budget includes time spent waiting for human approval responses. This is intentional so that long-running unattended sessions are always bounded."

The start time is a perf_counter() value stored under session.state["_function_invocation_budget_state"], but only when the harness ToolApprovalMiddleware is attached: that middleware is what copies the budget dict into client_kwargs on every request (_harness/_tool_approval.py line 388). So the question for a CPOE assistant is simple. A 30-minute budget, the clinician signs at minute 40. What happens to the write?

import asyncio, json, time
from typing import Annotated
from agent_framework import Agent, AgentSession, Message, ToolApprovalMiddleware, tool

WRITES = []

@tool(approval_mode="always_require")
def write_medication_order(patient_id: Annotated[str, "FHIR Patient id"], rxnorm: Annotated[str, "RxNorm code"]) -> str:
    """Write a MedicationRequest to the FHIR server."""
    WRITES.append((patient_id, rxnorm)); return "MedicationRequest written"

async def main(client):                                   # any shipped chat client; the lab uses a scripted one
    client.function_invocation_configuration["max_duration_seconds"] = 30 * 60
    agent = Agent(client=client, name="orders", tools=[write_medication_order],
                  middleware=[ToolApprovalMiddleware()])   # without this the clock restarts on resume
    session = AgentSession()
    r1 = await agent.run("Start metformin 500 mg for pt-123", session=session)
    req = next(c for m in r1.messages for c in m.contents if c.type == "function_approval_request")
    blob = json.dumps(session.to_dict())                  # session goes to the store, clinician reads the order
    ...                                                   # minutes pass, possibly on another worker
    session = AgentSession.from_dict(json.loads(blob))
    r2 = await agent.run(Message("user", [req.to_function_approval_response(approved=True)]), session=session)
    results = [c for m in r2.messages for c in m.contents if c.type == "function_result"]
    print(len(WRITES), results, r2.text)                  # what did the approval actually do?

asyncio.run(main(client))

Observed, three scenarios, scripted model. 30 s budget and a 1 s approval: one write, one function_result, text "Done.". 2 s budget and a 3 s approval: zero writes, zero function_result, no rejection result, no exception; the only trace is an INFO log line "Maximum duration reached (3.00s / 2.00s)", the model is called with tool_choice="none", and the scripted model, given no tool result, answers "Order placed." Same 2 s budget without ToolApprovalMiddleware: the budget state never reaches the session, the clock restarts on resume, the write happens. Script is test_af_duration_budget.py in the lab package.

What it changes. A late approval is not rejected, it is discarded, and the approved call falls through _drop_unexecutable_tool_contents_from_response with nothing returned to the model or the caller. The approval record you keep for audit will say "approved by NPI 1234567893 at 10:41" and the FHIR server will have no order. The fix is on your side: read session.state["_function_invocation_budget_state"]["start_time"] before you present the approval, and refuse to collect a signature the loop will not honour; or set max_duration_seconds=None on the client that serves approval resumes and enforce the deadline in your own queue, where you can emit an event. And note what the model said. As last week: the model's text is never the source of truth for whether a write happened.

  • start_time is time.perf_counter(), CLOCK_MONOTONIC on Linux, seconds since that host booted. A session restored on a different worker compares against a different clock, so the elapsed time is meaningless; depending on uptimes the budget may never expire or expire at once. Source-visible (_tools.py line 4127), not executed across hosts.
  • The "stop-reason signal" in the changelog is not a public field. What is observable is tool_choice="none" on the next model call and a fallback text if the model returns nothing.
  • Same release, f6a012a (#8142): FIDES PolicyEnforcementFunctionMiddleware gains max_pending_approvals=256 and pending_approval_ttl=timedelta(hours=1). Per docs/specs/004-python-function-calling-loop.md, an expired approval "executes nothing and produces a replacement approval request with the same occurrence identity and a fresh request generation". That is the behaviour you want; it lives in the FIDES policy layer, not in the duration budget. Docs and source only, not executed.
  • Unreleased on main, 119c795 (#8236, 11 Sept): RedisHistoryProvider keys become tenant and application scoped and missing session ids are rejected; key_format="legacy" opts out. Plan the migration before 1.19.

1.2 MCP Python SDK 2.2.0: a FHIR tool server can refuse a token minted for the scheduling server executed

The problem: an agent holding a token for your scheduling server can usually present it to your FHIR server, and the write goes through.

Commit 0c91368 (5 Sept, #3447) adds AuthSettings.validate_token_resource: bool | None in src/mcp/server/auth/settings.py and BearerAuthBackend(token_verifier, *, resource_server_url=None) in src/mcp/server/auth/middleware/bearer_auth.py. With the URL set, a token is accepted only if the AccessToken.resource your verifier reports (the RFC 8707 resource indicator) equals the server URL, compared as URLs with the trailing slash ignored. Unset, the SDK now warns that the default flips to True in 3.0.

from pydantic import AnyHttpUrl
from mcp.server.auth.middleware.bearer_auth import BearerAuthBackend
from mcp.server.auth.provider import AccessToken, TokenVerifier
from mcp.server.auth.settings import AuthSettings

FHIR_MCP = AnyHttpUrl("https://fhir-mcp.hospital.example/mcp")

class IntrospectingVerifier(TokenVerifier):
    async def verify_token(self, token: str) -> AccessToken | None:
        claims = await introspect(token)                  # RFC 7662 call to your authorization server
        if not claims or not claims["active"]:
            return None
        return AccessToken(token=token, client_id=claims["client_id"], scopes=claims["scope"].split(),
                           resource=claims.get("aud"),      # the audience the AS bound the token to
                           expires_at=claims.get("exp"))

settings = AuthSettings(issuer_url=AnyHttpUrl("https://idp.hospital.example"),
                        resource_server_url=FHIR_MCP, validate_token_resource=True)
backend = BearerAuthBackend(IntrospectingVerifier(), resource_server_url=FHIR_MCP)
# mount behind RequireAuthMiddleware(app, required_scopes=["patient/MedicationRequest.write"])

Observed with a stub verifier and three tokens: a token with resource equal to the FHIR MCP URL is accepted by both the loose and the pinned backend; a token issued for scheduling-mcp.hospital.example is accepted loose and refused pinned, with a WARNING naming both URLs; a token with resource=None (an authorisation server that ignores RFC 8707) is also refused when pinned. Script test_mcp_token_audience.py.

What it changes. Until now one SMART-style token from the hospital authorisation server would open every MCP server it signed, so a compromised low-risk tool (scheduling, directory lookup) could replay its token against the FHIR write server. Audience binding puts the blast radius per server, which is the property a HIPAA risk analysis wants to see stated. Audit gains a refusal event with both URLs in it. The cost: your authorisation server must actually bind tokens to the requested resource, and a legacy AS that omits the claim gets every token refused the day you enable it, so roll out with validate_token_resource=False and an alert on the WARNING first.

  • Commit 9972c21 (7 Sept, #3470) in the same release replaces Pydantic RootModel wrappers with type aliases: ContentBlock, ElicitRequestParams, EmptyResult, ClientResult, RequestId, Role and more are now unions. ContentBlock.model_validate(...) raises AttributeError (observed); use TypeAdapter(ContentBlock).validate_python(...). Not marked breaking in the changelog.
  • FuncMetadata.output_model became Any; dict[str, T] tool outputs validate through a TypeAdapter and a TODO at func_metadata.py line 507 notes Annotated metadata is lost on dict outputs.
  • c6762e8 (4 Sept): client redirects are followed only within the MCP endpoint origin. Good for PHI egress; a server behind a redirecting gateway will now fail.
  • FastMCP 4.0.3 (upload 5 Sept, 032b9f6): a tool annotated -> list or -> Sequence no longer gets an output schema or structuredContent. Annotate the item type or your structured-output consumers go quiet.

1.3 Anthropic Managed Agents: an auto permission policy that decides before the human does docs and SDK, not executed

The problem: if a machine can settle the approval question on its own, your audit trail has to show it did and on what grounds.

From the platform release notes for 10 September and the permission policies guide, cross-checked against anthropic 1.5.0 commit 62aa21b: permission_policy on any tool config now accepts {"type": "auto"} beside always_allow and always_ask. Every agent.tool_use and agent.mcp_tool_use event carries an evaluation object next to the top-level evaluated_permission; under auto the nested result is allow, ask with reason_code: "indeterminate", or deny with reason_code: "high_risk". A denied call gets a synthetic error tool result ("Permission to use {tool_name} has been denied", is_error: true), and a user.tool_confirmation sent for an event that is not ask returns HTTP 400.

{ "type": "agent_toolset_20260401",
  "default_config": { "permission_policy": { "type": "auto" } },
  "configs": [
    { "name": "fhir_write_medication_request", "permission_policy": { "type": "always_ask" } },
    { "name": "fhir_read_patient",             "permission_policy": { "type": "always_allow" } } ] }
{ "type": "agent.mcp_tool_use", "id": "sevt_01...", "name": "fhir_write_medication_request",
  "input": { "patient_id": "pt-123", "rxnorm": "197361" },
  "evaluated_permission": "ask",
  "evaluation": { "type": "always_ask" } }
// reply: {type: user.tool_confirmation, tool_use_id: sevt_01..., result: allow}   or result: deny, deny_message: ...

What it changes. The doc says it plainly: "auto is not a human checkpoint. If the server determines that a call is safe, the call runs before anyone sees it." So the design rule for a regulated toolset is the one in the snippet: auto as the default, always_ask pinned on every write to the record, and the pin reviewed in the same PR as the toolset. Two things go straight into the audit design. The evaluation object is the first time a vendor exposes why a call ran or paused as a structured field, so persist it beside the confirmation. And intent is read only from user.message events, "not from a tool result, a fetched webpage, an MCP server's response"; a FHIR document that says "the physician has approved this" cannot promote a call, which is the right default for prompt-injection through the chart.

  • The reason codes are an open union ("clients must tolerate unknown variants" in the SDK docstring), so an audit schema that enumerates them will break on the next code.
  • ant beta:sessions connect <session-id> gives a terminal approve or deny loop and a two-minute one-time Console URL with --web. The CLI version that ships it is not stated: unverified.
  • SDK 1.5.0 also refuses credentials files readable by group or others (7af3e2b, now mode & 0o077); a 0640 file that worked last week fails. And a user-profiles-2026-09-04 beta appears in the SDK (email_hash, account_status, "Anthropic does not verify them") with no public docs found: unverified.

1.4 OpenAI: Agents API public beta, and a cache diagnostic that doubles as a config-drift detector docs and SDK, not executed

The problem: a new place to run agents with nowhere visible to put the human, and a diagnostic that tells you when your validated configuration changed underneath you.

Five SDK releases in window, 3.9.0 to 3.13.0. Two matter. 1c4284a (3.13.0, 10 Sept) adds client.beta.agents with sessions, turns, environments and a streaming helper sessions.stream(session_id, input=..., tool_handlers=...) in src/openai/lib/streaming/agents/_streams.py: handlers run sequentially and a handler exception is reported to the model as {"success": false, "error": "Tool handler failed."} with the exception text deliberately withheld (_tools.py line 37). The public overview lists MCP tools, hosted or self-hosted environments, and states US data residency only and no zero-data-retention. I found no tool-approval checkpoint in the overview or quickstart; the only approval objects in the SDK types are the Responses-era mcp_approval_request and mcp_approval_response items. Whether those apply to Agents API sessions: unverified.

8326784 (3.9.0, 4 Sept, GA on 8 Sept per the diagnostics guide): Response.prompt_cache_diagnostics with type in cache_hit | cache_miss | comparison_response_not_found | unavailable and reason in model_changed, prompt_cache_key_changed, service_tier_changed, tools_changed, text_format_changed, reasoning_effort_changed, verbosity_changed, context_compacted, input_changed. You ask for it with prompt_cache_options.comparison_response_id. Read those reasons again: they are exactly the things a validated agent configuration is not supposed to change between runs.

from openai import OpenAI
client = OpenAI()
BASELINE = "resp_baseline_from_validation_run"         # the response id recorded when the extractor was validated

def extract_note(note: str, tools: list, json_schema_format: dict):
    r = client.responses.create(
        model="gpt-6-astra", instructions="Extract MEAT-supported ICD-10 codes with a verbatim span each.",
        input=note, tools=tools, text={"format": json_schema_format},   # {"type": "json_schema", "name": ..., "schema": ...}
        prompt_cache_options={"comparison_response_id": BASELINE})
    d = r.prompt_cache_diagnostics                      # None on models before gpt-5.6
    if d and d.type == "cache_miss" and d.reason in {"tools_changed", "text_format_changed",
                                                     "reasoning_effort_changed", "model_changed"}:
        raise RuntimeError(f"config drift vs validated baseline: {d.reason}")   # stop the batch, page someone
    return r.output_text

What it changes. The diagnostic was built to save money; for a validated extraction pipeline it is a free integrity check that the tool list, output schema, model and reasoning effort in production are byte-identical to the ones in the validation run, computed by the vendor from hashes. It costs nothing, never blocks the request, and the guide states raw prompts are not stored for the feature. Log reason and cache_missed_tokens per batch; a run of tools_changed is a change-control event that reached production without a ticket.

  • Diagnostic records expire "after a short period" (unstated), so the baseline id has to be refreshed, which itself is a change you must record.
  • context_compacted as a miss reason means server-side compaction rewrote your prompt; for an audit transcript that is the moment reproducibility ends.
  • Agents API helper docstring: "Only one caller may submit input to this session while the helper runs" and "Closing the stream does not cancel the backend turn". A UI that drops the connection does not stop the agent.
  • Unreleased on main (7e31f8c, 10 Sept): streaming delta merge produced invalid tool-call JSON when the first chunk carried duplicate index values. If you saw orphaned argument fragments this week, that is why.

1.5 Google ADK 2.9.0: a node that failed after its side effect runs again on resume source read, not executed

The problem: a workflow that fails just after it has written something and then resumes, which in a clinical system means a second order for the same patient.

CHANGELOG.md [2.9.0] (2026-09-10). Three breaking fixes on 8 September, all in src/google/adk/. c274ac3: workflow/utils/_rehydration_utils.py and _replay_interceptor.py now rerun a node that raised instead of replaying it as completed with no output; the changelog's own warning is that "a node that performs an external side effect and then fails will perform that side effect again on every resume". 6f2ee92: integrations/gcs/settings.py gains local_file_root: str | None = None, and a model-supplied path outside it raises ValueError("Local file path escapes the configured root"); local file access is off by default. a39ab52: before_tool_callback moves from the prepare phase into per-tool execution in flows/llm_flows/_tool_caller.py, so an approval callback now runs once per call, not once per batch. Also 3e1ae9f: warn_event_fields_not_stored() in sessions/_session_util.py logs which event fields your session backend silently drops.

What it changes. For a FHIR write node (POST Claim, POST Task) the rerun semantic is correct only if the node is idempotent: put the idempotency key (Bundle.identifier or an If-None-Exist conditional create) in the node's input, not generated inside it, or a transient failure after the POST becomes a duplicate claim on resume. The per-tool before_tool_callback makes an approval gate honest for parallel calls. The lossy-backend warning is the one to alert on: if your audit trail is the session store, a field it cannot store is a field you were never keeping.

  • Several commit hashes printed in the ADK changelog do not exist in the repository (the release branch was rewritten); cite the hashes above from git log, not the changelog.
  • 2.9.0 pins mcp>=1.24,<2; main widened to <3 on 11 Sept (d64dcfa). Under MCP 2.x, undeclared fields from a server no longer reach the caller; vendor extensions must move under _meta.

(3) Managed Agents decide allow, ask or deny before the human, with a structured evaluation on every event. (4) OpenAI's cache diagnostic reports which part of a validated configuration changed. Section 3

Papers, with the implementation note

A paper arrives as a claim. What a builder needs is the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence really supports it. Each entry below ends with that sentence.

ObGynLongBench: the evidence-to-EHR gap in longitudinal decision-making
arXiv 2609.07601 · 7 Sept · Fudan · code and data

1,500 decision points from 976 real pregnancy EHR histories, each with a pre-decision information boundary, evaluated in three scopes: evidence supplied, visit-level record, full history. Seventeen models. The gap between being handed the evidence and having to find it: Gemini-3-Flash 79.1 to 68.7, GPT-5.4-mini 77.4 to 64.9, Claude Haiku 4.5 75.5 to 59.8. Medical fine-tunes fall harder: MedGemma-1.5-4B 64.0 to 41.3, Hulu-Med-30A3 74.9 to 53.9. Among access strategies, a question-guided active-search agent beats direct full-context by 4.6 points overall and 5.7 on the hardest tier; static RAG and rolling summaries underperform. Implementation note: do not dump the chart. Have the agent name the decision target first, then retrieve for it; and stop assuming a medical fine-tune helps on longitudinal records, it lost more than the general models here.

Agents forget the rules, not the goal: constraint loss during context management
arXiv 2609.11024 · 10 Sept · Tencent Zhuque Lab · code promised at Tencent/AI-Infra-Guard

Factorial study over five models and 16 operational domains, 1,800 trajectories, manipulating goal pressure, control degradation and an executable unsafe opportunity. Neither factor alone does much; both together produce loss of control in 55% of runs (62% across ten further domains). Restoring the original control boundary drops it to 0% with the unsafe action still executable. The ablation that matters: compaction that preserves the authorisation constraints yields 0% loss of control, compaction that omits them yields 87%. Implementation note: when you summarise or compact a long EHR session, pin the scope-of-action and authorisation rules as an uncompressible block that is re-injected verbatim, and test the compactor for constraint retention, not just recall of facts. Pair this with OpenAI's context_compacted miss reason in section 1.4: it tells you when compaction happened.

Agents trust tools too much: reliance on unreliable tools
arXiv 2609.05587 · 4 Sept · Seoul National University

Fourteen models given three tools with corrupted returns: web search (418 FreshQA questions), a summarising sub-agent (45 documents) and a code executor whose stdout numbers are perturbed (300 arithmetic problems). Mean adoption of plausibly corrupted returns exceeds one third for every tool and reaches 68.0% for search; agents adopt over a third of corrupted executor outputs despite solving about 85% of the problems correctly with no tool. Corrupted evidence is equally persuasive as tool output, user text or RAG context (75.4, 77.4, 82.7%). Only 5.3% of adopting answers warn the user. Reliability metadata on the tool made corruption more persuasive, not less. Implementation note: a FHIR query result, a dose calculator or a sub-agent summary will be believed when wrong. Put range checks, independent recomputation and schema plausibility checks between the tool and the model, and surface tool-versus-model disagreement as a first-class event instead of a prompt instruction to "verify".

Will my assistant remember my allergy? What KV-cache compression forgets
arXiv 2609.05767 · 4 Sept · Duke · ACM HumanSys 2026

Existing eviction benchmarks compress a prompt that already contains the question. Hide the question and every training-free policy tested (H2O, SnapKV, StreamingLLM, DuoAttention-style) keeps an allergy mentioned in passing 0 to 1% of the time at a 20% budget, against 97% with full memory; SnapKV scores 0.975 with the question visible. The cause is the budget, not the scorer: the budget that would retain the fact is too large to be worth compressing. Replicated on Qwen2.5-7B, Llama-3.2-3B and Qwen3-8B. Implementation note: a compressed KV cache is an inference-reuse mechanism, never a persistence layer. Allergies, medications and code status get an explicit episodic store written at disclosure time, and the interface asks rather than invents when that store is empty. Read with last week's ClinTraceBench: two independent results that memory compression drops the clinical fact you needed.

VERDICT: grounded, faithful, consistent rationales for clinical trial matching
arXiv 2609.03366 · 3 Sept, announced 4 Sept · Stanford, UCLA, Emory, Mayo · EMNLP 2026 · code

LLM matchers apply eligibility policy inconsistently and write rationales that do not match their own decisions. VERDICT has the model translate the task, constraints and policy into SMT, derives the decision with an SMT or MaxSMT solver, and reports the "pivotal conditions" that would flip it. Self-faithfulness becomes a test: changing a pivotal condition must change the decision. On a SIGIR 2016-derived set and TREC 2021 it has the strongest decision accuracy among LLM-only and neurosymbolic baselines, perfect policy consistency and clinician-preferred rationales. Implementation note: for any criteria-based decision (trial eligibility, prior-auth medical necessity, coverage policy) let the model compile facts and rules and let a solver adjudicate. Determinism across patients and a machine-checked "what would change this" is exactly what a CMS-0057-F denial reason needs. Lab 5.3 is a 100-line version of this.

Auditable emergency triage for maternal and newborn care in India
arXiv 2609.09356 · 8 Sept · Noora Health, production deployment

Nurses on a WhatsApp service field over 50,000 queries a month in seven languages, mostly Romanised. The team replaced a monolithic "LLM classifies and explains" step with translation, LLM extraction of canonical symptoms against a clinician-owned vocabulary, and a deterministic rule engine that decides "emergency". Recall 0.565 to 0.810, F1 0.606 to 0.702 on 427 held-out queries; ablations attribute most of the gain to the rules, with the decomposition adding auditability at no quality cost. Since deployment: 152,421 queries, 18.7% flagged, over-escalation 17.8% with no increase in missed emergencies, and 48 rules added by clinicians without regression runs. Implementation note: separate perception (LLM to controlled vocabulary) from policy (rules clinicians can edit). You get stage-level error attribution and a blast radius per rule edit, which is what a QMS change record wants.

SIFTING: segment-level structured extraction with source spans, applied to lung cancer T-staging
arXiv 2609.07185 · 7 Sept · Axana, UCLH, NHS trusts

Reports are split into sentence-level segments with configurable context, each queried under strict output control, every finding linked to its span. On 130 radiology reports against a four-expert reference, a 4-bit Llama-3.3-70B (35 GB, self-hosted) reaches 90% T-stage accuracy (95% CI 84 to 95), statistically interchangeable with the experts. The same quantised model single-prompted scores 0.68; full-precision Llama 0.80, GPT-4.1 0.79, Qwen3-235B 0.87, DeepSeek-R1 0.86. Implementation note: per-segment prompting with mandatory span citation closed the gap from a quantised on-prem model to frontier APIs. Make the span an output field, not a post-hoc explanation, and you get the audit trail for free.

MedDeID: locally governed clinical-text de-identification from real or synthetic data
arXiv 2609.10049 · 9 Sept · University of Antwerp, UZA · code, models

On a 300-note adjudicated Dutch hospital benchmark a hospital-trained compact transformer detects 98.9% of identifying text while redacting 0.24% of non-identifier text; a synthetic-only counterpart detects 96.1%, and on 100 primary-care notes the synthetic model has higher recall (90.3 vs 87.0) and is more robust to identifier-format perturbations. An English instantiation trained with no real text detects 99.7% and 98.9% of identifier characters on two external synthetic benchmarks (transfer evidence only, the authors say). Real hospital weights are not released. Implementation note: synthetic-trained de-id is within three points of hospital-trained and generalises better across sites; run the released perturbation battery against whatever de-id layer sits in front of your agent before you trust it.

Also in window: VERGE, a bounded verify-refine loop on Llama-3.1-8B that lifts extraction precision 0.764 to 0.849 with 1.5% escalated to humans (2609.04366); rubric-guided OUD phenotyping with OPRO, F1 0.774 and 44% relative gain over zero-shot (2609.05682); MedWER, a model-free term-restricted WER for medical ASR, pip install medwer (2609.05728); risk-constrained stopping for sequential diagnosis agents, AUROC 0.853 vs 0.552 (2609.09678); a deterministic Python solver for MedCalc-Bench that helps at 32B and not reliably at 7B, and flags 16 of 55 benchmark formulas (2609.10728); CapScope, a capability-scoped harness that executes injected actions in 3 of 75 runs against 33 to 47 for baselines (2609.08371); KVMem, million-token agent workspaces on a 24 GB laptop GPU (2609.04852); LogiMed-RoB, 98.9% atomic consistency collapsing to 45.1% end-to-end on Cochrane logic (2609.11185). Nothing in window on prior authorisation, ambient note generation or ICD coding specifically.

Section 5

Lab: three things to run this week

Reading about a failure mode is not the same as watching it happen on your own machine, and only one of those changes what you build. Each of these takes about half an hour and ends with a change that points it at your own system.

5.1 The approval that arrives too late

The problem: your approval step has a deadline, and you have never seen what your clinician is told when they miss it.

test_af_duration_budget.py is the executed version of section 1.1: a scripted chat client composed with the shipped FunctionInvocationLayer, a write_medication_order tool with approval_mode="always_require", a session serialised to JSON between the request and the clinician's answer, three scenarios. pip install "agent-framework-core==1.18.0", no model key. Watch scenario B: zero writes, no result, "Order placed." Then change one thing: replace the scripted "Order placed." with what your real model says when tools are withdrawn and it has no tool result. That sentence is what your clinician would have read.

5.2 The token that opens the wrong server

The problem: you do not know which of your own tool servers will accept credentials that were issued for a different one.

test_mcp_token_audience.py, pip install "mcp==2.2.0". A stub TokenVerifier, three tokens, the loose and the pinned BearerAuthBackend, plus the ContentBlock alias change. Point the stub at your real introspection endpoint and run it against a token from each of your MCP servers; every "accepted" on the pinned line that should be "refused" is a finding for the risk register.

5.3 Prior authorisation as a solver problem

The problem: a denial reason you can defend has to come out the same every time the facts are the same.

prior_auth_verdict_lab.py, pip install z3-solver. One payer rule for MRI brain with contrast (CPT 70553) as propositional logic, six facts an extractor would pull from the attachment with the supporting span each, a z3 decision, the pivotal conditions computed by flipping each fact, a self-faithfulness assertion in the VERDICT sense, and a ClaimResponse-shaped stub whose denial reason is computed rather than drafted. Run it, then change the prior MRI to 80 days ago and watch the reason change to the single fact that caused it. Then replace the fact dictionary with a Pydantic AI agent returning the same typed shape from a synthetic note, and diff its facts against yours: that disagreement rate is the extraction eval, and the solver never moves.

LinkedIn post candidate

I gave an agent a 30-minute budget and a clinician who took 40. The order vanished and the model said "Order placed."

Microsoft's Agent Framework 1.18.0 added a wall-clock budget to the tool loop, and the docstring says the budget includes time spent waiting for human approval. Intentional, and sensible for unattended runs. So I ran it with a scripted model and no API key: a MedicationRequest write that requires approval, the session serialised to JSON while the clinician thinks, then the approval comes back after the budget.

Result: zero writes, no function result, no rejection, no exception. One INFO log line. The model is called with tools withdrawn, and with nothing to go on it says the order was placed. Your audit table records an approval by NPI at 10:41; the FHIR server has no order. And the budget only survives the round trip when ToolApprovalMiddleware is attached; without it the clock quietly restarts.

The same week, the MCP Python SDK let a FHIR tool server refuse a token minted for the scheduling server, Anthropic added a server-side permission policy that decides before a human sees the call, and Google's ADK started re-running failed workflow nodes on resume. The human step is getting clocks, audiences and pre-checks. Each is a place your approval record and your system of record can disagree. Code and diagram in the issue.
