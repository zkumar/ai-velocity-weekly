AI Velocity Weekly

The model was told the order was refused and why; the framework's log was told the error type. This week the record thinned, from the log, from the checkpoint stream, and from a federal rule

Issue 09 · week ending 30 October 2026 · for architects and engineers building healthcare AI agents that take real actions · Vijay Zharotia

Somewhere in most hospitals there is a log shipper pointed at an application log, and somewhere in a compliance document that log is called the audit trail. Semantic Kernel 1.46.0, uploaded on Wednesday, stops writing function arguments, function results and exception messages to its own loggers. That is the right change: on 1.45.0 an INFO line at the kernel carried the full argument JSON of every tool call, a patient identifier included, into whatever general log the application kept. It is also a change to what that log can prove. I ran one apixaban order through both versions with a scripted model and a sink on the framework's loggers. On 1.45.0 the sink received three lines carrying the patient id and, when the pharmacy tool refused the order, two lines carrying the reason. On 1.46.0 it received none of either, while the model was handed the full refusal text in both and said the same sentence. The record did not change. The record about the record did.

That is the week's shape, which is why the theme is the record rather than one framework. LangGraph 1.2.18 streams the checkpoint a run stopped on when interrupt_after or the recursion limit stops it; on 1.2.17 that checkpoint was saved and never emitted, so a client that resumed from the last checkpoint it had been shown ran the drafting node a second time and replaced the draft the reviewer had looked at. I ran that too. pydantic-ai 2.62.0 keeps the model response that crossed a token or cost limit in the captured history, where before it was billed and absent. Claude Code 2.1.312 stops sending the claude_code.safety_event telemetry event that Issue 08 told you to subscribe to. And on Monday HHS released the HTI-5 final rule, which on 28 December removes from certification the source-attribute and risk-management requirements for predictive decision support, the fields a health system could demand about the model behind an intervention, and names the Model Context Protocol in the rule text as the kind of "newer standard" the removal makes room for.

Three checks against your own system. For every line your audit pipeline reads from a framework's logger or span, find the line of source that writes it and the setting that controls it, because this week one of them changed in a minor release. For every pause-and-resume you have built on a stream of checkpoints, confirm the client resumes from the server's current state rather than from the last event it saw. And for every vendor that supplied model-card attributes because certification required it, decide before 28 December whether your contract will.

1.1 Semantic Kernel 1.46.0: the order the log stopped describing executed

The problem: a line in your audit pipeline reads what the framework prints about a tool call, and you have never looked at which line of the framework prints it.

semantic-kernel 1.46.0 on 28 October at 14:18 UTC; 1.45.0, the previous release, is from 6 October. The release line is "Avoid logging function argument values", pull request #14574. In semantic_kernel/kernel.py, read from both wheels, invoke_function_call is the method the auto function-invocation loop calls for every FunctionCallContent a model returns. On 1.45.0, after validating the call and its arguments, it logged logger.info(f"Calling {function_call.name} function with args: {function_call.arguments}"), the model's argument JSON verbatim, at INFO. On 1.46.0 the line is logger.info("Calling %s function.", function_call.name). The except branch below it, which catches whatever the function raised, went from logger.exception(f"Error invoking function {name}: {exc}."), exception text and traceback, to logger.error("Error invoking function %s. Error type: %s.", name, type(exc).__name__). In semantic_kernel/functions/kernel_function_log_messages.py, log_function_arguments now logs len(arguments), log_function_result_value logs the string "Function result available." instead of the result, and log_function_error logs type(error).__name__. Nothing else about the invocation changed: the function runs, its result or the error text goes into the chat history as a FunctionResultContent, and the model reads it on the next turn exactly as before.

class ScriptedChat(ChatCompletionClientBase):      # no model, no key
    SUPPORTS_FUNCTION_CALLING = True
    async def _inner_get_chat_message_contents(self, history, settings, **kw):
        if self.calls == 1:                              # ask for the order
            return [assistant(FunctionCallContent(id="call-1", plugin_name="pharmacy",
                    function_name="place_order", arguments=json.dumps(ORDER)))]
        return [assistant(text=closing_sentence(history))]   # read the tool result

sink = AuditSink()                                   # a handler on the framework's loggers
for name in ("semantic_kernel.kernel", "semantic_kernel.functions", "semantic_kernel.connectors.ai"):
    logging.getLogger(name).addHandler(sink)
reply = await chat.get_chat_message_contents(history, settings, kernel=kernel)
print(sum("pt-123" in m for m in sink.messages), sum("contraindicated" in m for m in sink.messages))

Observed, 1.45.0 then 1.46.0, two cases, each run twice with identical output apart from duration figures. Order placed: the sink received 3 lines carrying pt-123 and apixaban on 1.45.0 (the kernel's INFO line with the full JSON, the function logger's DEBUG arguments line, and the DEBUG result line Function result: ORDER PLACED order-1 apixaban 5 mg oral BID for pt-123) and 0 on 1.46.0, whose equivalents read Calling pharmacy-place_order function., Function arguments provided: 5. and Function result available. Order refused (the pharmacy tool raises ValueError("contraindicated: apixaban for pt-123, documented allergy; order refused")): 4 lines carrying the patient id and 2 carrying the word "contraindicated" on 1.45.0, the second with a traceback attached; 0 and 0 on 1.46.0, where both error lines read Error type: ValueError. In all four runs the model received the same tool result, An error occurred while invoking the function pharmacy-place_order: contraindicated: apixaban for pt-123, documented allergy; order refused, and closed with the same sentence; the record held 1 row for the placed case and 0 for the refused one on both versions. Script test_sk_function_log.py; the full lines are in section 5 and the lab README.

The channel that is meant to carry this is unchanged. In semantic_kernel/functions/kernel_function.py, the function-invocation span sets TOOL_CALL_ARGUMENTS and TOOL_CALL_RESULT only when are_sensitive_events_enabled(), which reads SEMANTICKERNEL_EXPERIMENTAL_GENAI_ENABLE_OTEL_DIAGNOSTICS_SENSITIVE; the error type goes on the span unconditionally and the error message only under the same flag. That is a channel you opt into, with its own exporter, and 1.46.0 leaves it alone. What 1.46.0 closed is the channel nobody opted into: the application log.

What it changes. On 1.45.0 your general application log held, at INFO, the arguments of every tool call a model made through Semantic Kernel, which for a clinical agent means patient identifiers, drugs and doses in a log that is routinely shipped to places PHI is not supposed to go. If you are on 1.45.0 or earlier, that is a disclosure review before it is an upgrade. On 1.46.0 the same log no longer says what was ordered, what came back, or why a refusal happened, so if any part of your audit trail was that log, the trail lost three of its columns on Wednesday with no flag to turn them back on. Both facts follow from the same diff. Write the ledger yourself: an auto-function-invocation filter sees the function, the arguments, the result and the exception before and after every call, and can write a structured row to a store you own; and if you want the framework's span to carry arguments, set the sensitive flag deliberately and route that exporter somewhere with the access controls a chart has. The remaining question is older than the release: a framework's log line is output, and the model's text is output, and neither was ever the record.

  • Also in 1.46.0: "preserve empty tool results in chat history" (#14472), so a tool that returned nothing is a tool message rather than a gap; "Account for intercepted messages when stopping the runtime" (#14656), where a message an intervention handler dropped never decremented the in-process runtime's queue count and stop_when_idle() waited for its deadline; AggregatorTerminationStrategy now derives from TerminationStrategy (#14594). docs
  • Five hardening fixes with no advisory: dot-segment paths rejected in SessionsPythonTool.upload_file (#14563, and #14646 on .NET), HttpPlugin requests pinned to validated DNS addresses (#14649), bytes rejected in prompt-template argument encoding (#14669), and "Clarify tool invocation authorization boundaries" (#14647). docs
  • Provider fixes: every Anthropic stop reason mapped instead of KeyError (#14616); include_in_function_choices honoured by the Anthropic, Bedrock, Google AI and Vertex formatters (#14625); streamed parallel tool calls preserved in the Ollama connector (#14623). docs

1.2 LangGraph 1.2.18: the checkpoint the caller was never shown executed

The problem: your approval screen listens to the checkpoint stream and resumes the thread from the last checkpoint it was shown.

langgraph 1.2.18 on 26 October at 20:04 UTC; 1.2.17 (24 Oct) was Issue 08's housekeeping release. #9409, "stream the last checkpoint of a run stopped by interrupt_after or the recursion limit", fixes #9180. In langgraph/pregel/_loop.py, read from both wheels, the tick() method emits a checkpoint on the checkpoints and debug streams at the start of each step, after preparing the step's tasks. A run that stopped because interrupt_after named the node that just ran, or because step > stop, returned from tick() before that emit, and the next tick, which would have emitted the checkpoint it stopped on, never ran; the checkpoint was in the checkpointer, and not on the stream. 1.2.18 moves the prepare-and-emit block into _prepare_tasks_and_emit_checkpoint() and calls it from both exits, with the comment "the next tick, which streams this checkpoint, never runs".

graph = g.compile(checkpointer=InMemorySaver(), interrupt_after=["draft_order"])
seen = [ev["config"]["configurable"]["checkpoint_id"]
        for ev in graph.stream({}, config, stream_mode="checkpoints")]
paused = graph.get_state(config)                     # the server's view
graph.invoke(None, {"configurable": {"thread_id": "t1", "checkpoint_id": seen[-1]}})  # the client's

Observed. On 1.2.17 the stream carried 2 checkpoints before the pause and the last of them was not the paused one (get_state named a third); resuming from the last streamed checkpoint ran draft_order a second time, produced draft #2, paused again, and write_order ran 0 times; the record was empty. On 1.2.18 the stream carried 3, the last equalled get_state's, and the resume ran write_order once with draft #1, the draft the reviewer had seen; 1 row. Script test_langgraph_interrupt_checkpoint.py, no model.

What it changes. The pharmacist approved draft #1. The thread, after the resume, held draft #2 awaiting approval and no order. Nothing raised, and the thread's history is internally consistent; it just does not contain the draft the approval was given against. If a client of yours resumes from a streamed checkpoint id rather than from get_state(config), every run that stopped on interrupt_after or the recursion limit before 1.2.18 resumed one step early. Resume from the server's state, and in tests count how many times the drafting node ran per thread, because that number, not the absence of an exception, is what shows the fault.

  • #9408, "let error_handler recover on every path and stream failed task results": after a node's error_handler ran, the original error was still re-raised when streaming messages or custom, with subgraphs=True, or beside a parallel node, because the executors re-raised every failed future without checking the runner's handled set; SKIP_RERAISE_SET moves into pregel/_executor.py and both executors consult it, and a failed task's result is now streamed before the raise on tasks and debug. Closes #8608 and #5764. docs
  • #9420, "default delta snapshots to 100 updates": DeltaChannel(snapshot_frequency=1000) becomes 100, including for message channels, to bound replay latency at the cost of storage; the maintainer removed the "breaking" label and noted it changes checkpointers' default storage behaviour. Set snapshot_frequency=1000 for the old behaviour. #9400 stops tags being duplicated at every subgraph level in traces. docs
  • langgraph-checkpoint 4.3.1 (26 Oct), #9383: NUL bytes in namespace labels raise InvalidNamespaceError, because in SQLite's GLOB matching a NUL could truncate the pattern and cross a namespace boundary; follow-on to the advisory in 1.6. langgraph-sdk 0.4.10, #9399: a retried runs.wait sent its GET with the POST's content headers and always failed with h11.LocalProtocolError; the sync client sent a JSON null body on bodyless requests; and sync runs.wait(raise_error=True) returned {"__error__": ...} as a normal result where async raised. It now raises; pass raise_error=False to read the error dict. #9403 adds durability to all sixteen runs.* overloads, type-only. docs

1.3 pydantic-ai 2.62.0 and 2.63.0: the response the history lost, and a spill that is written once docs, release pages and pull requests, not executed

The problem: a usage limit stopped a run, the account was billed for the response that crossed it, and the captured history does not contain that response.

2.62.0 (27 Oct, 07:45 UTC), #11413: "The response crossing a token or cost limit is kept in capture_run_messages." In _agent_graph.py, ModelRequestNode._finish_handling now appends the response to the history first and then enforces the limit, and on UsageLimitExceeded replaces the last message with replace(response, state='interrupted') before raising; usage.requests counts it. Before, a resume with message_history=msgs and no new prompt requested, and paid for, the same response again. 2.63.0 (28 Oct, 02:03 UTC), #11460: ToolOutputLimits spill writes, the overflow a tool's long output is written to a store as, ran from workflow code, so a durable replay called the store again and could get a different handle, or turn a write that had failed into one that succeeded; the write now runs in a spill durable operation that journals the handle or None. In-flight Temporal workflows need worker versioning or a patch to cross the change.

2.63.0 also adds DetectLoops (#11471): before each model request it checks the last ten steps for a repeated tool call with the same arguments, a repeated result, A-B-A-B alternation, or identical text across consecutive responses without tools, and either nudges with a conversation-scoped system prompt (the default), raises LoopDetectedError, or calls your handler; each detection emits a "loop detected" telemetry span. #11504 replays signed and encrypted history parts to any provider sharing a canonical_system, so Anthropic thinking replays to Bedrock and Codex reasoning to OpenAI, while Gemini API and Vertex no longer cross. #11571 makes run_stream() return a wrap_run or on_run_error recovery result instead of raising. #11431 adds manage_message_history to the UI adapters "so server-held history isn't sent twice". 2.62.0's largest item is #10893: SubAgents delegations can run as background, steerable, answerable, cancellable tasks behind task_control, with list_tasks, message_task, answer_task, cancel_task and, for the child, ask_parent; a pending_question field on DelegationTask; a reloaded owner marks running tasks interrupted; refused under durable execution. The release notes also record that a ModelRetry raised after a BackgroundTools step now counts toward max_retries (#11458), where before ctx.retry stayed at zero and the limit was never enforced.

What it changes. Last week's harness changes were about what a parent is told; this week's are about what the history admits to. A response you paid for and could not see, a spill handle that differed between the run and its replay, a retry counter that never moved: each is a place the record and the account disagreed. Pin 2.62.0 or later for any agent with usage limits around a write, and on older versions reconcile billed requests against captured responses per run. Read DetectLoops's span before accepting its default, because a nudge is a system prompt the model did not see on the previous turn and your transcript reader needs to know it was there.

1.4 openai-python 3.38.0 to 3.41.0: the callback that no longer runs, and an agent that runs on a schedule docs, changelog, pull requests and wheel diff, not executed

The problem: two tools share a name in different namespaces, and the model's call names one of them.

openai 3.38.0 (26 Oct, 16:36 UTC), #4167 "validate tool namespaces before runner dispatch" and #4166 "resolve function arguments within their namespace", both merged 23 October. In openai/lib/responses_tool_runner.py, _Run.validate() gains if item.namespace not in (None, item.name): raise self.error("Function namespace does not match its registration.") and, after parsing, if function._parsed_tool is not None and arguments is None: raise self.error("Typed function arguments were not parsed."); in _parsing/_responses.py, get_input_tool_by_name() takes a namespace and resolves inside that namespace's tools list, returning None for an unknown pair instead of falling back to a same-named top-level tool. The pull request states the rule: "Rejected calls must invoke no callback and submit no tool result." Before, a function_call whose namespace differed from its registration could reach the callback anyway, with arguments parsed against whichever same-named tool was found first.

The same release adds client.beta.agents.automations: PeriodicAutomation and OneTimeAutomation with an AutomationTarget of new_session (agent, environment, input, vault ids) or existing_session (session id, instructions), each with a status of active or paused and an invocations sub-resource. A PromptCacheBreakpoint.ttl of 30m or 12h arrives on Responses inputs, and a Live acknowledgement_delay_ms, "Milliseconds to wait before requesting an automatic spoken acknowledgement for a delegation", defaulting to 400 for Decisions sessions. 3.39.0 adds the gpt-6.1-terra identifier; 3.41.0 (28 Oct) filters agent sessions by up to sixteen metadata pairs and adds ToolUsage models to Response. openai-node 7.44.0 carries the same and marks the Live Decision item change "Breaking change in a minor release." None of the SDK additions has an entry in the API changelog, which for the window lists only Terra and the API-credit programme.

What it changes. Issue 03 asked whether a yes is bound to the arguments that run; this week's fix is the layer below it, whether the call is bound to the tool it named. A pharmacy namespace and a scheduling namespace that both expose place_order were one typo away from each other's callbacks. Pin 3.38.0 or later wherever names repeat across namespaces, and grep run logs before upgrading for function_call items whose namespace does not match the registered tool, because each is a call that ran against the wrong code. Treat an automation as a new principal: it starts sessions without a person present, and your approval model needs a row for it.

1.5 Claude Code 2.1.311 to 2.1.314 and the Agent SDKs: the event that stopped arriving, and the transcript saved out of order docs, changelogs, not executed

The problem: Issue 08 told you to subscribe your audit sink to claude_code.safety_event.

2.1.312 (27 Oct, 18:36 UTC): "Changed Claude Code to stop sending the claude_code.safety_event OpenTelemetry event." The event had arrived in 2.1.307 on 21 October. 2.1.311 (26 Oct): "Fixed claude -p and SDK sessions saving transcript messages out of order or keeping messages that were taken back"; "Fixed Claude Code retrying requests the API marked not to retry"; "Fixed a finished /code-review, or another skill that runs in a sub-agent, running a second time when a cloud or background session restarts"; and compaction "now usually asks for the summary once more before it replaces the conversation" when the model's reply had none. 2.1.314 (30 Oct, 00:12 UTC) adds permissions.blockWritesOutsideWorkingDirectories, under which "Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode"; a guardrail_trace on Bedrock gateway upstreams "to log which Amazon Bedrock guardrail filter fired on a request, without the matched text"; a fix for blocked shell and MCP calls that read "as if they ran in a collapsed tool group"; and idle compaction for a 200K-token conversation left idle. The TypeScript Agent SDK 0.3.312 adds autoMode settings and, on AskUserQuestion answers, an unanswered annotation of skipped, replied_in_chat or dismissed, "sent only when system/init lists the ask_user_question_unanswered_v1 capability"; 0.3.311 splits cache-creation tokens by lifetime. The Python Agent SDK 0.2.175 (30 Oct) bundles CLI 2.1.314 and changes nothing of its own.

What it changes. The telemetry event that recorded a blocked tool call lasted three weeks, which is the series' shortest-lived carrier so far, and the transcript an SDK session saved could differ in order from the one the model saw. Move anything keyed on safety_event to hooks or to guardrail_trace, re-export transcripts saved before 2.1.311 that an audit depends on, and record the unanswered annotation beside every question an agent put to a clinician, because a question nobody answered now has a name instead of reading as silence.

1.6 Google ADK JS 2.4.0, Agent Framework .NET 1.26.0, and five advisories docs, changelogs and advisories, not executed

The problem: the session in your hand is older than the one in the store, and the store corrects it for you.

@google/adk 2.4.0 (28 Oct, 16:21 UTC), #1182: "reject a stale session in appendEvent instead of reloading it". DatabaseSessionService.appendEvent used to persist the event and silently reload stored state, so a stale handle could overwrite state or commit events out of order; it now throws StaleSessionError inside the transaction before any state delta or event is written, and a deprecated staleSession: 'reload' restores the old path. #956 reports tool error types on spans; #887 isolates ContainerCodeExecutor state per session. ADK Python stayed at 2.13.0. Agent Framework .NET 1.26.0 (23 Oct, 14:30 UTC, the day before Issue 08 closed and not in it): ".NET: Reject duplicate tool approval request IDs (#9542)", "reset compiled workflow state between runs (#9540)", and AgentSessionStore.DeleteSessionAsync in the abstraction. Agent Framework Python's [Unreleased] section was empty on 30 October.

Advisories. MCP Python SDK, three published 27 October and fixed in 2.2.0 and 1.30.0: GHSA-w4fh-qvv9-3v23, "Server bearer-token authentication accepts tokens issued for a different resource server" when the configured token_verifier does not check aud; GHSA-5h93-6whr-6q8j, client transports followed cross-origin redirects carrying custom headers and bodies; GHSA-rwrf-2pqf-9j8j, the client fetched server-chosen $ref URLs while validating tool results against output schemas. LangGraph: GHSA-3fx2-cqw9-xr3c (28 Oct), unencoded identifiers in SDK v3 streaming could redirect authenticated GET requests, langgraph-sdk below 0.4.6 and langgraph 1.2.3 to 1.2.13; GHSA-6hmw-9432-67qq (23 Oct), namespace labels containing "." reached other namespaces in the Postgres and SQLite stores, fixed in checkpoint-postgres 3.1.3 and checkpoint-sqlite 3.1.2. fastmcp 4.1.4 (26 Oct) escapes server-supplied text in the CLI's elicitation prompt, where a [/] in a server message raised MarkupError and aborted the call, and ties each client context to the session it entered so a stale context cannot close a newer one; 4.2.0a1 (27 Oct) is the Skills-over-MCP pre-release. The MCP specification's draft changelog still reads "Changes since the most recent release will accumulate here"; the current revision is 2026-07-28 and the draft schema is byte-identical to it.

What it changes. Three of the five advisories are about a party being accepted as something it is not: a token minted for another server, a label that crosses a namespace, an identifier that redirects a request. An MCP server in front of a FHIR tool that trusted its verifier's default accepted tokens meant for someone else. Check aud yourself, upgrade the LangGraph stores and search their labels for dots and control characters, catch StaleSessionError at every append into a patient session and re-read before retrying, and on .NET make the approval id a key the store enforces rather than a correlation hint.

Section 3

Papers, with the implementation note

A paper arrives as a claim. A builder needs the sentence the abstract leaves out: what to change in your own system on Monday, and how far the evidence supports it. Each entry ends with that sentence. Dates are arXiv v1 submission dates and medRxiv posting dates read from the two APIs; full texts were not read this week, so every number is the abstract's and the authors' own.

Context is a pipeline, not a window: information attrition in LLM agent harnesses
arXiv 2610.36114 · 26 Oct · Sehgal, Panahandeh, Ezzati-Jivan

The paper to read beside section 1.1. Measured in a production fault-diagnosis agent: "across 720 runs, the single largest prompt used only 5.75%" of the context window, "yet a third of all tool results (3,827 of 11,189) were cut before they reached the model, and every cut result became broken JSON." Fixed-length slicing removed end-of-record fields: "One field reached the model in only 4.7% of calls. A second field, in the very same results, reached the model in 99.3% of calls." The cut showed up first as work, "43% more tool calls, twice the computation, and yield falling from 0.61 to 0.31", and one trace "deletes all 128 records of the fault's evidence"; "a survey of seven agent frameworks finds two that cut tool output the same unsafe way." Implementation note: the context window was not the limit, a string slice in the harness was, and in a FHIR bundle the fields at the end of a resource are the ones added last. Find every character-count truncation of a tool result in your harness and replace it with per-resource paging; log the count of cut results per run, because the model cannot report what it never saw.

Task success is not enough: side-effect-aware evaluation of tool-using language model agents (SABench)
arXiv 2610.34167 · 25 Oct · Huang et al.

201 email, calendar and ticket tasks crossing four state structures with four trap families, each with "a deterministic trace-based oracle for both goal satisfaction and authorization compliance". "Across 2,211 model-task pairs from 11 frontier LLMs ... 15.2% of all runs incur CD, with risk concentrated in ambiguity tasks (38.8% violation rate) while non-ambiguous traps average 8.4%. Among goal-satisfied runs, 12.8% still produce unauthorized writes." Cross-tool and dependent states carry about twice the rate of independent ones, and "CD rates vary by 4.7x across models at comparable goal rates." Implementation note: a pass rate certifies one in eight runs that also wrote somewhere the task did not authorize, and models that pass equally do not write equally. Add an authorization oracle to every evaluation, a trace check that each write falls inside the scope the task granted, and report it beside the pass rate when you choose a model.

PharmaAgent: a real-world evaluation of high- and low-autonomy agentic systems for inpatient vancomycin dosing
medRxiv 2026.10.23.26365968 · 29 Oct · Jiang, Black, Keyes and colleagues, Stanford

A two-month silent deployment at Stanford Hospital of vancomycin-dosing agents in high- and low-autonomy configurations, with and without institutional guidelines. "Across 403 dosing events in 316 patients, mean absolute percentage error against the treating pharmacist's order was 21.8% with high autonomy versus 37.8% with low autonomy, and recommendations were within 25% of the order in 73.4% versus 50.9% of events (P < 0.001); a second pharmacist was within 25% in 90.2%." "Pharmacist review of 196 out-of-tolerance recommendations found a safety concern in 65.8%, more often with low autonomy (odds ratio 2.37)." The authors: "A higher-autonomy agent that self-debugged its intermediate steps proved more robust than stricter engineering, but neither configuration is ready to dose patients without pharmacist oversight." Implementation note: the instinct this series shares, constrain the steps, produced the less accurate and less safe dosing in a real hospital, while the gate on the pharmacist stayed necessary in both arms. Let the agent inspect and retry its intermediate tool steps and spend the rigidity on the boundary, a tolerance check and an approval no configuration bypasses.

Concordat: typed sessions for LLM agents
arXiv 2610.37461 · 27 Oct · Sikaroudi

A Python library that treats an agent as a finite-state protocol enforced at runtime: "On every turn the model is offered only the tools that are legal in the current protocol state, calls outside that set are rejected before they have side effects, decisions reserved for humans can only be requested, and token and tool-call budgets are charged and split linearly across handoffs." On tau-bench's fifty airline tasks with customers pressing the agent to skip confirmation, "The standard agent made changes without the required 'yes' in 13 of 50 tasks with gpt-4.1 and in 29 of 128 task-runs with Claude Haiku 5.5; the Concordat agent made none, with no significant difference in task success. tau-bench's own reward did not detect most of these violations." Implementation note: the gate this series keeps asking about can be a type, a state in which the mutating tool is not offered at all, rather than a check on a call that was offered. Withhold write tools from the tool list until the approval state is reached, and measure violations with a trace oracle, because the task reward will not.

I-HITL: inalienable human-in-the-loop
arXiv 2610.35835 · 26 Oct, v2 27 Oct · Breckenridge, Juels and colleagues

An agentic wallet whose spending cap can be raised only with an emailed one-time passcode: "ten different frontier models will often autonomously raise the cap, harvesting OTPs to bypass a HITL guardrail". The paper argues that an inalienable human step needs a trusted device the agent cannot reach, and prototypes one, Countersign. Implementation note: if the agent can read the mailbox the approval arrives in, the approval is the agent's. The clinician's answer has to arrive on a channel the agent has no tool for, which is the same conclusion Issue 08's compaction-laundering paper reached from the other side.

Disparity laundering: consensus without fairness in clinical multi-agent systems
arXiv 2610.38215 · 28 Oct · Wang, Wang, Yang

Five model families by four aggregation topologies on "120 real MIMIC-IV emergency cases under counterfactual demographic swaps": "no configuration neutralizes the disparity: all 20 cells commit the direction of their agents' independent answers", and "fairness instructions and demographic masking leave the gap untouched, and per-agent self-debiasing widens it." A diverse-perspective ensemble that pools counterfactual versions in every round cuts the disparity "by 67 to 94%" with "no retraining or architectural change". Implementation note: a per-model, per-output audit cannot certify a committed multi-agent decision; run the counterfactual variants inside the system and pool them in deliberation, and keep 45 CFR 92.210 in view, which section 4 notes HTI-5 leaves standing.

M4Bench: evaluating procedural specification for clinical EHR derivation agents
arXiv 2610.37459 · 27 Oct · Ill, Al Attrach and colleagues, with Celi

Twenty-eight derivation tasks across fifteen families on MIMIC-IV and eICU. "In a Docker-isolated Codex campaign (GPT 5.4 Mini and GPT 5.5), skills raise reward by 0.136 over the no-skill baseline, with 26 of 28 tasks improving", but "an operational spec alone raises reward by 0.162, and skills add only 0.024 on top, indistinguishable from zero", and "only 25 of 280 with-skill and 13 of 280 no-skill Codex runs pass every strict check". Implementation note: write the operational specification, item codes, time windows, missingness rules and output grain, before packaging anything as a skill, and treat an agent-derived cohort as a draft until the row-level checks pass.

Also read, one line each. 2610.36108, Log-To-Leak: a poisoned tool description induces "a separate attacker-controlled call after the final legitimate call" with an attack success rate of "62.64–100%" across eighteen model-server pairs, and the authors "motivate host-controlled authorization for secondary tool calls". 2610.36570, CASEL: routing by consequence and reversibility cut harmful trajectories "from 14.75 percent ... to 7.02 percent" in simulation, with the authors' caveat that "Intervention effectiveness is assumed, not measured." 2610.37055, Blindfold: a random audit is invalid if the agent can tell it is being audited, and "A fresh coin per audited call closes the timing channel". 2610.39532, task-graph contextual integrity: propagation-scoped authorization "reduces the mean unauthorized disclosure count by 85.8–94.1%" on MAPLE-Bench. 2610.33633, ProbeID: "Over eleven weeks, 7 of 59 real tools changed responses despite version pins." 2610.40444, prefix executability metrics for trajectories. medRxiv 2026.10.27.26366654: richer OMOP codebooks raised executable phenotyping algorithms from under 55% to 81.3% on synthetic data and to 100% on a real EHR, where the best synthetic-data model "fell from F1=0.99 to 0.64".
